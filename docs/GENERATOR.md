# Генератор Room Forge: раскладка, наполнение, экспорт

Документ для программиста движка. Цель — чтобы движок мог **повторить прогон бит в бит** по тому же
проекту и сиду либо просто прочитать готовый экспорт (`room-forge-run`). Реализация-эталон:
`src/gen/generate.ts`, `src/gen/geom.ts`, `src/gen/world.ts`, ГСЧ — `src/model/rng.ts`.

Соглашения (как во всём проекте):

- единица длины — клетка (`settings.cellM` = 0.1 м), ось **Y вниз**;
- клетка `(x, y)` — квадрат `[x, x+1] × [y, y+1]`, центр клетки — точка `(x+0.5, y+0.5)`;
- стороны: `N` — вверх (y−1), `S` — вниз (y+1), `E` — вправо (x+1), `W` — влево (x−1);
- поворот `rot` — градусы по часовой (при оси Y вниз визуально тоже по часовой), N→E→S→W.

## 1. ГСЧ (обязателен для повторения)

**Хэш строки** (FNV-1a, 32 бита) — по **кодовым единицам UTF-16** (`charCodeAt`), не по байтам UTF-8.
Для русских сидов это важно.

```
h = 0x811c9dc5
for каждой UTF-16 единицы c:  h = (h XOR c) * 0x01000193   (умножение mod 2^32)
результат — uint32
```

**Поток** `makeRng(seed)` — mulberry32. Состояние `a` (uint32) = hash(seed) (или само число, если сид — число).
`base` = начальное значение `a`.

```
next():
  a = (a + 0x6D2B79F5) mod 2^32
  t = a
  t = imul(t ^ (t >>> 15), t | 1)
  t ^= t + imul(t ^ (t >>> 7), t | 61)
  return ((t ^ (t >>> 14)) >>> 0) / 4294967296        // double в [0, 1)
```

`imul` — младшие 32 бита произведения; `>>>` — беззнаковый сдвиг; `^`, `|`, `+` в 32 битах.

Производные операции (точно в таком виде, считать в double):

| операция | определение | обращений к next() |
|---|---|---|
| `int(lo, hi)` | если `hi < lo` → `lo` **без обращения**; иначе `lo + floor(next()·(hi−lo+1))` | 0 или 1 |
| `chance(p)` | `next() < p` | 1 (всегда, даже при p = 0 или 1) |
| `pick(arr)` | `arr[floor(next()·len)]` | 1 (даже при len = 1) |
| `weightedIndex(w)` | `sum = Σ max(0, wᵢ)` по порядку; если `sum ≤ 0` → **−1 без обращения**; иначе `r = next()·sum`; по порядку `r -= max(0, wᵢ)`, первый `i` с `r < 0`; если не нашлось — последний индекс | 0 или 1 |
| `shuffle(arr)` | Фишер–Йетс с конца: `for i = n−1 … 1: j = floor(next()·(i+1)); swap(i, j)` | n−1 |
| `sub(label)` | новый поток `makeRng(hash(base + ":" + label))`, где `base` — десятичная запись uint32 | 0 |

Потоки прогона:

- `root = makeRng(settings.seed)`;
- `L_0 = root.sub("layout")`, `L_k = root.sub("layout:" + k)` — попытки раскладки (§4.3);
- `F = root.sub("fill")` — дозаполнение листьями (§4.7);
- `C(i) = root.sub("content:" + inst.id)` — наполнение экземпляра `inst.id` (например `content:i7`);
- `F(i) = root.sub("finish:" + inst.id)` — отделка экземпляра (стены, пол; §5.6).

Потоки независимы: изменение наполнения одной комнаты не сдвигает раскладку и соседей.
Наполнение разыгрывается только для выбранной попытки раскладки.

## 2. Геометрия экземпляра

Экземпляр = копия комнаты с поворотом `rot ∈ {0, 90, 180, 270}` вокруг начала координат комнаты
`(0, 0)` и последующим сдвигом `(dx, dy)`.

**Клетка** (как квадрат):

| rot | (x, y) → |
|---|---|
| 0 | (x, y) |
| 90 | (−y−1, x) |
| 180 | (−x−1, −y−1) |
| 270 | (y, −x−1) |

затем `+ (dx, dy)`.

**Точка** (декор, споты — дробные координаты):

| rot | (x, y) → |
|---|---|
| 0 | (x, y) |
| 90 | (−y, x) |
| 180 | (−x, −y) |
| 270 | (y, −x) |

затем `+ (dx, dy)`; поворот объекта: `rot_мир = (rot_лок + inst.rot) mod 360`.

**Сторона**: поворот на `rot/90` шагов по кругу `N → E → S → W → N`.

**Отрезок** (дверь/метка: `cx, cy, side, len`; клетки `(cx+i, cy)` для N/S, `(cx, cy+i)` для E/W):
поворачиваются первая и последняя клетки как клетки, сторона — как сторона; новая стартовая клетка —
**покомпонентный минимум** двух повёрнутых клеток; `len` не меняется. Затем сдвиг.

Вспомогательные величины мирового отрезка:

- **линия** (координата по нормали): `N → cy`, `S → cy+1`, `W → cx`, `E → cx+1`;
- **начало** (вдоль стены): `N/S → cx`, `E/W → cy`;
- **знак нормали** `σ(side)`: `N, W → −1`, `S, E → +1`.

## 3. Совместимость меток

Теги сравниваются функцией `tagsCompatible(a, b)` (`src/model/segments.ts`):

- направленный тег `"a>b"` стыкуется **только** с `"b>a"` (прихожая `"hall>kitchen"` ↔ кухня
  `"kitchen>hall"`; две прихожие через кухонные проёмы не соединятся);
- простой тег (без `>`) — только с точно таким же (`"stair"` ↔ `"stair"`), но не с направленным.

Режим `settings.match`:

| режим | условие |
|---|---|
| `exact` | `lenA = lenB` **и** `tagsCompatible(tagA, tagB)` |
| `tag` | `tagsCompatible(tagA, tagB)`, длины могут отличаться |
| `len` | `lenA = lenB`, теги не важны |

Метки с `len < 1` генератором игнорируются полностью.

## 4. Раскладка (попытки на потоках `L_k`)

### 4.0. Нормализация настроек

`count = max(1, floor(count))`, `gap = clamp(floor(gap), 0, 64)`, `match` ∉ {tag, len} → `exact`,
`sightM = max(0, sightM)` (§7), `fill = (fill === true)` (§4.7).

### 4.1. Пул

Для каждой комнаты **в порядке `project.rooms`** (этот порядок — «порядок пула»):

- комнаты без клеток пропускаются;
- `effMax = unique ? 1 : max(0, floor(gen.max))`;
- `effMin = min(max(0, floor(gen.min)), effMax)`;
- `weight = max(0, gen.weight)`;
- комната в пуле, если `(weight > 0 или effMin > 0) и effMax > 0`;
- при `sightM > 0` из пула исключаются комнаты, внутри которых обзор длиннее предела (§7.3).

### 4.2. Ростовые метки и потенциал (без ГСЧ, один раз на прогон)

Считаются для меток всех непустых комнат (`len ≥ 1`); «цели» стыковки — только комнаты пула.
`compat(c)` — список пар (S, b): комната пула S и её метка b (`len ≥ 1`), совместимая с c (§3).

**Ростовая метка** `grow(c)` — наибольшая неподвижная точка:

```
grow(c) = true для всех c
повторять, пока что-то меняется:
  для каждой c с grow(c) = true:
    если НЕТ (S, b) ∈ compat(c), у которой есть другая метка b2 ≠ b с grow(S, b2) = true
      → grow(c) = false
```

Смысл: через ростовую метку можно пристыковать комнату, у которой останется ещё ростовая метка, — то
есть мир может расти через неё неограниченно (без учёта max и геометрии). Метки, ведущие только к
«листьям» (кухня, санузел, квартира целиком: `hall>kitchen`, `landing>apt`), — не ростовые; лестницы и
коридоры (`stair`, `corridor`) — ростовые. Результат не зависит от порядка обхода. Обратные метки
листьев (`kitchen>hall`) формально ростовые (ведут назад в прихожую → к площадке), но открытыми не
бывают: лист ставится именно через них.

**Потенциал** `pot(c)` — оптимистичная оценка числа комнат, которые можно поставить через метку:

```
pot_0(c) = 0
pot_k(c) = min(1000, max по (S, b) ∈ compat(c) из [1 + Σ_{b2 ≠ b, len ≥ 1} pot_{k−1}(S, b2)])   (0, если compat пуст)
pot = pot_6     // 6 итераций, все метки обновляются одновременно
```

Используется только для не ростовых меток — как запас «листового» фронта.

Константы: `RESERVE = 2`, `RESERVE_STEP = 15`, `RESERVE_MAX = 10`, `SUPPLY_FACTOR = 0.5`, `GROW_BONUS = 1`,
`LEAF_BONUS = 1`, `FRONT_DEPTH_M = 2`, `FRONT_SIDE_M = 0.5`, `ATTEMPTS = 6`.

### 4.3. Попытки

Попытка `k = 0 … ATTEMPTS−1` идёт на своём потоке: `L_0 = root.sub("layout")`,
`L_k = root.sub("layout:" + k)` при `k ≥ 1`. Каждая попытка — независимая раскладка с нуля
(§4.4–4.6). Берётся первая попытка, где `instances = count` (дальше не считаем); если такой нет —
попытка с наибольшим числом экземпляров (при равенстве — более ранняя). Если взята попытка `k > 0`,
в warnings пишется «Раскладка: взята попытка k+1 из 6 …». Если старт выбрать не из чего, попытки
прекращаются сразу.

### 4.4. Старт (в каждой попытке)

1. Если `startRoomId` задан и комната существует и не пуста — она (без ГСЧ).
2. Иначе список непустых комнат с тегом `"start"` (в порядке проекта, независимо от пула):
   `i = L.weightedIndex(веса)`, при `−1` → `i = 0`.
3. Иначе тем же способом по пулу.
4. Если выбрать нечего — прогон пуст (с предупреждением).

Старт ставится с `rot = 0, dx = dy = 0`, `id = "i0"`, `depth = 0`, `parent = null`, и засчитывается в
счётчик своей комнаты (для max/min).

Экземпляры получают `id = "i" + n` и `order = n` в порядке постановки.

### 4.5. Рост

Список открытых меток `open` — пары (экземпляр, индекс метки в `room.connectors`). После постановки
экземпляра в конец `open` добавляются его метки с `len ≥ 1` в порядке `room.connectors`
(кроме той, которой он пристыкован). Ростовость записи = `grow` этой метки её комнаты (§4.2).

Пока `instances < count` и `open` не пуст:

1. **Резерв роста (адаптивный).** `g` — число ростовых записей в `open`;
   `K = clamp(RESERVE + floor((count − instances) / RESERVE_STEP), RESERVE, RESERVE_MAX)` — чем больше
   ещё ставить, тем больше ростовых меток держим открытыми; `few = (0 < g ≤ K)`;
   `supply = Σ pot` по **не ростовым** записям `open`;
   `reserve = few и supply · SUPPLY_FACTOR < count − instances` — ростовых меток осталось мало, и
   листовой фронт уже не доберёт count.
2. **Выбор метки.** Ключ записи: `key = depth(владельца) − (ростовая ? GROW_BONUS : 0) −
   (fill и листовая метка ? LEAF_BONUS : 0)` (листовая метка — §4.7) —
   BFS-подобный рост (карта компактна), но лестницы/коридоры обрабатываются чуть раньше, пока
   квартиры не обступили их.
   - Обычно: `cand` — индексы записей с минимальным ключом, в порядке списка;
     `A = open[cand[L.int(0, |cand|−1)]]`.
   - При `reserve` — **рост наружу**, без ГСЧ: из ростовых записей берётся та, у которой середина
     метки (`segmentMid`, мировая) дальше всего от центра масс поставленного
     `C = Σ(центр bbox экземпляра · число его клеток) / Σ(число клеток)` (квадрат расстояния;
     при равенстве — первая по списку). Карта не обступает сама себя: достраиваются окраины.

   Выбранная запись удаляется из `open` (остальные сохраняют порядок).
3. **Кандидаты-комнаты** (в порядке пула). Комната пропускается, если `count(room) ≥ effMax` или у неё
   нет ни одной метки (`len ≥ 1`), совместимой с `A`. Остальные делятся на две группы:
   - `G1` — ещё не набрали min: `count(room) < effMin`;
   - `G2` — остальные с `weight > 0`.
4. **Проходы.** Если `few` и `A` ростовая — два прохода: сначала **ростовой**, затем обычный; иначе
   один обычный. В каждом проходе группы перебираются по очереди (`G1`, затем `G2`).
   - В ростовом проходе допустимы только метки `B` комнаты, для которых у комнаты есть другая
     ростовая метка `b2 ≠ B`; комнаты группы без таких меток исключаются (фильтр в порядке группы,
     без ГСЧ). В обычном проходе допустимы все совместимые метки (`len ≥ 1`).
   - Внутри группы — **ленивый взвешенный перебор без возвращения**: `k = L.weightedIndex(веса
     оставшихся)` (при `−1` → `k = 0` без обращения к ГСЧ), комната извлекается из списка и пробуется;
     если не подошла — следующий бросок среди оставшихся.
   - Обычный проход после ростового начинается заново с полных `G1`, `G2`.
5. **Проба комнаты R.** `B_idx` — индексы допустимых меток R в порядке `room.connectors`;
   `L.shuffle(B_idx)`. Для каждой метки `B` по порядку:
   - поворот, при котором мировая сторона `B` = `OPPOSITE(A.side)` (единственный):
     `rot = 90 · ((idx(OPPOSITE(A.side)) − idx(B.side)) mod 4)`, где `idx`: N=0, E=1, S=2, W=3;
   - `B'` = `B`, повёрнутая на `rot` при `dx = dy = 0` (правило отрезка из §2);
   - **цель стыковки** (мировая стартовая клетка `B`):
     ```
     side  = OPPOSITE(A.side)
     line  = линия(A) + gap · σ(A.side)
     start = начало(A) + floor((lenA − lenB) / 2)   // при равной длине — совмещение начал
     N: (cx, cy) = (start, line)       S: (start, line − 1)
     W: (cx, cy) = (line, start)       E: (line − 1, start)
     ```
     `dx = cx − B'.cx`, `dy = cy − B'.cy`;
   - **коллизия**: кандидат отвергается, если существует клетка `q` кандидата и клетка `p` любого уже
     поставленного экземпляра с `max(|qx−px|, |qy−py|) ≤ gap` (то есть между комнатами минимум `gap`
     клеток стены; при `gap = 0` — просто без наложения). Дополнительно: bbox кандидата, расширенный на
     `gap`, обязан лежать в `[−16000, 16000]` по обеим осям (ограничение упаковки ключей; на практике
     не достигается);
   - **свободный фасад** (только в ростовом проходе): у кандидата должна быть другая ростовая метка
     `b2 ≠ B` (мировая, со сдвигом `dx, dy`), перед которой свободна полоса: по нормали — клетки на
     расстоянии от `gap + 1` до `D = max(gap + 1, round(FRONT_DEPTH_M / cellM))` наружу, вдоль — клетки
     метки плюс `S = round(FRONT_SIDE_M / cellM)` клеток с каждой стороны; каждая клетка полосы на
     расстоянии Чебышёва > `gap` от всех клеток уже поставленных экземпляров (кандидат не учитывается).
     Иначе кандидат отвергается. Это не даёт, например, межэтажной площадке сесть вплотную на
     площадку и закрыть собой обе лестницы;
   - **предел обзора** (только при `sightM > 0`): кандидат отвергается, если через проём новой связи
     проходит линия длиннее предела (§7.3);
   - первый не отвергнутый кандидат ставится: `parent = A.inst`, `depth = parent.depth + 1`,
     записывается `Link { a: A, b: B }`, метки нового экземпляра (кроме `B`) добавляются в `open`;
     перебор для метки `A` заканчивается.
6. Если ни одна комната не подошла — `A` остаётся **тупиком** (без обращений к ГСЧ сверх уже
   сделанных).

Реализационные подсказки (на результат не влияют): индекс занятости — множество клеток всех
поставленных экземпляров плюс клетки в пределах `gap` от их *граничных* клеток (клетка с 4-соседом вне
комнаты) — этого достаточно (им же проверяется свободный фасад); проверка кандидата — сначала
пересечение bbox, расширенных на `gap`, затем поклеточно только внутри объединения задетых bbox.

### 4.6. Замыкание петель (в каждой попытке)

После роста: `free` — все несвязанные метки (`len ≥ 1`) в порядке (экземпляр по `order`, метка по
индексу). Для `i` по возрастанию (пропуская уже связанные) ищется первое `j > i` другого экземпляра,
несвязанное, такое что метки совместимы (§3) и стоят **лицом к лицу**:

```
B.side = OPPOSITE(A.side)
линия(B) = линия(A) + gap · σ(A.side)
начало(B) = начало(A) + floor((lenA − lenB)/2)   ИЛИ   начало(A) = начало(B) + floor((lenB − lenA)/2)
```

(второе условие — та же формула с точки зрения B: при нечётной разнице длин округление вниз
несимметрично). При `sightM > 0` пара пропускается, если её проём открывает линию длиннее предела
(§7.3). Найденная пара связывается `Link { a: A, b: B }`. ГСЧ не используется.

`openConnectors` — все оставшиеся несвязанные метки (`len ≥ 1`) выбранной попытки в том же порядке.

### 4.7. Дозаполнение листьями (`settings.fill = true`)

Выполняется **после** выбора попытки (§4.3) и её замыкания петель, на отдельном потоке
`F = root.sub("fill")`. При `fill = false` шаг пропускается целиком — раскладка бит в бит прежняя.
При `fill = true` меняется и основной рост: листовые метки получают бонус приоритета `LEAF_BONUS`
(§4.5, шаг 2) — квартира достраивается, пока рядом есть место, до того как соседи займут его.

**Листовая комната** (считается вместе с ростовыми метками, §4.2; видно в `analyzeGrowth(p).leaf`).
Хаб — комната, у которой ≥ 2 ростовых меток. Комната (в пуле) листовая, если:

- у неё ровно одна метка (`len ≥ 1`), **или**
- у неё есть «тихая» метка b — пристыкованная ею комната не получает ростовых меток (нет `b2 ≠ b`
  с `grow = true`), **и** ни одна её метка не совместима (§3) ни с одной меткой хаба (т.е. это не
  «вход» в хаб, как прихожая `apt>landing` для площадки `landing>apt`).

При дозаполнении лист пристыковывается только тихими метками (для комнаты с одной меткой — ею).
**Листовая метка** — метка, к которой совместима тихая метка какой-либо листовой комнаты пула.

Итог на пресетах: кухни, санузлы, жилые (в т.ч. зал со спальней и балконом), балконы, кладовки,
служебные — листья; прихожие, площадки, марши,
коридоры — нет.

**Порядок.** Очередь — все несвязанные метки (`len ≥ 1`) в порядке (экземпляр по `order`, метка по
индексу). Обрабатываем по очереди; поставленный экземпляр дописывает свои несвязанные метки в конец
очереди (так зал, поставленный на тупик прихожей, получит спальню и балкон). Для метки `A` (если она
ещё не связана):

1. Кандидаты — только листовые комнаты пула: `count < effMax`, есть совместимая с `A` тихая метка;
   `G1` — `count < effMin`, `G2` — остальные с `weight > 0` (как в §4.5).
2. Ленивый взвешенный перебор по `G1`, затем `G2` на потоке `F`; совместимые тихие метки комнаты
   (в порядке `room.connectors`) — `F.shuffle`;
   поворот, цель стыковки, коллизия и предел обзора — как в §4.5 (без ростового прохода и фасада).
3. Первый подошедший кандидат ставится обычным экземпляром (`id = "i" + n`, `parent = A.inst`,
   `depth = parent.depth + 1`), записывается `Link`, проём учитывается в W.
4. Ничего не подошло — метка остаётся тупиком.

После очереди — ещё одно замыкание петель (§4.6) по всем несвязанным меткам. `count` может быть
превышен. В warnings — строка «Дозаполнение: +N комнат (итого M).». Наполнение (§5) разыгрывается
для всех экземпляров, включая добавленные.

### 4.8. Предупреждения и диагностика остановки

Человекочитаемые строки по-русски: не набран min комнаты, взята не первая попытка, сколько добавлено
дозаполнением, исключённые пределом обзора комнаты, min > max, пустая комната с min > 0, не найдена
стартовая комната или проходка. Движку повторять не нужно.

**Почему рост остановился** (только если count не набран — тогда в Run есть поле `stop`). Для каждой
метки, оставшейся тупиком, запоминается причина последней неудачи (основной рост; при дозаполнении —
только если причины ещё нет):

| причина | условие | поле `stop` |
|---|---|---|
| нет совместимых комнат | в пуле нет ни одной комнаты с совместимой меткой (не считая упёршихся в max) | `noMatch`, теги — `noMatchTags` |
| упёрлись в max | совместимые комнаты есть, но все набрали max (они — в `maxRooms`) | `atMax` |
| нет места | кандидаты были, все отвергнуты коллизией / фасадом | `noSpace` |
| предел обзора | хотя бы один кандидат прошёл коллизию, но нарушил предел обзора | `sight` |

`stop = { open, noMatch, atMax, noSpace, sight, maxRooms: id[], noMatchTags: string[] }`. В warnings —
строка «Поставлено N из count комнат: рост остановился, открытых меток M (нет места — …, …)» и советы:
«поднимите max у: …» (если есть `maxRooms`), «увеличьте предел обзора» (если `sight ≥ open/4`),
«мало места — добавьте хабы, ведущие наружу, или уменьшите count» (если `noSpace ≥ open/2`),
«для меток … нет совместимых комнат» (если есть `noMatchTags`).

Локального отката (снятия последних экземпляров) нет: на пресетах адаптивного резерва, роста наружу
и перезапусков (§4.3) хватает — count 150 набирается при пределе обзора 0/8/9 м на 10 из 10 сидов.
Снимок-тест раскладки (`sight.test.ts`) обновлён вместе с этим алгоритмом.

## 5. Наполнение (поток `C(inst)` на каждый экземпляр, в порядке `order`)

Порядок шагов и обращений к ГСЧ фиксирован.

Проходка: `pass = economy.passes[id = settings.passId]` или нет. Множитель предмета
`boost(item) = pass.itemBoost[item]`, если это число ≥ 0, иначе 1 (без проходки — 1).

### 5.1. Элитность «при заходе»

Если `room.elite` не пуст:
`wᵢ = max(0, eliteᵢ.weight) · (pass и tier.level ≥ 2 ? pass.tierBoost : 1)`; для ссылки на
несуществующий тир `wᵢ = 0`. `i = C.weightedIndex(w)`; `−1` → тира нет.

Иначе тира нет. `danger = tier ? tier.danger : 0`.
`dangerAcc = dangerAcc(parent) + danger` (у старта — просто `danger`), то есть накопленная опасность
по пути роста от старта, включая эту комнату. Порог `economy.dangerLimit` — «уровень горит».

### 5.2. Группы спотов

Для групп **в порядке `room.spotGroups`**:

- группа без вариантов пропускается (без броска);
- `v = C.weightedIndex(веса вариантов)`; `−1` (все веса 0) — группа пропускается;
- **один бросок на группу**: P(вариант) = wᵥ / Σw;
- **проходимость** (§8): если выпавший вариант вместе с фиксированным декором и вариантами предыдущих
  групп этой комнаты перегораживает проход между проёмами — он подменяется **без бросков ГСЧ** (поток `C`
  не сдвигается), запись группы получает `fallback: true`;
- для спотов комнаты **в порядке `room.spots`** с `groupId` этой группы создаётся `SpawnedSpot`:
  мировая позиция спота (§2), `content = variant.assign[spotId]` или `null` (нет ключа — спот пуст),
  `rot = (spot.rot + inst.rot + (content ? content.rot : 0)) mod 360`.

Споты без группы в генерации не участвуют.

### 5.3. Лут комнаты

Для строк **в порядке `room.loot`**: `p = min(1, chance · boost(itemId))`; `C.chance(p)`;
при успехе `count = C.int(floor(min), floor(max))`; запись `{itemId, count, from: "room", rowId}`
добавляется, если `count > 0`.

### 5.4. Лут тира

Только если тир выпал. Для строк **в порядке `tier.loot`**:

1. **Место.** Если `where` не пуст: `places` = id фиксированного декора комнаты (в порядке
   `room.decor`), у prop которого в `tags` есть `where`, затем `"spot:" + spotId` для выпавших на
   шаге 5.2 спотов (в их порядке) с `content.kind = "prop"` и таким тегом у prop. Пусто — строка
   **не разыгрывается** (без бросков).
2. **Предмет.** `source.kind = "item"` → `itemId = source.id`. `source.kind = "shop"` → магазин
   существует и имеет товары (иначе строка пропускается без бросков), `offer = C.pick(offers)`,
   `itemId = offer.itemId`, `shopId = shop.id`.
3. **Ступени.** Отбросить ступени с `floor(upTo) < 1`, `upTo = floor(upTo)`, устойчиво отсортировать
   по `upTo` **по убыванию**. По очереди: `C.chance(min(1, chance · boost(itemId)))`; первая
   сработавшая → `count = C.int(1, upTo)`, дальше не проверять. Ни одна не сработала — ничего.
4. При `count > 0`: если `where` задан — `decorId = C.pick(places)`. Запись
   `{itemId, count, from: "tier", rowId, decorId?, shopId?}`.

Вероятность «хоть что-то» и матожидание (то, что показывает редактор — `stepsStats`):

```
miss = 1, mean = 0
для ступеней по убыванию upTo:  mean += miss · pᵢ · (1 + upToᵢ)/2;  miss *= (1 − pᵢ)
pAny = 1 − miss
```

Текст для игрока (`stepsText`): «до 30 — 70%, иначе до 25 — 50%»; ступени после гарантированной (100%)
не показываются; одна ступень «до 1» — просто «5%».

### 5.5. Итоги

`totals[itemId]` = Σ `count` по всему луту прогона + по 1 за каждый спот с `content.kind = "item"`.
`Run.ms` — время генерации в миллисекундах (не детерминировано, в сравнении прогонов не участвует).

### 5.6. Отделка (поток `F(inst)`)

Обои, кафель, покраска, побелка на стенах и линолеум/паркет/плитка на полу. Разыгрывается на
**своём** потоке `F(i) = root.sub("finish:" + inst.id)`, поэтому правила отделки не сдвигают ни
раскладку, ни остальное наполнение (`C(i)`).

Данные проекта: `project.finishes` — таблица отделок (`surface: "wall" | "floor"`), `project.finishRules` —
правила по тегу комнаты: `{ tag, wall: [{finishId, weight}], floor: [{finishId, weight}] }`; у комнаты
`room.finish = { wall, floor }` — явное назначение (id) или `null` («по правилу»).

**Правило комнаты** — первое правило по порядку **тегов комнаты**: `room.tags[0]`, если для него есть
правило, иначе `room.tags[1]` и т.д. (порядок самих правил не важен). Нет ни одного — правила нет.

Поверхности разыгрываются по очереди: **сначала `wall`, потом `floor`**, на одном потоке `F`:

1. Явное назначение `room.finish[s]` — если отделка с таким id существует и её `surface = s` — берётся
   она, **без броска**.
2. Иначе строки `rule[s]` (в их порядке) с весами `wᵢ = max(0, weight)`; строка на несуществующую
   отделку или отделку другой поверхности весит 0. `i = F.weightedIndex(w)`; `−1` (Σw ≤ 0 или правила
   нет — пустой список) → `null` **без броска**; иначе `finishId = rule[s][i].finishId`.

Результат — `content.finish = { wall: id | null, floor: id | null }`. P(отделка) = w / Σw по строкам
правила; одинаковые отделки в нескольких строках складываются (`finishChances` в редакторе).

**Нижняя панель (dado).** У стеновой отделки может быть `dado = { finishId, heightM }`: от пола до высоты
`heightM` стена облицована отделкой `finishId` (тоже стеновой), выше — самой отделкой. Пример пресетов:
«Подъезд: зелёная панель 1.5 м + побелка» — текстура побелки, `dado` → «Краска масляная зелёная», 1.5 м;
«Санузел: кафель 1.5 м + краска»; «Кухня: масляная краска 1.2 м + побелка». Панель у панели не
разворачивается (движок берёт только первый уровень).

**Наложение текстуры.** `tex` — бесшовная плитка (JPEG data:URI); `tileW × tileH` — её реальный размер на
поверхности, м (рулон обоев 0.53, кафель 15×15 см → в плитке 4×4 = 0.6, «Дамаск» — 0.62 × 0.6). На стене
U идёт вдоль стены (метры от начала грани / tileW), V — вверх от пола (метры / tileH); на полу U, V — мировые
x, y плана в метрах / tileW, tileH. Без текстуры — заливка `color` (средний цвет текстуры). Готовая
облицовка стен по комнатам и материалы — в болванке (`docs/BLOCKOUT.md`, `docs/BLOCKOUT-BABYLON.md`).

## 7. Предел дальности обзора (`settings.sightM`)

Цель — не давать генератору собирать длинные прямые «простреливаемые» коридоры: чем меньше предел,
тем больше завихрений. `sightM` — метры, `0` — без ограничения (раскладка при этом бит в бит та же,
что и без этой функции). `Run.sight` считается **всегда**.

### 7.1. Проходимое пространство W

- все клетки всех экземпляров (владелец — экземпляр);
- **проём** каждой связи `Link(A, B)` (включая замкнутые петли): клетки зазора между линиями меток
  A и B на пересечении их длин. Вдоль стены: `t ∈ [max(начало A, начало B), min(начало A + lenA,
  начало B + lenB))`; по нормали: `gap` клеток — при `σ(A.side) = +1` от `линия(A)` до
  `линия(A) + gap − 1`, при `σ = −1` от `линия(A) − gap` до `линия(A) − 1`. Владелец — «проём»;
- при `gap = 0` клеток проёма нет; вместо этого проходимы рёбра между клеткой A и клеткой B на том же
  пересечении (у соседних комнат без связи общая граница — стена).

Несвязанные метки и двери — стена.

### 7.2. Линия обзора

Направления: `(1,0)`, `(0,1)`, `(1,1)`, `(1,−1)`. Шаг между соседними по стороне клетками p → q
разрешён, если обе в W и (владелец один | одна из них — проём | ребро p–q — ребро связи при gap = 0).
**Диагональный** шаг p → p + (dx, dy) разрешён, только если разрешены все четыре ортогональных шага
через обе угловые клетки `(px+dx, py)` и `(px, py+dy)` — сквозь угол смотреть нельзя.

Линия — максимальная цепочка из `n` клеток с разрешёнными шагами. Длина:
`n · cellM` по прямой, `n · cellM · √2` по диагонали (одна клетка — тоже линия: `cellM` или
`cellM·√2`). Отрезок в `Run.sight.line` — **от края до края**: для горизонтали
`[x0, y0 + 0.5, x0 + n, y0 + 0.5]`, вертикали `[x0 + 0.5, y0, x0 + 0.5, y0 + n]`, диагонали (1,1)
`[x0, y0, x0 + n, y0 + n]`, диагонали (1,−1) `[x0, y0 + 1, x0 + n, y0 + 1 − n]`, где (x0, y0) — первая
клетка линии. Длина отрезка равна длине линии.

`Run.sight = { maxM, line }` — максимум по всему прогону (`maxM` округлён до 0.001 м). Полный скан —
динамика `len(c) = шаг(c − d → c) ? len(c − d) + 1 : 1`; клетки обходятся по возрастанию (y, x), для
направления (1, −1) — по убыванию; направления — в указанном порядке; побеждает строго большая длина
(при равных — найденная раньше). В экспорте прогона — поле `sight` того же вида.

### 7.3. Ограничение при `sightM > 0`

Пределы в клетках: `Nорт = floor(sightM / cellM + 1e−9)`, `Nдиаг = floor(sightM / (cellM·√2) + 1e−9)`.
Линия допустима, если `n ≤ N` своего направления.

1. **Пул.** Комнаты, у которых собственная (внутренняя) линия обзора длиннее `sightM`, исключаются
   из пула до расчёта ростовых меток и потенциала (§4.2), warning со списком имён. Если такая комната —
   стартовая, она всё равно ставится (warning).
2. **Кандидат** (§4.5, после коллизии и свободного фасада): строится проём будущей связи; кандидат
   отвергается, если какая-либо линия, проходящая **через клетку проёма** (при gap = 0 — через клетку A
   у проёма), в пространстве `W ∪ клетки кандидата ∪ проём` длиннее предела. Этого достаточно: при
   `gap ≥ 1` клетки кандидата отделены от всего поставленного стеной и соединены с W только через
   новый проём, а его собственные линии не длиннее предела (п. 1). Проверка: от каждой клетки проёма по
   каждому направлению идём назад и вперёд, пока шаги разрешены, и останавливаемся, как только длина
   превысила предел.
3. **Петли** (§4.6): пара лицом к лицу не связывается, если её проём даёт линию длиннее предела
   (та же проверка без кандидата); тогда обе метки остаются в `openConnectors`.

ГСЧ в проверках обзора не используется; отвергнутый кандидат — как при коллизии: перебор идёт дальше.

## 8. Проходимость (игрок-капсула)

По карте ходит игрок — капсула радиусом **R = 0.3 м** (Babylon `ellipsoid` 0.3 / 0.85 / 0.3), поэтому мебель и
то, что выпало на спотах, не должны отрезать один проём комнаты от другого. Реализация — `src/gen/walk.ts`
(`walkCheck`), правило одно для редактора, генератора и тестов пресетов.

**Правило.** Комната проходима, если центр капсулы может дойти от любого её проёма до любого другого.
Проём — каждая дверь и метка стыковки (совпадающие по геометрии — один проём); связанность меток в прогоне
не важна, проверяется комната целиком. Проход нужен шириной **≥ 2R = 0.6 м**.

**Препятствия.**

- стены — всё, что не пол комнаты; перед каждым проёмом пол продлевается наружу на R («створ»), так что
  центр капсулы может встать прямо на линии проёма, если проём не уже 0.6 м и изнутри к нему не придвинута
  мебель ближе 0.3 м;
- prop фиксированного декора и prop на спотах — прямоугольник `w × h` с центром в точке и поворотом
  (декор — `rot`, спот — `spot.rot + content.rot`), любой угол;
- **не препятствия**: «плоские» prop — теги/имя «ковёр», «коврик», «половик», «дорожка» или высота болванки
  `propHeightM` < 0.1 м (`src/blockout/core.ts`); предметы (`kind: "item"`); лут без позиции.

**Дискретизация.** Центр капсулы ставится в углы клеток `(X, Y)` и центры клеток `(X + ½, Y + ½)`; точка
свободна, если ни одна стеновая клетка и ни один прямоугольник prop не ближе R (касание ровно на R — свободно).
Шаги: угол ↔ соседний угол по осям, угол ↔ центр любой из четырёх смежных клеток. Проём «стоит», если свободен
хоть один угол на его линии; комната проходима, если все проёмы стоят и лежат в одной компоненте связности.
Для щелей вдоль осей правило точное (0.60 м проходима, 0.59 м — нет), для диагональных — с запасом ≤ 0.07 м.
Отрезанные проёмы — все, кроме проёмов основной компоненты (той, которой касается больше всего проёмов;
при равенстве — найденной раньше, обход проёмов: метки в порядке `room.connectors`, затем двери).

**Розыгрыш спотов (§5.2).** Для группы после броска `v`:

1. Если у `v` нет напольных prop (только предметы, плоские prop, пусто) — берётся `v`.
2. Если проход перекрыт уже фиксированным декором — проверок нет, берётся `v` (это ошибка комнаты, её
   показывает редактор; на пресетах тест `presets.test.ts` такого не допускает).
3. Иначе проверка: декор + напольные prop выбранных вариантов предыдущих групп этой комнаты + prop `v`.
   Проходимо — берётся `v`.
4. Не проходимо — перебор остальных вариантов группы с весом > 0 **по убыванию веса** (при равных — по
   порядку в группе): первый проходимый (вариант без напольных prop проходим всегда). Без бросков ГСЧ.
5. Не нашлось — «крайний случай»: `v` без напольных prop (предметы и плоские prop остаются),
   `variantId = v.id`.

В шагах 4–5 запись группы — `{ groupId, variantId, fallback: true }`, в `Run.warnings` — строка
«Проходимость: подменено вариантов спотов — N из M…» (только если подмены были). Без подмен прогон бит в бит
совпадает с прогоном без проверки проходимости. Порядок групп и обращений к ГСЧ не меняется.

**Редактор.** Слой «Проходимость» (список слоёв): красноватая заливка — центр капсулы здесь встать не может,
оранжевая — может, но отрезан от проёмов; у проёмов — зелёные (достижим) и красные (отрезан) маркеры. В HUD —
«двери «A» и «B» разделены мебелью» (видно и при выключенном слое) и варианты спотов, которые в генерации будут
подменены. Пересчёт — на каждом перетаскивании декора (кэш: решётка пола — по клеткам комнаты, решётка с
декором — по расстановке; комната 4000 клеток с нуля ≈ 1 мс, с декором из кэша ≈ 0.1 мс).
