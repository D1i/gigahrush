# Складчатый (4D) генератор Room Forge

Документ для геймдизайнера и программиста движка (Babylon). Второй генератор раскладки: у комнат нет
общей 3D-физики, квартиры могут занимать одно и то же место в пространстве, а разводит их четвёртая
координата **W** («слой»), которую сдвигают пороги.

Реализация-эталон: `src/gen4d/fold.ts` (`generateFoldRun`, `visibleSet`, `overlapPairs`,
`validateFoldRun`), складчатая стыковка, петли и PVS — `src/gen4d/foldcore.ts` (общие с бесконечным миром),
геометрия — `src/gen4d/space.ts`, лучи обзора по порталам — `src/gen4d/sight4d.ts`,
потенциально видимые наборы — `src/gen4d/pvs.ts`, **бесконечный мир** (генерация на ходу, сохранение) —
`src/gen4d/stream.ts`, §15. Всё, что не описано здесь (ГСЧ, геометрия
экземпляра, совместимость меток, пул, ростовые метки, наполнение), — **ровно как у евклидова
генератора**, см. [`docs/GENERATOR.md`](GENERATOR.md); ссылки вида «§4.5 G» ведут туда.

---

## 1. Идея

> Квартиры могут быть в одной точке, проходить через одни места в 3-мерном пространстве. Пороги
> определяют смещение по 4-мерному пространству, благодаря которому это и возможно. Игроки могут
> находиться в одной и той же точке для 3D пространства, но в разных для 4D. Игрок видит только 3D.

- Каждая комната (экземпляр) стоит в 3D как обычно (`rot`, `dx`, `dy`) и дополнительно имеет целую
  координату `w` — номер слоя.
- Каждая связь (порог, дверной проём между двумя метками) имеет сдвиг `dw = w(b) − w(a)`. Обычный
  порог — `dw = 0`; «складка» — `dw ≠ 0`.
- В 3D двери связанных комнат **всегда** совпадают (стоят лицом к лицу через стену толщиной `gap`, как в
  евклидовом генераторе). Игрок проходит дверь и не замечает ничего, кроме того, что за спиной теперь
  другой мир: соседняя по 3D квартира, которую он видел бы через стену, в его новом слое отсутствует —
  её место может занимать совсем другая комната.
- Слой — это обычный план: внутри одного `w` комнаты не пересекаются. Пересекаться в 3D могут только
  комнаты из **разных** слоёв и **далёкие** по графу дверей.

Что получает игрок: бесконечный подъезд, где из коридора можно зайти в три квартиры, занимающие одно и
то же место; лестница, ведущая «вниз», приводит на площадку, стоящую там же, где осталась предыдущая;
тупиковая в обычном мире дверь открывается — за ней комната из другого слоя.

## 2. Гарантии генератора

Термин: две комнаты **пересекаются**, если есть клетка одной и клетка другой на расстоянии Чебышёва
`max(|Δx|, |Δy|) ≤ gap` — то есть стена одной налезла бы на пол другой (при `gap = 0` — просто общие
клетки). Это тот же критерий, что у коллизии евклидова генератора (§4.5 G). Связанные двери стоят ровно
через `gap` клеток стены — связанные комнаты **не** пересекаются.

1. **Слой — плоский план.** В одном слое `w` никакие две комнаты не пересекаются. По слою можно считать
   физику и строить «болванку» (`docs/BLOCKOUT.md`) как для евклидова прогона.
2. **Локальная евклидовость.** Любые две комнаты на расстоянии ≤ `localRadius` по графу связей не
   пересекаются, в каких бы слоях они ни были. Расстояние — по **итоговому** графу (с петлями и
   дозаполнением).
3. **Пороги.** Связанные метки стоят лицом к лицу в 3D точно как в евклидовом генераторе (совместимые
   теги, `facing`, §4.6 G). `|dw| ≤ maxShift`; порог с меткой `'never'` — `dw = 0`; с меткой
   `'always'` — `dw ≠ 0`; все слои `|w| ≤ maxLayer`.
4. **Складки.** Комнаты дальше `localRadius` по графу **могут** пересекаться в 3D — но только из разных
   слоёв. Именно это даёт «квартиры в одной точке». Сколько таких пар — `Run.fold.overlaps`.

Следствие для рендера: **видимое множество** «комната + все комнаты в ≤ `d` дверях от неё» не содержит
пересекающихся пар, если `2·d ≤ localRadius` (любые две комнаты множества — в ≤ `2d` дверях друг от
друга через текущую). По умолчанию `localRadius = 2`, `d = 1`: «где стою + что за дверями».

Проверка всех гарантий независимой реализацией — `validateFoldRun(project, run)` (пустой массив — всё
верно); на пресетах она гоняется в `src/gen4d/fold.test.ts`.

## 3. Параметры

### 3.1. Настройки генератора

`GeneratorSettings.mode = 'fold'` включает складчатый генератор (`generateFoldRun`); `GeneratorSettings.fold`:

| поле | по умолчанию | нормализация | смысл |
|---|---|---|---|
| `shiftChance` | 0.2 | `[0, 1]` | вероятность сдвига на пороге `'auto'`, **даже когда место в слое есть** — «складки по желанию» |
| `maxShift` | 2 | целое `[0, 64]` | максимальный `|dw|` одного порога. 0 — плоский план (см. §9) |
| `localRadius` | 2 | целое `[1, 16]` | радиус локальной евклидовости по графу. 2 — безопасно для рендера «комната + соседи», 4 — «+ соседи соседей» |
| `maxLayer` | 12 | целое `[0, 1000]` | допустимые слои `|w| ≤ maxLayer` |
| `seamless` | true | `false` — выкл. | бесшовная видимость (§14): комнаты одного PVS не пересекаются в 3D; работает только при `sightM > 0` |

Нет поля / мусор — значение по умолчанию (`normFold`). Остальные настройки — как у евклидова: `seed`,
`count`, `gap`, `match`, `startRoomId`, `passId`, `fill` (дозаполнение листьями поддержано) и
`sightM` — предел дальности обзора, но линия обзора считается **по порталам** (§13): сквозь проёмы
связей, независимо от слоёв.

### 3.2. Метка порога `Connector.shift`

| метка | смысл |
|---|---|
| нет поля / `'auto'` | по настройкам: сдвиг с вероятностью `shiftChance`, а если в слое родителя нет места — сдвиг «по нужде» |
| `'always'` | этот проём всегда сдвигает W (например входные двери квартир `landing>apt`: за каждой — своё измерение) |
| `'never'` | обычный порог, `dw = 0` всегда (например лестничные марши — подъезд остаётся цельным) |

Режим порога — по паре меток (у родителя `A` и у ставимой комнаты `B`):

| A \ B | auto | always | never |
|---|---|---|---|
| **auto** | auto | always | never |
| **always** | always | always | ✗ |
| **never** | never | ✗ | never |

✗ — пара несовместима (такую стыковку генератор пропускает); `'always'` при `maxShift = 0` — тоже ✗.
Евклидов генератор поле `shift` игнорирует.

### 3.3. Рецепты для геймдизайнера

- «Каждая квартира — в своём измерении»: `shift: 'always'` на метках `landing>apt` площадок/коридоров.
  На пресетах при count 150 так получается ~11 слоёв, у каждого входа в квартиру `dw ≠ 0`.
- «Подъезд цельный, складываются только квартиры»: `'never'` на `stair` и `corridor`, `'always'` на
  `landing>apt`, `shiftChance = 0`.
- «Почти обычный дом, складки — только где не влезает»: `shiftChance = 0`. Сдвиг будет только у тех
  проёмов, за которыми в своём слое не поместилась ни одна подходящая комната (в евклидовом генераторе
  такой проём стал бы тупиком), а при нехватке ростовых меток — ни одна комната, дающая рост (§4.4).
- Хотите видеть через две двери (`depth 2`) — ставьте `localRadius = 4`. Складок меньше по месту
  (пересечений в ~3 раза меньше), но и «невозможных» соседств меньше.
- «Давящее пространство — дальше 6 м не видно никогда»: `sightM = 6` (§13). Складчатый генератор
  набирает такие карты заметно лучше евклидова.

## 4. Алгоритм (для повторения в движке бит в бит)

### 4.1. Потоки ГСЧ

ГСЧ и производные операции — §1 G. Потоки прогона:

- `root = makeRng(settings.seed)`;
- `L_0 = root.sub("fold-layout")`, `L_k = root.sub("fold-layout:" + k)` — попытки раскладки;
- `F = root.sub("fold-fill")` — дозаполнение листьями;
- `C(i) = root.sub("content:" + inst.id)`, `Fin(i) = root.sub("finish:" + inst.id)` — наполнение и
  отделка экземпляра, **как в евклидовом** (§5 G);
- `root.sub("fold-loops")` зарезервирован за петлями; сейчас замыкание петель ГСЧ не использует.

### 4.2. Подготовка (без ГСЧ)

1. Нормализация настроек — §4.0 G плюс `normFold` (§3.1).
2. Пул, `effMin/effMax/weight` — §4.1 G; при `sightM > 0` комнаты, внутри которых обзор длиннее
   предела, исключаются из пула (§7.3 G, п. 1 — та же внутренняя линия, без проёмов).
3. Ростовые метки `grow`, потенциал `pot`, листовые комнаты `leaf` и листовые метки — §4.2 и §4.7 G
   по этому пулу (в коде — `analyzeGrowth(p, { match, sightM })`).
4. Константы те же: `ATTEMPTS = 6`, `RESERVE = 2`, `RESERVE_STEP = 15`, `RESERVE_MAX = 10`,
   `SUPPLY_FACTOR = 0.5`, `GROW_BONUS = 1`, `LEAF_BONUS = 1`, `LIMIT = 16000`.

### 4.3. Попытки и старт

Как §4.3–4.4 G на потоках `L_k`. Стартовый экземпляр: `rot = 0, dx = dy = 0, w = 0`.

### 4.4. Рост

Список открытых меток, резерв роста, ключ и выбор метки `A`, группы `G1/G2`, ростовой и обычный проходы
— **дословно §4.5 G, шаги 1–4** (центр масс для «роста наружу» — по всем экземплярам всех слоёв).
Отличие — проба кандидатов (шаг 5 G заменяется на «складчатую стыковку» ниже); проверки свободного
фасада нет, предел обзора — по порталам (§13).

**Складчатая стыковка метки `A` родителя `P` (слой `wP`)** — для одного прохода с группами `G1, G2`
и допустимыми метками (`okB` прохода):

*Фаза 1 — свой слой (или разыгранный).* Для группы `G1`, затем `G2`: ленивый взвешенный перебор без
возвращения (`L.weightedIndex`, при −1 → 0 без броска), для комнаты `R` — индексы допустимых меток в
порядке `room.connectors`, `L.shuffle`. Для каждой метки `B` по порядку:

1. `mode = режим(A.shift, B.shift)` по таблице §3.2. ✗ → кандидат пропущен (без ГСЧ, причина «правила»).
2. Поворот, `B'`, цель стыковки, `dx, dy` — §4.5 G, шаг 5. Если bbox кандидата, расширенный на `gap`,
   выходит за `[−16000, 16000]` — пропуск.
3. **Локальная проверка (гарантия 2).** `near` — все экземпляры на расстоянии ≤ `localRadius − 1` по
   текущему графу связей от `P` (включая сам `P`; BFS считается один раз на метку `A`). Если кандидат
   пересекается (§2) хотя бы с одним из них — пропуск. Слой здесь не важен.
3а. **Предел обзора** (только при `sightM > 0`, §13.3): если через проём будущей связи проходит линия
   длиннее предела — пропуск (причина «обзор»). Слой на линии не влияет, поэтому отказ по обзору —
   повод пробовать следующего кандидата, а не другой `dw`. ГСЧ не используется.
3б. **Бесшовность** (только при `seamless` и `sightM > 0`, §14.4): PVS кандидата по пробной геометрии;
   кандидат не должен пересекаться ни с одной комнатой из PVS(A) для всех A ∈ PVS(кандидата), а сам его
   PVS — попарно без пересечений. Иначе пропуск (причина «бесшовность»); как и обзор, от слоя не зависит.
4. **Порядок сдвигов `order`** (здесь броски ГСЧ, `M = maxShift`):
   ```
   randNZ():  k = L.int(1, 2M);  return k ≤ M ? k : M − k        // +1…+M, затем −1…−M
   first =
     'never'  → 0                                                    (без броска)
     'always' → randNZ()                                             (1 бросок)
     'auto'   → если M > 0 и shiftChance > 0 и L.chance(shiftChance) → randNZ()   (1 или 2 броска)
                иначе 0                                              (при M = 0 или shiftChance = 0 — без броска)
   order = [first]
   если mode ≠ 'never':
     если mode = 'auto' и first ≠ 0 → order += [0]
     для k = 1 … M:  a = (wP ≤ 0 ? +k : −k)     // при равном |dw| — сначала к слою 0
                     если a ≠ first → order += [a];  если −a ≠ first → order += [−a]
   order = те d из order, где |wP + d| ≤ maxLayer
   ```
5. Если `order` не пуст и **слой** `wP + order[0]` свободен (кандидат не пересекается ни с одним
   экземпляром этого слоя) — кандидат ставится в этот слой, стыковка закончена. Иначе кандидат
   запоминается (с его `order`) и перебор продолжается.

*Фаза 2 — складка «по нужде».* Если в фазе 1 никто не встал: запомненные кандидаты **в том же порядке**,
для каждого `order[1], order[2], …` — первый свободный слой. Бросков ГСЧ нет.

Постановка: `w = wP + dw`, `id = "i" + n`, `parent = P`, `depth = P.depth + 1`,
`Link { a: A, b: B, dw }`, метки нового экземпляра (кроме `B`) — в конец открытых. Ничего не подошло —
`A` остаётся тупиком с причиной (нет совместимых / все в max / обзор, если хоть один кандидат отвергнут
пределом обзора / бесшовность, если хоть один отвергнут ею / правила, если все отвергнуты правилами /
иначе нет места).

Порядок при двух проходах (§4.5 G, шаг 4): ростовой проход (фаза 1, фаза 2), затем обычный (фаза 1,
фаза 2) — сложить комнату, дающую рост, лучше, чем закрыть одну из последних ростовых меток листом.
Следствие: при `shiftChance = 0` сдвиг бывает **только** у проёма, за которым ни одна комната прохода
не влезла в слой родителя; «по нужде» карта складывается, а не глохнет.

### 4.5. Замыкание петель (после роста каждой попытки и после дозаполнения)

`free` — несвязанные метки (`len ≥ 1`) в порядке (экземпляр по `order`, метка по индексу). Для `i` по
возрастанию (пропуская связанные) — первое `j > i` другого экземпляра, несвязанное, такое что:

1. метки совместимы (§3 G) и стоят лицом к лицу в 3D (§4.6 G) — **в любых слоях**;
2. `dw = w(b) − w(a)` допустим: `|dw| ≤ maxShift` и правила пары меток (§3.2: `never` → 0, `always` → ≠ 0, ✗ — нет);
3. новая связь не нарушает гарантию 2: `NA` — экземпляры в ≤ `localRadius − 1` от `a` (с расстояниями
   `dA`), `NB` — от `b`; для всех `X ∈ NA, Y ∈ NB, X ≠ Y` с `dA(X) + 1 + dB(Y) ≤ localRadius` — `X` и `Y`
   не пересекаются (это ровно пары, которые новая дверь сводит в радиус);
4. при `sightM > 0` проём петли не открывает линию длиннее предела (§13.3, та же проверка);
5. при бесшовности петля не делает пересекающиеся комнаты взаимно видимыми (§14.4).

Пара связывается `Link { a, b, dw }`. ГСЧ не используется.

### 4.6. Дозаполнение листьями (`fill = true`)

§4.7 G, но на потоке `F = root.sub("fold-fill")` и со складчатой стыковкой §4.4 (фазы 1/2, броски
`F.weightedIndex`, `F.shuffle`, `order` — на `F`). После очереди — замыкание петель §4.5.

### 4.7. Наполнение

§5 G без изменений: для каждого экземпляра в порядке `order` — `rollContent` на `C(i)` (+ отделка на
`Fin(i)`); `dangerAcc` — по дереву роста (`parent`), как в G.

### 4.8. Сводка и диагностика

`Run.fold = { minW, maxW, layers, overlaps, shifted }`: диапазон слоёв (с учётом стартового 0), число
занятых слоёв, число пересекающихся пар (§2, все пары), число связей с `dw ≠ 0`. Если count не набран —
`Run.stop` как в §4.8 G (`sight` — тупики из-за предела обзора; «правила» и «бесшовность» считаются в
`noSpace` и дают отдельные строки). `Run.sight` — полный скан по порталам (§13.2), `Run.pvs` — §14.
Предупреждения: «Складки: слоёв N (W от a до b), порогов со сдвигом W — S из L, пар комнат в одном
месте 3D — O.», обзор, дозаполнение, попытки, min/max — по-русски, движку повторять не нужно.

Реализационные подсказки (на результат не влияют): форма комнаты в повороте и её «раздутая на gap»
битовая карта кэшируются; проверка пары — сначала bbox, расширенные на `gap`, затем клетки меньшей
комнаты против карты большей; экземпляры хранятся по слоям; индекс петель — по линии метки.

## 5. Формат

| где | поле | смысл |
|---|---|---|
| `Instance` | `w` | слой, целое, `|w| ≤ maxLayer`; нет поля — 0 (евклидов прогон) |
| `Link` | `dw` | `w(b) − w(a)`; `a` — родитель или более ранняя метка петли; нет поля — 0 |
| `Run.settings` | `mode: 'fold'`, `fold: FoldSettings` | нормализованные настройки |
| `Run` | `fold: FoldStats` | сводка §4.8 |
| `Run` | `sight` | `{ maxM, line }` — самая длинная линия обзора по порталам (§13.2), считается всегда |
| `Run` | `pvs` | `{ [instId]: instId[] }` — что рендерить, стоя в комнате (§14); только при `seamless` и `sightM > 0` |

Связь двусторонняя: из `a` в `b` слой меняется на `+dw`, из `b` в `a` — на `−dw`. Остальное (клетки,
метки, декор, споты, наполнение) — как в евклидовом прогоне, в мировых 3D-координатах; одна и та же
мировая клетка может принадлежать нескольким экземплярам разных слоёв.

В экспорте `room-forge-run` (`exportRunJSON`) `links[].dw` и `settings.fold` уже есть;
`instances[].w` и сводку `fold` экспорт должен передавать так же (нет поля — 0 / нет сводки).

## 6. Как рендерить

**Есть `Run.pvs` (бесшовность, §14) — рисуем PVS текущей комнаты**, это точнее и без мерцания дверей.
Ниже — запасной вариант для прогонов без PVS.

**Видимое множество — по графу, а не по слою.** Рисуем текущую комнату и комнаты в ≤ `d` дверях от неё:
`visibleSet(run, roomId, d)`. Комнаты своего слоя, до которых далеко по дверям, **не рисуем**: в 3D они
могут стоять там же, где соседи за сдвигающей дверью.

Почему это безопасно: любые две комнаты множества связаны путём ≤ `2d` дверей через текущую; при
`2d ≤ localRadius` они не пересекаются (гарантия 2) — множество выглядит как кусок обычного дома, двери
совпадают с дверями, стены не прорастают в пол. По умолчанию `localRadius = 2` → `d = 1`.

Практика (Babylon):

- Меши и коллайдеры строятся **по экземплярам** (по `inst.id`) и включаются/выключаются
  `setEnabled(true/false)` при смене текущей комнаты. Пул мешей можно держать для «комната + соседи +
  соседи соседей», чтобы переход был без подгрузки.
- Болванка (`docs/BLOCKOUT-BABYLON.md`) рассчитана на плоский план. Для складчатого прогона её строят по
  **видимому подмножеству**: в JSON прогона оставить экземпляры из `visibleSet`, связи с обоими концами
  внутри, у меток со связью наружу — `linkedTo: null`. Пересечений внутри нет — ядро болванки работает
  как есть; двери, ведущие за границу множества, закроются панелью «тупика» — это и есть «дальняя
  дверь закрыта». Результат кэшируется по текущей комнате.
- Дальние двери соседей (ведут в комнаты на расстоянии `d + 1`) рисовать закрытыми, тёмными или с
  «туманом» в проёме. Открытую дверь в комнату, которой нет в множестве, рисовать нельзя — за ней может
  стоять пересекающаяся комната.
- Нужен взгляд через две двери — `localRadius = 4`, `d = 2`.

**Вариант для `localRadius = 1` — порталы со стенсилом.** При `localRadius = 1` гарантировано только
«текущая комната не пересекается ни с одним соседом»; два соседа между собой могут пересекаться. Тогда
каждый сосед рисуется **только сквозь свой проём**:

1. Текущая комната — обычным проходом (цвет + глубина).
2. Квады всех проёмов текущей комнаты: тест и запись глубины, цвет не пишется, стенсил := `k` (номер
   двери). Ближний к камере проём выигрывает пиксель — дальний проём, видный «сквозь» ближний, стенсил
   не перезапишет.
3. Для каждого соседа `k`: очистить глубину (цвет и стенсил не трогать) и нарисовать соседа с тестом
   «стенсил = k». В Babylon: `material.stencil` (`MaterialStencilState`), сосед — в своей rendering
   group, `scene.setRenderingAutoClearDepthStencil(group, true, true, false)` (глубину чистить, стенсил
   нет), `RenderingManager.MAX_RENDERINGGROUPS` поднять под число дверей.
4. Почему пересекающиеся соседи не мешают друг другу: отрезок луча от камеры до проёма `k` лежит внутри
   текущей комнаты, а сосед `k` с ней не пересекается — значит в области портала `k` перед дверью нет
   ничего, кроме текущей комнаты, и всё, что видно сквозь портал, — геометрия соседа `k`. Области
   порталов на экране не перекрываются (шаг 2), так что соседи `j ≠ k` туда не попадут.

Это дороже (по проходу на дверь) и требует порталов для физики (см. §7), поэтому по умолчанию — `localRadius 2`.

## 7. Как считать физику

**Рекомендуется — по видимому множеству.** Коллайдеры текущей комнаты и соседей (то же множество, что
рисуется, или `d = 1` при большем рендере). Пересечений нет — физика ведёт себя как в обычном доме,
проём двери проходим, стены соседей стоят где нарисованы. Игрок за кадр проходит не больше одной двери,
после перехода множество пересчитывается.

**По слою текущей комнаты — не годится в одиночку.** Слой — плоский план без пересечений, но сосед за
сдвигающей дверью лежит в **другом** слое: в своём слое на его месте может стоять чужая комната, игрок
упрётся в её стены у самого проёма. Если физика всё же «по слоям», нужно добавлять соседей за дверями
(и тогда это то же видимое множество).

Предметы, NPC, лут принадлежат экземпляру (`inst.id`): симулируются, только пока их комната в чьём-то
активном множестве; навигация NPC — навмеш по комнатам + связи как переходы с `w += dw`.

## 8. Двое игроков в одной точке

Состояние игрока: позиция в 3D + **текущая комната** `roomId` (+ `w` для детекторов). Комнату нельзя
определять по точке в 3D: одну точку могут занимать несколько комнат разных слоёв. Её ведут по переходам
через пороги (§9); на старте — стартовая комната.

- Игрок B **виден** игроку A, если `B.roomId ∈ visibleSet(A.roomId, d)`. То же правило для звука,
  выстрелов, взаимодействия.
- Двое в одной точке 3D, но в пересекающихся комнатах разных слоёв: эти комнаты по гарантиям дальше
  `localRadius ≥ 2d` по графу, значит не входят в видимые множества друг друга — игроки не видят и не
  толкают друг друга, хотя их координаты совпадают.
- Сетевой код: сервер хранит `roomId` каждого, рассылает сущности только из комнат видимого множества
  получателя (interest management по графу, а не по расстоянию).

## 9. Переход через порог

Связь `L` — пара меток лицом к лицу; между ними полоса стены толщиной `gap` клеток (проём). Триггер
перехода — объём этой полосы (длина проёма × `gap`, по высоте двери). Игрок, вошедший со стороны `a` и
вышедший со стороны `b`:

```
roomId = L.b.inst
w      = w + L.dw          // со стороны b в a: w − L.dw
```

3D-позиция не меняется: двери совпадают. Видимое множество пересчитывается от новой комнаты; прежняя
комната остаётся в нём (она сосед), так что «за спиной» ничего не пропадает. Пропадают комнаты, которые
стали дальше `d`, — они за закрытыми дальними дверями.

## 10. Детекторы (позже)

Данные уже есть в прогоне, сами детекторы — геймдизайн:

- **Слой** текущей комнаты `w`, разница `|Δw|` до других игроков/объектов: «он рядом, но через 2 слоя».
- **Соседство в 4D** — комнаты, пересекающиеся с текущей в 3D (другие слои того же места):
  `overlapPairs(project, run)` → для комнаты список «кто здесь же в других слоях». Детектор может
  показывать их контуры-призраки, считать их, подсвечивать «за этой стеной в слое +1 кухня».
- **Слои рядом**: комнаты в слоях `w ± 1`, близкие в 3D, — кандидаты на «просачивание» Самосбора.
- Игроки в одной точке 3D и разных `w` — «фантомное присутствие» (шаги, холод), без видимости.

## 12. Ограничения

- `maxShift = 0` (или `maxLayer = 0`) даёт плоский план без пересечений с теми же гарантиями, что у
  евклидова, но без проверки «свободного фасада» (§4.5 G) — он хуже заполняет место (count 300 на
  пресетах — 1/10). Для плоских карт используйте евклидов генератор.
- Складки «по нужде» происходят у каждого проёма, за которым в своём слое ничего не влезло, — поэтому
  даже при `shiftChance = 0` на 30 комнатах бывает несколько сдвигов. Режим «складывать только при
  остановке роста» — возможное развитие.
- `overlaps` считает пары по критерию §2 (с зазором `gap`), а не только общие клетки пола.
- Предел обзора 5 м и меньше пресеты не выдерживают (§13.4): нужны комнаты с короткими входами.
- Бесшовность дорожает и снижает достижимость больших count при жёстком пределе (§14.6).

## 13. Дальность обзора в 4D (`settings.sightM`)

### 13.1. Зачем

Дискомфорт: **неестественно недалеко видно**, будто сами структуры не дают смотреть вдаль. Генератор не
собирает ни одной прямой линии взгляда длиннее `sightM` — ни внутри комнаты, ни сквозь цепочку дверей:
каждая анфилада ломается, за проёмом — стена, тамбур, поворот. В 4D это сильнее, чем в обычном доме:
дом бесконечен и сам себя перекрывает, но взгляд всегда упирается в несколько метров.

### 13.2. Определение — по порталам

Луч всегда находится в **контексте**: комната (экземпляр) или проём связи. Проём — клетки зазора между
двумя связанными метками на пересечении их пролётов (как §7.1 G); при `gap = 0` клеток нет, проём —
ребро между рядом клеток одной комнаты и рядом клеток другой на том же пересечении.

Шаг по стороне из клетки `p` (в контексте `K`) в соседнюю клетку `q`:

| контекст `K` | `q` | новый контекст |
|---|---|---|
| комната | клетка этой комнаты | та же комната |
| комната | клетка проёма одной из **её** связей (gap ≥ 1) | этот проём |
| комната | шаг через ребро её связи (gap = 0) | связанная комната |
| проём | клетка этого проёма | тот же проём |
| проём | клетка одной из двух его комнат | эта комната |
| иначе | — | стена, луч кончился |

Диагональный шаг `(dx, dy)` — только если проходимы **оба** обхода через угловые клетки
(`p → (px+dx, py) → q` и `p → (px, py+dy) → q`) и они приводят в один контекст: сквозь угол смотреть
нельзя. Направления, линия (максимальная цепочка шагов) и длина — как §7.2 G: `n·cellM` по прямой,
`n·cellM·√2` по диагонали; отрезок `Run.sight.line` — «от края до края».

Слой `W` в определении не участвует. Комнаты других слоёв, занимающие те же клетки, **для луча не
существуют** — не удлиняют и не обрывают его; проходимость задаёт только цепочка комнат вдоль луча.
Несвязанные двери — стена. Одну и ту же мировую клетку могут пересекать разные линии из разных цепочек
комнат.

**Полный скан** (`Run.sight`): у каждой максимальной линии ровно одно начало — состояние
(контекст, клетка), из которого шаг назад невозможен. Для каждого направления (порядок §7.2 G), каждого
контекста (комнаты по `order`, затем проёмы по номеру связи) и каждой его клетки (по возрастанию
`(y, x)`), если шаг назад невозможен, — идём вперёд до упора. Побеждает строго большая длина; `maxM`
округлён до 0.001 м. Работа линейна по числу клеток (каждое состояние лежит ровно на одной линии
направления); count 150 — около 15–30 мс.

### 13.3. Ограничение при `sightM > 0`

Пределы в клетках — §7.3 G (`Nорт`, `Nдиаг`).

1. **Пул** — §4.2, п. 2 (комнаты с собственной линией длиннее предела — из пула, предупреждение; если
   такая комната стартовая — ставится всё равно, с предупреждением).
2. **Кандидат** (§4.4, шаг 3а): комната-кандидат и проём будущей связи добавляются на пробу. От каждой
   клетки проёма (при `gap = 0` — от клеток родителя у ребра) по каждому направлению идём назад (в
   родителя и дальше сквозь его проёмы — в любые слои) и вперёд (в кандидата), останавливаясь, как только
   длина превысила предел. Длиннее — кандидат отвергается. Этого достаточно: у кандидата единственная
   связь, значит любая новая линия проходит через её проём.
3. **Петли** (§4.5, п. 4) — та же проверка для проёма петли (обе комнаты уже стоят).

ГСЧ в проверках обзора не используется. Независимая проверка — `validateFoldRun`: свой полный скан по
мировым клеткам (`instanceWorld`) и меткам связей; каждая линия ≤ предела (кроме линий целиком внутри
стартовой комнаты, если она сама длиннее), `Run.sight.maxM` совпадает со сканом.

### 13.4. Помогает ли складывание

Пресеты, 10 сидов `hrush-001…010`, `fill = false`; «набрано» — сколько сидов дали count; пересечения —
среднее число пар комнат в одном месте 3D:

| `sightM` | count | 4D набрано | 4D комнат мин–макс | слоёв | пересечений | евклидов набрано | евклидов мин–макс |
|---|---|---|---|---|---|---|---|
| 0 | 150 | 10/10 | 150 | 8.8 | 303 | 10/10 | 150 |
| 9 | 150 | 10/10 | 150 | 9.7 | 307 | 10/10 | 150 |
| 7 | 60 | 10/10 | 60 | 7.7 | 83 | 6/10 | 16–60 |
| 7 | 150 | 8/10 | 71–150 | 9.2 | 280 | 0/10 | 16–138 |
| 6 | 60 | 9/10 | 46–60 | 7.9 | 61 | 5/10 | 48–60 |
| 6 | 150 | 1/10 | 43–150 | 8.7 | 125 | 0/10 | 58–148 |
| 5 | 30 | 0/10 | 11–20 | 3.3 | 1 | 2/10 | 7–30 |

Да, помогает на 6–7 м. Слой на линии обзора не влияет (луч идёт сквозь слои), так что складка не может
«сломать» длинную линию. Но в евклидовом генераторе кандидата при жёстком пределе отсекают **два**
фильтра — коллизия с уже построенным и обзор, — и вместе они быстро глушат рост. В 4D коллизию снимает
складка (остаётся только локальная — с соседями родителя), и единственным серьёзным фильтром остаётся
обзор. Тупики при 6 м — примерно поровну «обзор» и «нет места» (последнее — соседи родителя по
`localRadius`: ванная, упирающаяся в уже стоящую кухню той же прихожей).

При 5 м не работают оба генератора: из пула уходят 17 комнат (все залы, длинные коридоры), а прямой взгляд
с площадки в квартиру — глубина площадки 2.4–3.5 м + проём + прихожая ≥ 1.8 м — уже длиннее 5 м, так что
квартиры не пристыковываются. Для 5 м нужны свои комнаты: узкие тамбуры и повороты у входов.

### 13.5. Рекомендации

| `sightM` | ощущение |
|---|---|
| 5–7 м | давящее: дальше пары комнат не видно никогда; 6–7 м — рабочий диапазон на пресетах |
| 9 м | умеренное: почти не мешает, длинные анфилады исчезают |
| ≥ 12 м или 0 | не ощущается |

### 13.6. Как поддержать ощущение в движке

- **Давит геометрия, а не затемнение.** Генератор гарантирует, что по прямой (оси, диагонали) дальше `sightM`
  смотреть некуда — взгляд упирается в стену, тамбур, поворот. Портальный рендер (§6,
  `docs/BLOCKOUT-BABYLON.md` §12) показывает всё, что видно, без тумана: даль не темнеет, если место не тёмное
  по смыслу (тёмная лестница — отдельная локация со своим туманом).
- **Туман на `sightM` — по желанию** (атмосфера; в Babylon — `scene.fogMode = Scene.FOGMODE_LINEAR`,
  `fogEnd = sightM`, `fogStart ≈ 0.4·sightM`). Обязателен только при рендере набора PVS одной сценой (§14.5):
  там он прячет край набора.
- **Видимое множество** (§6) — по графу, а не по слоям; луч обзора по определению тоже идёт по графу
  (по порталам), поэтому то, что генератор считает видимым, — ровно то, что движок рисует сквозь двери.
- **Портальный рендер** (§6, стенсил) естественно сужает картинку до проёмов; дальние двери соседей —
  закрытые или тёмные.
- Свет — короткие источники, тёмные проёмы; звук — затухание по числу дверей, а не по метрам.

## 14. Бесшовная видимость (PVS, `fold.seamless`)

### 14.1. Почему мерцало

Рендер «комната + соседи по графу» закрывает двери на краю набора. При переходе через порог набор
меняется: дверь, бывшая краем (закрытой), становится внутренней (открытой), а у новой границы
закрываются другие. Игрок видит, как двери появляются и исчезают. Математика позволяет сделать это
бесшовно: рисовать не «соседей по графу», а всё, что **может быть видно** из комнаты, и гарантировать, что
это множество непротиворечиво в 3D.

### 14.2. Определение

**PVS(A)** — потенциально видимый набор комнаты A: комнаты, в которые из A (из любой точки её пола **и**
клеток её проёмов) можно увидеть хоть что-то по прямой в плане (любого направления, не только 4 оси) сквозь
цепочку проёмов, не дальше `sightM`, независимо от W (портальная логика §13.2). A ∈ PVS(A).

Набор **консервативен** — надмножество настоящей видимости: лишняя комната допустима, пропущенная — нет.
Дальность ограничена `sightM`: при рендере набора одной сценой движок обязан делать туман до полной
непрозрачности к `sightM` (§13.6) — то, что дальше, не видно в любом случае (оси и диагонали генератор и так
не пускает дальше `sightM`, а косые линии отрезает туман). Портальному рендеру туман не нужен: он открывает
проёмы, пока они видны, а бесконечный мир раскрывает комнаты на дальность его горизонта (§15.7).

### 14.3. Гарантия и почему смена набора невидима

**Гарантия:** для каждой комнаты A комнаты PVS(A) попарно не пересекаются в 3D (критерий §2, с зазором `gap`).

- Рендер PVS(A) точен: это кусок обычного дома без наложений, всё, что видно из A, в нём есть.
- Комнаты PVS(A), которые из текущей точки не видны, закрыты стенами видимых комнат (стена, в которую
  упирается луч, принадлежит комнате, до которой луч дошёл, — она видна и нарисована) или туманом.
- **Порог.** Игрок переходит из A в B, текущая комната меняется, когда глаз в проёме связи A–B. Клетки
  проёма входят в источник **обоих** наборов, поэтому всё, что видно из этой точки, лежит в PVS(A) ∩ PVS(B).
  Остальные комнаты каждого набора из этой точки не видны (закрыты стенами или туманом). Значит, кадр из
  точки переключения одинаков с PVS(A) и с PVS(B): смена набора не меняет ни одного пикселя.
- **Двери на краю PVS** (ведут в комнату вне набора) рисуются **открытыми, в темноту** — без заглушки.
  Сквозь такую дверь из текущей комнаты не проходит ни одна прямая (иначе комната за ней была бы в PVS),
  поэтому её проём не виден; а заглушка была бы видна и исчезала бы при смене набора — то самое мерцание.
  Тупики (метки без связи) — обычная стена или дверь-заглушка, одинаковая во всех наборах.

### 14.4. Расчёт (`src/gen4d/pvs.ts`)

Обход цепочек проёмов от A (поиск в глубину по связям; проём в цепочке не повторяется). Цепочка
продолжается через проём, если:

1. проём в пределах `sightM` (евклидово, в плане) от рамки источника — прямая длиной ≤ `sightM` до
   дальнего проёма не дотянется;
2. цепочка «прокалываема»: есть прямая, проходящая источник и все проёмы цепочки в нужную сторону.
   Прямые — `(θ, s)`: направление и смещение вдоль нормали `(−sin θ, cos θ)`. Направления разбиты на
   720 корзин по 0.5°. Для корзины у каждого отрезка интервал смещений `[min, max]` проекций его концов в
   центре корзины, расширенный на `|p − o|·0.25°` (столько проекция может уехать внутри корзины), —
   поэтому, если прямая есть хоть при каком-то угле корзины, проверка её не пропустит. Корзина жива, пока
   пересечение интервалов не пусто и направление идёт через каждый проём в нужную сторону.
   - Источник — выпуклая оболочка клеток A вместе с прямоугольниками всех её проёмов.
   - Проём из A — только дальняя линия (взгляд может начаться внутри проёма); следующие проёмы — обе
     линии (ближняя и дальняя) — прямая проходит проём насквозь.
   - Проёмы удлинены на допуск `0.05 м` с каждой стороны; стены промежуточных комнат и порядок
     пересечения проёмов не учитываются. Всё это только расширяет набор.

Каждая комната, в которую вошла живая цепочка, — в PVS(A).

**В генераторе.** PVS ведётся по экземплярам и только растёт.

- **Кандидат R** (§4.4, шаг 3б) — PVS(R) по пробной геометрии (R и проём). Видимость симметрична, а у R
  единственная связь, поэтому R появится ровно в PVS(A) для A ∈ PVS(R), и других изменений нет: новые
  прямые проходят через новый проём и кончаются в R. Проверка: R не пересекается ни с одной комнатой из
  PVS(A) для всех A ∈ PVS(R); пары внутри PVS(R) проверяются, кроме тех, что обе лежат в PVS(родителя) —
  они уже проверены. После постановки: PVS(R) записан, R добавлен в PVS(A) для A ∈ PVS(R).
- **Петля X–Y** — новые прямые проходят X и Y, значит затронуты комнаты, видящие X или Y:
  `{X, Y} ∪ PVS(X) ∪ PVS(Y)`. Их наборы пересчитываются и объединяются со старыми; новые члены не должны
  пересекаться с остальными, иначе петля не замыкается.
- Отказ — следующий кандидат или поворот, а не другой `dw`: пересечение в 3D от слоя не зависит.

**В валидаторе** (`validateFoldRun`): (1) каждый PVS попарно без пересечений; (2) выборочно —
консервативность: из точек пола каждой комнаты (сетка 0.2 м; по умолчанию 4 точки на комнату,
`{ pvsPoints, pvsRays }` — гуще) и клеток проёмов выпускаются лучи в 180 направлениях; марш по клеткам
(DDA) с портальной логикой до стены или `sightM`; каждая комната, куда луч зашёл, обязана быть в PVS
источника. На пресетах при полной сетке и 240–360 лучах промахов нет; настоящий набор в среднем 6–7
комнат, PVS — 7–8 (запас консервативности ~1.3 комнаты).

### 14.5. Как рендерить в движке

- **Рендер:** меши комнат `run.pvs[текущая комната]` — включить, остальные — выключить. Набор меняется
  на пороге (§9), это невидимо (§14.3).
- **Двери на краю PVS** — открытые, без заглушки; за ними — фон или цвет тумана.
- **Туман:** до полной непрозрачности к `sightM` (§13.6) — обязательная часть гарантии рендера набором
  (у портального рендера тумана нет, `docs/BLOCKOUT-BABYLON.md` §12.3).
- **Физика:** по PVS текущей комнаты (пересечений нет, всё, во что можно упереться рядом, в нём есть)
  или по слою текущей комнаты плюс соседи за сдвигающими дверями (§7). Двое игроков: B виден A, если
  `B.roomId ∈ pvs[A.roomId]` (§8 с PVS вместо видимого множества).
- **Формат:** `Run.pvs: { [instId]: instId[] }` — id экземпляров по возрастанию `order`, включая саму
  комнату; в экспорте `room-forge-run` — поле `pvs` (или `null`).

## 15. Бесконечный мир (`src/gen4d/stream.ts`)

### 15.1. Идея

> Карта бесконечно генерируется, пока мы идём куда-то. Уже прогенерированное пространство сохраняется
> локально, и в него можно вернуться. Всё генерируется на основе сида + модификаторов сида.

Мир не строится целиком. Старт — одна комната. Когда игрок входит в комнату, движок просит мир «раскрыть»
окрестность — сгенерировать комнаты за ещё не открытыми дверями поблизости. Сгенерированное больше не
меняется, сохраняется (`save()` → localStorage) и при возврате восстанавливается как было.

Стыковка, проверки, петли, предел обзора и PVS — **те же, что у складчатого прогона** (общий код —
`foldcore.ts`, §4.4–4.5, §13, §14). Отличаются порядок роста (по дверям, которые открывает игрок), ГСЧ (по
«адресам», §15.5), тупики и гарантия бесконечности (§15.4).

Складки по умолчанию другие, чем у прогона (`DEFAULT_STREAM_FOLD`):

| поле | значение | почему |
|---|---|---|
| `seamless` | **false** | рендер — порталами: комната за дверью рисуется только в экранной области проёма, поэтому комнаты в поле зрения **могут** пересекаться в 3D; бесшовность даёт рендер, а не запрет. PVS всё равно считается — это список того, что обходить порталами |
| `localRadius` | **1** | комната не пересекается со своими соседями — нужно физике на пороге (текущая + соседняя) |
| `shiftChance` | 0.8 | складок много |
| `maxShift` | 4 | шире окно слоёв: при возврате цепочки в плотное место 3D свободный слой находится чаще (§15.4) |
| `maxLayer` | 1000 | слоёв сколько угодно |

Предел обзора `sightM` (по умолчанию 9 м) **действует** — по порталам (§13): структуры не дают смотреть вдаль.

### 15.2. API

```ts
import { createStreamWorld, streamSettings, viewHorizonM, worldKey } from './gen4d/stream';

const key = worldKey(seed, mods);                       // "room-forge/world/<seed>[+mod+mod]"
const saved = localStorage.getItem(key);
const world = createStreamWorld(project, streamSettings(seed, { deadEndChance: 0.2 }), saved ? JSON.parse(saved) : undefined);
if (world.stale) console.warn(world.warnings);          // сохранение не подошло к проекту — мир начат заново

let here = world.startId!;
world.ensureAround(here);                                // при входе в комнату
world.ensureVisible(here);                               // всё, что может попасть в кадр (до viewHorizonM(sightM)), — окончательно
const run = world.run();                                 // Run: instances (w), links (dw), content, pvs, fold, sight
world.onChange((ids) => { buildMeshes(ids); localStorage.setItem(key, JSON.stringify(world.save())); });
```

| метод | что делает |
|---|---|
| `run()` | снимок мира — обычный `Run` складчатого прогона: `instances` (с `w`), `links` (с `dw`), `openConnectors` (заколоченные **и** ещё не раскрытые двери), `content`, `pvs` (при `sightM > 0`), `fold`, `sight`. Кэшируется до следующего изменения; новый снимок — новый объект (экземпляры и связи не меняются никогда) |
| `expand(id)` | раскрыть экземпляр: решить судьбу всех его нераскрытых дверей. Возвращает id новых экземпляров |
| `ensureAround(id, doors = aheadDoors)` | раскрыть всё на расстоянии `< doors` по графу дверей от `id` (BFS), дальше — нет |
| `ensureVisible(id, reachM?)` | раскрыть всё, что видно из `id` сквозь проёмы до дальности `reachM` (по умолчанию `viewHorizonM(sightM)` — горизонт портального рендера), — до замыкания (§15.7). `reachM ≤ sightM` — только PVS(`id`), как раньше |
| `viewHorizonM(sightM)` | горизонт без тумана, м: max(3·`sightM`, 24), при `sightM = 0` — 40 (`src/gen4d/pvs.ts`) |
| `doorState(id, connectorId)` | `'linked'` — проём; `'dead'` — заколоченная дверь (тупик); `'pending'` — ещё не раскрыта |
| `isExpanded(id)`, `addressOf(id)` | раскрыт ли экземпляр; его адрес (§15.5) |
| `stats()` | комнат, раскрыто, нераскрытых дверей (и ростовых), выросло / петель / тупиков по шансу / «не встало», слои, пересечения, время раскрытия (ср / p95 / макс по последним 500) |
| `save()` / `onChange(cb)` | сохранение (§15.8) / подписка на новые экземпляры (возвращает отписку) |
| `warnings`, `stale`, `startId` | предупреждения мира, «сохранение устарело», стартовый экземпляр |
| `locationOf(id)`, `descend(id)`, `exitOf(id)` | спец-локации: розыгрыш локации экземпляра; переход на этаж(и) ниже — комната-выход (§15.14) |

Проверка снимка — тот же `validateFoldRun(project, world.run())` (§15.10).

### 15.3. Настройки `StreamSettings`

| поле | по умолчанию | смысл |
|---|---|---|
| `seed`, `mods` | —, `[]` | сид и модификаторы сида (§15.9); ГСЧ мира — `makeRng(seed)` или `makeRng(seed + "+" + mods.join("+"))` |
| `gap`, `match` | 1, `'exact'` | как у генератора |
| `sightM` | 9 | предел обзора по порталам, м (0 — без предела и без PVS) |
| `fold` | `DEFAULT_STREAM_FOLD` | §15.1 |
| `startRoomId` | null | стартовая комната; null — по тегу `start` (вес), иначе по весу |
| `deadEndChance` | 0.15 | вероятность, что дверь при раскрытии окажется **заколоченной**, даже если за ней есть место |
| `branching` | 1 | ветвистость: вес развилки с `k` ходами вперёд × `branching^(k − 1)` (§15.6) |
| `aheadDoors` | 2 | окно `ensureAround` по умолчанию |

Нормализация — `normStream` (мусор → умолчания, `deadEndChance ∈ [0, 1]`, `branching ∈ [0, 100]`,
`aheadDoors` — целое `[0, 16]`); `streamSettings(seed, partial)` — полные настройки.

### 15.4. Раскрытие экземпляра (для повторения в движке)

**Двери.** Метка с `len ≥ 1` — дверь. У раскрытого экземпляра каждая дверь либо связана, либо заколочена;
нераскрытые двери бывают только у нераскрытых экземпляров. «Ростовая» дверь — ростовая метка §4.2 G
(за ней может встать комната, продолжающая рост).

**Потоки ГСЧ** (адрес — §15.5): `root = makeRng(seedKey)`; старт — `root.sub("start")`; дверь —
`D = root.sub("door:" + адрес двери)`; магистраль — `root.sub("spine:" + адрес экземпляра)`; наполнение —
`root.sub("content:" + адрес)`, отделка — `root.sub("finish:" + адрес)`.

**Старт:** комната по `startRoomId` / тегу `start` / весу (`root.sub("start").weightedIndex`), `rot = 0,
dx = dy = 0, w = 0`, адрес `0000000000000000`; старт — на магистрали.

**Раскрыть экземпляр P:**

1. Если P на **магистрали** — сначала её продолжение: нераскрытые ростовые двери P в порядке
   `room.connectors`, повёрнутом на `off = root.sub("spine:" + адрес P).int(0, k − 1)` (при `k = 1` — без
   броска). По очереди — «дверь магистрали» (ниже), пока за одной не встанет комната с нераскрытой ростовой
   дверью: она становится магистралью.
2. Остальные нераскрытые двери P — по порядку `room.connectors`, «обычная дверь».
3. Если в мире не осталось ни одной нераскрытой ростовой двери — крайняя мера (§15.4, «Бесконечность»).

**Дверь A экземпляра P:**

1. `roll = D.next() < deadEndChance` — бросок **всегда** (поток роста от статуса двери не зависит).
   `reserve` = дверь ростовая и нераскрытых ростовых дверей в мире (включая эту) `≤ STREAM_RESERVE = 10`.
2. Обычная дверь: `roll` и не `reserve` → **заколочена** («по шансу»). Иначе — **петля**: если напротив A в 3D
   (любой слой) стоит нераскрытая дверь другого экземпляра и связь проходит проверки §4.5 (совместимость, лицом
   к лицу, правила порогов, гарантия 2, обзор, бесшовность), — связать. Кандидатов несколько — в каноническом
   порядке (глубина, адрес, индекс метки). Без ГСЧ. У двери магистрали шаг 2 пропускается.
3. **Складчатая стыковка** §4.4 на потоке D со следующими отличиями:
   - кандидаты — все комнаты пула с весом > 0, совместимые с A, одной группой (min в бесконечном мире
     смысла не имеет);
   - вес — `weight × branchMul(grow, branching) × applyMods(...)`;
   - комната, которую сейчас ставить нельзя (`unique` уже стоит; `max` в окрестности — §15.6), **остаётся в
     списке весов**: выпала — пропускается без бросков. Так выбор остальных комнат не зависит от того, где
     уникальная уже встала;
   - **«комната важнее слоя»**: кандидат, прошедший проверки, сразу пробует весь свой порядок `dw` (фаза 2
     §4.4 не откладывается). Выбор комнаты не зависит от занятости слоёв — от неё зависит только `W`;
   - у двери магистрали и при `reserve` — сначала проход только комнат, дающих рост (`growOthers > 0`), затем
     обычный (как ростовой проход §4.5 G).
4. Ничего не встало — дверь заколочена с причиной (`space` / `sight` / `seam` / `rule` / `max` / `nomatch`).

Новый экземпляр: `id = "i" + n` (n — номер постановки), `parent`, `depth`, `w`; связь `parent → ребёнок`
с `dw`; PVS (§14.4, без бесшовности — по поставленной геометрии; затем симметрично в наборы видимых);
наполнение — §4.7 на потоках адреса, `dangerAcc` — по родителю.

**Бесконечность.** Гарантия: у мира всегда есть нераскрытая ростовая дверь, а всё сгенерированное связно —
до неё можно дойти.

- **Магистраль** — одна линия роста от старта, выбранная по адресам: её двери не заколачиваются по шансу и
  сначала пробуют комнаты, дающие рост. Пока магистраль продолжается, мир бесконечен независимо от тупиков.
  Если ни одна ростовая дверь её комнаты не дала роста (нет места / обзор), магистраль переходит к первой
  новой комнате с ростовой дверью, поставленной где угодно.
- **Резерв роста** (как в генераторе, `RESERVE_MAX`): пока нераскрытых ростовых дверей ≤ 10, ростовые двери
  не заколачиваются по шансу и сначала пробуют рост. На пресетах держит фронт на ~10 дверях.
- **Крайняя мера**: если после раскрытия нераскрытых ростовых дверей не осталось (подряд отказали все — так
  бывает, когда цепочка возвращается в место 3D, где заняты все слои `w ± maxShift`), «расколачивается»
  заколоченная по шансу ростовая дверь — самая глубокая (при равной — с большим адресом); её экземпляр снова
  нераскрыт и становится магистралью. Предупреждение в `warnings`.
- Мир может кончиться, только если все ростовые двери отказали по месту или обзору, а заколоченных по шансу
  нет (`deadEndChance = 0` или их не было) — тогда сводка говорит «Мир заглох». На пресетах ни разу
  (6 сидов × 4000 комнат «пожирающим фронт» игроком, §15.11).
- **Бесшовность** (`fold.seamless = true`) поддержана с теми же гарантиями, что у прогона, но бесконечному миру
  она вредит: на пресетах мир глохнет на ~40 комнатах (бесшовность отвергает много стыковок, а фронт роста
  мал). Для потокового мира — портальный рендер и `seamless: false`.

### 15.5. Детерминизм и адреса

**Адрес** экземпляра — 64-битный хэш пути дверей от старта:

```
addr(старт)   = "0000000000000000"
addr(ребёнок) = childAddr(addr(родитель), id метки родителя, через которую он поставлен)
childAddr(p, c) = hex8(FNV1a32(p + "/" + c)) + hex8(FNV1a32(c + "\" + p))
```

Адрес двери — адрес комнаты, которая за ней встанет. Все броски, относящиеся к двери, — на её потоке
`root.sub("door:" + адрес)`, наполнение и отделка — на потоках адреса экземпляра. Поэтому:

- **Наполнение** (тир, споты, лут, отделка) комнаты по адресу **не зависит** от порядка, в котором игрок ходил:
  если по тому же пути стоит та же комната, у неё то же наполнение (тест: 0 расхождений).
- **Раскладка** может зависеть от истории раскрытий — это нормально, мир сохраняется. Что может зависеть:
  занятость слоёв (меняет `W`, не комнату), уникальные комнаты (кто первый), резерв роста (сколько ростовых
  дверей открыто во всём мире), петли (существует ли уже дверь напротив), линии обзора сквозь соседей
  соседей. Не зависит: всё остальное — броски по адресам, окно `max` (§15.6), порядок дверей экземпляра.
- **Каноническая очередь**: `ensureAround` раскрывает нераскрытые экземпляры окна по одному — каждый раз
  минимальный по (глубина от старта, адрес), окно пересчитывается после каждого раскрытия; `ensureVisible` —
  так же по PVS. Два разных маршрута к одному месту чаще дают одно и то же.

Замер (тест «две разные истории»: два игрока-блуждателя по 150 шагов, в мире A сначала ходит первый, в мире B
— второй; 6 сидов): общих адресов 812, **постановка** (комната, поворот, место) совпала в **98.6 %**, из них
сдвиг порога `dw` — в 94.6 %; наполнение при совпавшей постановке — 100 %. Абсолютный `W` совпадает реже: одно
расхождение слоя сдвигает `W` всего поддерева (`w = w(родителя) + dw`), игроку это не видно.

Что улучшило совпадение (было 85 %): потоки ГСЧ по адресам дверей; запрещённые комнаты остаются в списке
весов; «комната важнее слоя»; магистраль вместо частого переключения резерва.

### 15.6. Тупики, ветвистость, max / unique / min

- **`deadEndChance`** — доля дверей, заколоченных по шансу (кроме магистрали и резерва). Плюс тупики «не
  встало» (~7 % дверей на пресетах). Замер — §15.11.
- **`branching`** — `branchMul`: развилка с `k` ходами вперёд (ростовых меток кроме входной) получает вес ×
  `branching^(k − 1)`: коридор (2 ростовые) — ×1, T (3) — ×`branching`, крест (4) — ×`branching²`. Множитель
  «всем хабам» ничего бы не дал: с одной дверью совместимы комнаты одного рода (за дверью коридора — только
  коридоры), важна доля развилок среди них. Пресеты, доля развилок среди поставленных хабов: `branching`
  0.25 → 0.14, 1 → 0.36, 4 → 0.67.
- **`unique`** — один раз на мир.
- **`max`** — «не больше `max` копий в окрестности пути»: окрестность — `MAX_WINDOW = 10` предков по дереву
  роста (включая саму комнату) и все их дети. Буквально «не больше `max` в мире» убил бы бесконечность (у
  площадок и коридоров пресетов `max = 99`: после сотни площадок рост встал бы), а окрестность пути
  существует целиком к моменту раскрытия при любом порядке ходьбы — правило не зависит от истории. Смысл для
  дизайнера: «на пути игрока такая комната встречается не чаще `max` раз на ~10 дверей».
- **`min`** не применяется: у бесконечного мира нет конца, к которому его выполнять.

### 15.7. Сколько раскрывать: `aheadDoors` и `ensureVisible`

- **Физика** — текущая комната + соседи за порогами: они существуют после `expand(текущей)`. `aheadDoors = 2`
  (по умолчанию) раскрывает и соседей — шагнув через порог, игрок уже окружён готовыми комнатами.
- **Рендер** — PVS текущей комнаты. Комната, которая могла бы быть видна, но ещё не сгенерирована, при
  генерации «появится» в кадре. PVS дотягивается далеко по дверям (пресеты, 9 м — глубина PVS в дверях:
  2 — 18 %, 3 — 33 %, 4 — 33 %, 5 — 13 %, 6 — 4 %), поэтому рекомендация «`aheadDoors` ≥ глубины PVS» означает
  5–6 дверей и много лишнего.
- **Точнее — `ensureVisible(id)`**: раскрыть все комнаты, которые видны из комнаты, пока среди них есть
  нераскрытые. После этого всё, что видно из комнаты (и из её проёмов), окончательно: каждая линия взгляда
  идёт по видимым комнатам, а у раскрытых комнат все двери либо ведут в комнату (она тоже видна —
  консервативность), либо заколочены. В момент входа в комнату B из A взгляд — из проёма A–B, а он входит в
  источник набора A, который уже был замкнут, — новые комнаты в кадр не попадают.
- **Дальность — горизонт рендера, а не `sightM`.** Генератор не пускает дальше `sightM` прямые по осям и
  диагоналям, но косая линия сквозь цепочку дверей бывает длиннее. Раньше её край прятал обязательный туман
  на `sightM`; портальный рендер теперь без тумана открывает проёмы, пока они видны, до горизонта
  `viewHorizonM(sightM)` = max(3·`sightM`, 24 м) (без предела обзора — 40 м; `docs/BLOCKOUT-BABYLON.md` §12.3).
  Поэтому `ensureVisible(id, reachM = viewHorizonM(sightM))`:
  1. PVS(`id`) (`Run.pvs`, дальность `sightM`) — как раньше: каждый раз нераскрытый экземпляр, минимальный по
     (глубина, адрес), и так, пока такие есть;
  2. если `reachM` больше `sightM` — «дальний» набор: `computePvs` (§14.4, та же логика: цепочки проёмов,
     прокалываемые прямой, допуск 5 см) с дальностью `reachM` от комнаты **по текущей геометрии мира** (он не
     хранится — считается на месте, ≈ 0.3 мс); все его нераскрытые экземпляры раскрываются в каноническом
     порядке, затем набор пересчитывается (раскрытые добавили проёмы); снова п. 1 — до замыкания.

  Если сквозь проём в кадре видно хоть что-то, туда дошла прямая из глаза сквозь всю цепочку проёмов, а все
  они ближе горизонта (дальше рендер проёмы комнаты не открывает) — значит комната за ним в дальнем наборе
  (глаз — внутри источника, расстояние от рамки источника не больше расстояния от глаза), и она раскрыта:
  нераскрытых дверей (проёмов в пустоту) в кадре нет. Замкнутость устойчива: позже раскрытые где-то ещё комнаты не видны из этой (иначе были бы в наборе), а
  петля к её видимой комнате не может появиться — у раскрытой комнаты нет нераскрытых дверей.

  Цена (пресеты, `sightM` 9 → дальность 27 м, блуждание 200 шагов, 3 сида): дальний набор в среднем
  11–13 комнат (PVS — 7–8), максимум 25–38; комнат в мире на тех же шагах — на 1–8 % больше; `ensureVisible`
  0.6–1.0 мс в среднем, p95 ≤ 4 мс, максимум 15–41 мс (раскрытие сразу нескольких комнат).

Рекомендация движку: при входе в комнату — `ensureAround(id)` (`aheadDoors = 2`) **и** `ensureVisible(id)`
(по умолчанию — на горизонт рендера). Без предела обзора (`sightM = 0`) хранимого PVS нет, но
`ensureVisible` работает (дальний набор на 40 м). `ensureVisible(id, sightM)` — прежнее поведение (только
PVS; тогда рендеру нужен туман на `sightM`).

### 15.8. Сохранение

`save()` → `StreamSave` (`format: 'room-forge-world', version: 1`), ключ localStorage — `worldKey(seed, mods)`:

| поле | что |
|---|---|
| `settings` | нормализованные настройки (при загрузке берутся отсюда, а не из аргумента) |
| `run` | снимок `Run` **без клеток и без наполнения**: экземпляры (`roomId, rot, dx, dy, w, parent, depth`), связи (`dw`), `pvs`, `sight`, `fold`, предупреждения мира. Геометрия при загрузке — из проекта по `roomId + rot + dx + dy`; наполнение выводится заново из адресов (тот же ГСЧ — тот же результат) |
| `expanded` | id раскрытых экземпляров |
| `dead`, `deadWhy` | заколоченные двери `"inst/connector"` и причины (`chance` / `space` / …) |
| `spine` | экземпляры магистрали |
| `rooms` | отпечатки комнат мира: `roomId → "клеток:хэш"` (FNV по отсортированным клеткам и меткам: id, место, сторона, длина, тег, порог) |
| `savedAt` | время |

Загрузка не генерирует ничего заново: комнаты, связи, слои, пространство лучей и PVS восстанавливаются в
том же порядке, поэтому **продолжение после загрузки даёт ровно то же, что без сохранения** (тест: три набора
настроек, прогоны и повторные сохранения совпадают). ГСЧ сохранять не нужно — потоки по адресам.

Если в проекте комната мира изменилась (клетки, метки) или удалена, двери старого мира больше не стоят лицом к
лицу — мир помечается **устаревшим** (`stale = true`), предупреждение «Сохранённый мир устарел: комната
«…» изменена…», сохранение отбрасывается, мир начинается заново с того же сида. Правки, не трогающие
геометрию (лут, споты, отделка), не делают мир устаревшим — наполнение просто выводится по-новому.

Размер: ~320 Б на комнату (3000 комнат — ~1 МБ JSON; save ~0.1–0.2 с, загрузка ~0.7 с с выводом наполнения).

### 15.9. Модификаторы сида (план)

Сейчас `mods` только входят в сид (`hash(seed + "+" + mods)`) — другой модификатор даёт другой мир. Точка
расширения — `applyMods(mods, room, weight)` (вес комнаты при выборе, сейчас возвращает вес как есть). План:
множители весов по тегам («+подвал», «−кухня»), сдвиг `shiftChance` / `deadEndChance` («лабиринт»), запрет
комнат, «тьма» (меньше `sightM`). Модификаторы, меняющие веса, ключ `worldKey` уже различает.

### 15.10. Проверка

`validateFoldRun(project, world.run())` работает и для снимка бесконечного мира: нераскрытые и заколоченные
двери — в `openConnectors`; проверяются слои (нет пересечений в слое), `localRadius` (соседи не
пересекаются), пороги и `dw`, линии обзора по порталам ≤ `sightM` и `Run.sight` против полного скана, PVS —
консервативность лучами (при `seamless` ещё и попарно без пересечений; без бесшовности наложения в PVS
допустимы — их разводит портальный рендер), сводка `fold`. Опция `pvsPoints: 0` — только лучи из проёмов
(для очень больших миров).

### 15.11. Цифры (пресеты, ноутбук разработчика)

«Исследователь» — игрок идёт к случайной нераскрытой комнате кратчайшим путём, в каждой комнате —
`ensureAround` (жёсткий режим: съедает фронт роста); «блуждание» — случайный сосед. Настройки по умолчанию.

| сценарий | шагов | комнат | слоёв | пар в одном месте 3D | тупиков | раскрытие, мс ср / p95 / макс |
|---|---|---|---|---|---|---|
| блуждание | 2000 | 317 | 27 | 1 657 | 17.5 % | 1.2 / 4.6 / 11.5 |
| исследователь | 5 055 | 1 000 | 44 | 11 983 | 20.7 % | 0.3 / 1.3 / 4.3 |
| исследователь | 23 769 | 3 001 | 76 | 51 863 | 20.2 % | 1.4 / 6.1 / 14.4 |
| исследователь + `ensureVisible` (PVS, 9 м — было) | 12 270 | 3 006 | 61 | 40 231 | 20.2 % | 1.0 / 4.1 / 8.3 |
| исследователь + `ensureVisible` (горизонт, 27 м — сейчас) | 10 488 | 3 009 | 70 | 43 364 | 19.4 % | 0.7 / 2.7 / 10.6 |

Раскрытие одного экземпляра (обычно 1–4 новые комнаты) — единицы миллисекунд и на 3000 комнатах (индекс
занятости по слоям — корзины 32 клетки, PVS и линия обзора — только для новой комнаты и нового проёма).
Пересечений в 3D много — 3–17 пар на комнату: это и есть 4D.

Тупики (3 сида × 600 шагов блуждания): `deadEndChance` 0 → 7.2 % дверей (все — «не встало»), 0.15 → 17.3 %,
0.5 → 42.7 %.

### 15.12. Как пользоваться в движке (Влад, Babylon)

- **Вход в комнату** (переход через порог, §9): `world.ensureAround(id); world.ensureVisible(id);` — в том же
  кадре (миллисекунды). Новые экземпляры приходят в `onChange` — строить их меши и коллайдеры там (по
  `inst.id`), а сохранение — с задержкой (раз в несколько секунд), не на каждый шаг.
- **Рендер — порталами** (`src/view3d/portal.ts`, `docs/BLOCKOUT-BABYLON.md` §12): текущая комната обычным
  проходом, комнаты за дверями — только внутри экранной области проёма (стенсил), по связям, пока проём
  виден в кадре, до горизонта `viewHorizonM(sightM)`. Комнаты в кадре могут пересекаться в 3D — портальный
  рендер их разводит. Тумана не нужно (по желанию — атмосфера, §13.6).
- **Двери**: `doorState` — `'dead'` рисовать заколоченной (доски, глухое полотно); `'pending'` встречается
  только у нераскрытых комнат на краю — после `ensureVisible` (на горизонт рендера) такие двери не видны;
  если видна — закрытая.
- **Физика** — коллайдеры текущей комнаты + соседа за порогом, который игрок пересекает (`localRadius = 1`:
  они не пересекаются). Комнаты-соседи за другими дверями между собой пересекаться могут — их коллайдеры не
  включать.
- **Состояние игрока** — текущий `inst.id` и `w` (§8–9); после загрузки — те же id.
- **Сохранение** — `JSON.stringify(world.save())` в localStorage по `worldKey(seed, mods)`; при загрузке
  проверять `world.stale` и показывать `world.warnings`.

### 15.13. Ограничения

- Мир бесконечен по графу, но в 3D ограничен ±16000 клеток (±1.6 км при 0.1 м): у края стыковки наружу
  отвергаются, рост идёт вдоль и внутрь. Случайное блуждание удаляется на ~√N комнат — до края порядка 10⁵
  комнат.
- Раскладка зависит от истории раскрытий (§15.5) — два игрока с одним сидом, ходившие по-разному, получат
  немного разные миры; для общего мира нужен общий сервер мира.
- Петли на пресетах редки (двери должны встать точно лицом к лицу в 3D); на «коробках» с дверями на всех
  сторонах — есть.
- Бесшовность для бесконечного мира непригодна (§15.4); `sightM = 0` — без хранимого PVS (`ensureVisible`
  считает дальний набор на 40 м на месте).
- Время раскрытия медленно растёт с плотностью мира в 3D (больше соседей в корзинах): ~0.3 мс на 1000
  комнатах, ~1–1.5 мс на 3000 (среднее «исследователя»).

### 15.14. Спец-локации и этажи

Подробно — `docs/LOCATIONS.md` §4. Коротко:

- Экземпляр комнаты со спец-локацией (`Room.location`, например «Бесконечная лестница») вниз сам не
  раскрывается: `expand` / `ensureAround` / `ensureVisible` решают только его двери. Переход создаёт
  `descend(id)` — один раз, детерминированно по адресу (поток `root.sub("descent:" + адрес)`): комната-выход
  (площадка/коридор с маршем) на этаже `floor − k`, `k = rollStairwell(spec, locationSeedKey(seedKey, адрес)).floorsDown`
  (тот же розыгрыш отдаёт `locationOf(id)` движку), и связь `{ kind: 'descent', floors: k }` (в `Run.links`
  после дверей; метки у локации нет, у выхода — марш прихода). Выход — ребёнок локации, адрес
  `childAddr(адрес, "@descent")`, начало своей магистрали; дальше мир растёт от него как обычно.
- `Instance.floor` (нет поля — 0) — ещё одно измерение занятости, как W: слой занятости — пара (этаж, W)
  (`layerKey` в `foldcore.ts`; на этаже 0 — просто W, прогоны без переходов бит в бит прежние). Двери этаж не
  меняют, петли между этажами не замыкаются, пересечения в 3D (`overlaps`, `overlapPairs`, `validateFoldRun`)
  считаются внутри этажа. `Run.fold.layers` — число занятых пар (этаж, W).
- Переход — не проём: в пространстве лучей, PVS и соседстве по дверям его нет. Сохранение — с этажами и
  переходами; `validateFoldRun` проверяет переход (из локации, метка прихода есть, этаж = этаж локации − floors).
