# Складчатый (4D) генератор Room Forge

Документ для геймдизайнера и программиста движка (Babylon). Второй генератор раскладки: у комнат нет
общей 3D-физики, квартиры могут занимать одно и то же место в пространстве, а разводит их четвёртая
координата **W** («слой»), которую сдвигают пороги.

Реализация-эталон: `src/gen4d/fold.ts` (`generateFoldRun`, `visibleSet`, `overlapPairs`,
`validateFoldRun`), складчатая стыковка, петли и PVS — `src/gen4d/foldcore.ts` (общие с бесконечным миром),
геометрия — `src/gen4d/space.ts`, лучи обзора по порталам — `src/gen4d/sight4d.ts`,
потенциально видимые наборы — `src/gen4d/pvs.ts`, **бесконечный мир** (генерация на ходу, сохранение) —
`src/gen4d/stream.ts`, §15, квартиры, биомы и переходы — §16, подвал (ходы, хабы, кольца, бесконечные участки) — §17, параметры генераторов «Прогулки» — §18. Всё, что не описано здесь (ГСЧ, геометрия
экземпляра, совместимость меток, пул, ростовые метки, наполнение), — **ровно как у евклидова
генератора**, см. [`docs/GENERATOR.md`](GENERATOR.md); ссылки вида «§4.5 G» ведут туда.

---

## 1. Идея

> Квартиры могут быть в одной точке, проходить через одни места в 3-мерном пространстве. Пороги
> определяют смещение по 4-мерному пространству, благодаря которому это и возможно. Игроки могут
> находиться в одной и той же точке для 3D пространства, но в разных для 4D. Игрок видит только 3D.

- Каждая комната (экземпляр) стоит в 3D как обычно (`rot`, `dx`, `dy`) и дополнительно имеет целую
  координату `w` — номер слоя.
- Каждая связь (порог, дверной проём между двумя метками) имеет сдвиг `dw = w(b) − w(a)`. Обычный
  порог — `dw = 0`; «складка» — `dw ≠ 0`.
- В 3D двери связанных комнат **всегда** совпадают (стоят лицом к лицу через стену толщиной `gap`, как в
  евклидовом генераторе). Игрок проходит дверь и не замечает ничего, кроме того, что за спиной теперь
  другой мир: соседняя по 3D квартира, которую он видел бы через стену, в его новом слое отсутствует —
  её место может занимать совсем другая комната.
- Слой — это обычный план: внутри одного `w` комнаты не пересекаются. Пересекаться в 3D могут только
  комнаты из **разных** слоёв и **далёкие** по графу дверей.

Что получает игрок: бесконечный подъезд, где из коридора можно зайти в три квартиры, занимающие одно и
то же место; лестница, ведущая «вниз», приводит на площадку, стоящую там же, где осталась предыдущая;
тупиковая в обычном мире дверь открывается — за ней комната из другого слоя.

## 2. Гарантии генератора

Термин: две комнаты **пересекаются**, если есть клетка одной и клетка другой на расстоянии Чебышёва
`max(|Δx|, |Δy|) ≤ gap` — то есть стена одной налезла бы на пол другой (при `gap = 0` — просто общие
клетки). Это тот же критерий, что у коллизии евклидова генератора (§4.5 G). Связанные двери стоят ровно
через `gap` клеток стены — связанные комнаты **не** пересекаются.

1. **Слой — плоский план.** В одном слое `w` никакие две комнаты не пересекаются. По слою можно считать
   физику и строить «болванку» (`docs/BLOCKOUT.md`) как для евклидова прогона.
2. **Локальная евклидовость.** Любые две комнаты на расстоянии ≤ `localRadius` по графу связей не
   пересекаются, в каких бы слоях они ни были. Расстояние — по **итоговому** графу (с петлями и
   дозаполнением).
3. **Пороги.** Связанные метки стоят лицом к лицу в 3D точно как в евклидовом генераторе (совместимые
   теги, `facing`, §4.6 G). `|dw| ≤ maxShift`; порог с меткой `'never'` — `dw = 0`; с меткой
   `'always'` — `dw ≠ 0`; все слои `|w| ≤ maxLayer`.
4. **Складки.** Комнаты дальше `localRadius` по графу **могут** пересекаться в 3D — но только из разных
   слоёв. Именно это даёт «квартиры в одной точке». Сколько таких пар — `Run.fold.overlaps`.
5. **Складки не ближе `localM` м пути** (если `FoldSettings.localM > 0`, §18.5). Пересекающиеся комнаты
   дальше друг от друга по ходьбе: путь — через двери связей (и швы `wrap`), внутри комнаты — по прямой
   между серединами её проёмов, сам проём — 0.

Следствие для рендера: **видимое множество** «комната + все комнаты в ≤ `d` дверях от неё» не содержит
пересекающихся пар, если `2·d ≤ localRadius` (любые две комнаты множества — в ≤ `2d` дверях друг от
друга через текущую). По умолчанию `localRadius = 2`, `d = 1`: «где стою + что за дверями».

Проверка всех гарантий независимой реализацией — `validateFoldRun(project, run)` (пустой массив — всё
верно); на пресетах она гоняется в `src/gen4d/fold.test.ts`.

## 3. Параметры

### 3.1. Настройки генератора

`GeneratorSettings.mode = 'fold'` включает складчатый генератор (`generateFoldRun`); `GeneratorSettings.fold`:

| поле | по умолчанию | нормализация | смысл |
|---|---|---|---|
| `shiftChance` | 0.2 | `[0, 1]` | вероятность сдвига на пороге `'auto'`, **даже когда место в слое есть** — «складки по желанию» |
| `maxShift` | 2 | целое `[0, 64]` | максимальный `|dw|` одного порога. 0 — плоский план (см. §9) |
| `localRadius` | 2 | целое `[1, 16]` | радиус локальной евклидовости по графу. 2 — безопасно для рендера «комната + соседи», 4 — «+ соседи соседей» |
| `maxLayer` | 12 | целое `[0, 1000]` | допустимые слои `|w| ≤ maxLayer` |
| `seamless` | true | `false` — выкл. | бесшовная видимость (§14): комнаты одного PVS не пересекаются в 3D; работает только при `sightM > 0` |

Нет поля / мусор — значение по умолчанию (`normFold`). Остальные настройки — как у евклидова: `seed`,
`count`, `gap`, `match`, `startRoomId`, `passId`, `fill` (дозаполнение листьями поддержано) и
`sightM` — предел дальности обзора, но линия обзора считается **по порталам** (§13): сквозь проёмы
связей, независимо от слоёв.

### 3.2. Метка порога `Connector.shift`

| метка | смысл |
|---|---|
| нет поля / `'auto'` | по настройкам: сдвиг с вероятностью `shiftChance`, а если в слое родителя нет места — сдвиг «по нужде» |
| `'always'` | этот проём всегда сдвигает W (например входные двери квартир `landing>apt`: за каждой — своё измерение) |
| `'never'` | обычный порог, `dw = 0` всегда (например лестничные марши — подъезд остаётся цельным) |

Режим порога — по паре меток (у родителя `A` и у ставимой комнаты `B`):

| A \ B | auto | always | never |
|---|---|---|---|
| **auto** | auto | always | never |
| **always** | always | always | ✗ |
| **never** | never | ✗ | never |

✗ — пара несовместима (такую стыковку генератор пропускает); `'always'` при `maxShift = 0` — тоже ✗.
Евклидов генератор поле `shift` игнорирует.

### 3.3. Рецепты для геймдизайнера

- «Каждая квартира — в своём измерении»: `shift: 'always'` на метках `landing>apt` площадок/коридоров.
  На пресетах при count 150 так получается ~11 слоёв, у каждого входа в квартиру `dw ≠ 0`.
- «Подъезд цельный, складываются только квартиры»: `'never'` на `stair` и `corridor`, `'always'` на
  `landing>apt`, `shiftChance = 0`.
- «Почти обычный дом, складки — только где не влезает»: `shiftChance = 0`. Сдвиг будет только у тех
  проёмов, за которыми в своём слое не поместилась ни одна подходящая комната (в евклидовом генераторе
  такой проём стал бы тупиком), а при нехватке ростовых меток — ни одна комната, дающая рост (§4.4).
- Хотите видеть через две двери (`depth 2`) — ставьте `localRadius = 4`. Складок меньше по месту
  (пересечений в ~3 раза меньше), но и «невозможных» соседств меньше.
- «Давящее пространство — дальше 6 м не видно никогда»: `sightM = 6` (§13). Складчатый генератор
  набирает такие карты заметно лучше евклидова.

## 4. Алгоритм (для повторения в движке бит в бит)

### 4.1. Потоки ГСЧ

ГСЧ и производные операции — §1 G. Потоки прогона:

- `root = makeRng(settings.seed)`;
- `L_0 = root.sub("fold-layout")`, `L_k = root.sub("fold-layout:" + k)` — попытки раскладки;
- `F = root.sub("fold-fill")` — дозаполнение листьями;
- `C(i) = root.sub("content:" + inst.id)`, `Fin(i) = root.sub("finish:" + inst.id)` — наполнение и
  отделка экземпляра, **как в евклидовом** (§5 G);
- `root.sub("fold-loops")` зарезервирован за петлями; сейчас замыкание петель ГСЧ не использует.

### 4.2. Подготовка (без ГСЧ)

1. Нормализация настроек — §4.0 G плюс `normFold` (§3.1).
2. Пул, `effMin/effMax/weight` — §4.1 G; при `sightM > 0` комнаты, внутри которых обзор длиннее
   предела, исключаются из пула (§7.3 G, п. 1 — та же внутренняя линия, без проёмов).
3. Ростовые метки `grow`, потенциал `pot`, листовые комнаты `leaf` и листовые метки — §4.2 и §4.7 G
   по этому пулу (в коде — `analyzeGrowth(p, { match, sightM })`).
4. Константы те же: `ATTEMPTS = 6`, `RESERVE = 2`, `RESERVE_STEP = 15`, `RESERVE_MAX = 10`,
   `SUPPLY_FACTOR = 0.5`, `GROW_BONUS = 1`, `LEAF_BONUS = 1`, `LIMIT = 16000`.

### 4.3. Попытки и старт

Как §4.3–4.4 G на потоках `L_k`. Стартовый экземпляр: `rot = 0, dx = dy = 0, w = 0`.

### 4.4. Рост

Список открытых меток, резерв роста, ключ и выбор метки `A`, группы `G1/G2`, ростовой и обычный проходы
— **дословно §4.5 G, шаги 1–4** (центр масс для «роста наружу» — по всем экземплярам всех слоёв).
Отличие — проба кандидатов (шаг 5 G заменяется на «складчатую стыковку» ниже); проверки свободного
фасада нет, предел обзора — по порталам (§13).

**Складчатая стыковка метки `A` родителя `P` (слой `wP`)** — для одного прохода с группами `G1, G2`
и допустимыми метками (`okB` прохода):

*Фаза 1 — свой слой (или разыгранный).* Для группы `G1`, затем `G2`: ленивый взвешенный перебор без
возвращения (`L.weightedIndex`, при −1 → 0 без броска), для комнаты `R` — индексы допустимых меток в
порядке `room.connectors`, `L.shuffle`. Для каждой метки `B` по порядку:

1. `mode = режим(A.shift, B.shift)` по таблице §3.2. ✗ → кандидат пропущен (без ГСЧ, причина «правила»).
2. Поворот, `B'`, цель стыковки, `dx, dy` — §4.5 G, шаг 5. Если bbox кандидата, расширенный на `gap`,
   выходит за `[−16000, 16000]` — пропуск.
3. **Локальная проверка (гарантия 2).** `near` — все экземпляры на расстоянии ≤ `localRadius − 1` по
   текущему графу связей от `P` (включая сам `P`; BFS считается один раз на метку `A`). Если кандидат
   пересекается (§2) хотя бы с одним из них — пропуск. Слой здесь не важен. При `localM > 0` в `near` —
   ещё все экземпляры ближе `localM / cellM` клеток пути от двери `A` (`aroundM`, гарантия 5).
3а. **Предел обзора** (только при `sightM > 0`, §13.3): если через проём будущей связи проходит линия
   длиннее предела — пропуск (причина «обзор»). Слой на линии не влияет, поэтому отказ по обзору —
   повод пробовать следующего кандидата, а не другой `dw`. ГСЧ не используется.
3б. **Бесшовность** (только при `seamless` и `sightM > 0`, §14.4): PVS кандидата по пробной геометрии;
   кандидат не должен пересекаться ни с одной комнатой из PVS(A) для всех A ∈ PVS(кандидата), а сам его
   PVS — попарно без пересечений. Иначе пропуск (причина «бесшовность»); как и обзор, от слоя не зависит.
4. **Порядок сдвигов `order`** (здесь броски ГСЧ, `M = maxShift`):
   ```
   randNZ():  k = L.int(1, 2M);  return k ≤ M ? k : M − k        // +1…+M, затем −1…−M
   first =
     'never'  → 0                                                    (без броска)
     'always' → randNZ()                                             (1 бросок)
     'auto'   → если M > 0 и shiftChance > 0 и L.chance(shiftChance) → randNZ()   (1 или 2 броска)
                иначе 0                                              (при M = 0 или shiftChance = 0 — без броска)
   order = [first]
   если mode ≠ 'never':
     если mode = 'auto' и first ≠ 0 → order += [0]
     для k = 1 … M:  a = (wP ≤ 0 ? +k : −k)     // при равном |dw| — сначала к слою 0
                     если a ≠ first → order += [a];  если −a ≠ first → order += [−a]
   order = те d из order, где |wP + d| ≤ maxLayer
   ```
5. Если `order` не пуст и **слой** `wP + order[0]` свободен (кандидат не пересекается ни с одним
   экземпляром этого слоя) — кандидат ставится в этот слой, стыковка закончена. Иначе кандидат
   запоминается (с его `order`) и перебор продолжается.

*Фаза 2 — складка «по нужде».* Если в фазе 1 никто не встал: запомненные кандидаты **в том же порядке**,
для каждого `order[1], order[2], …` — первый свободный слой. Бросков ГСЧ нет.

Постановка: `w = wP + dw`, `id = "i" + n`, `parent = P`, `depth = P.depth + 1`,
`Link { a: A, b: B, dw }`, метки нового экземпляра (кроме `B`) — в конец открытых. Ничего не подошло —
`A` остаётся тупиком с причиной (нет совместимых / все в max / обзор, если хоть один кандидат отвергнут
пределом обзора / бесшовность, если хоть один отвергнут ею / правила, если все отвергнуты правилами /
иначе нет места).

Порядок при двух проходах (§4.5 G, шаг 4): ростовой проход (фаза 1, фаза 2), затем обычный (фаза 1,
фаза 2) — сложить комнату, дающую рост, лучше, чем закрыть одну из последних ростовых меток листом.
Следствие: при `shiftChance = 0` сдвиг бывает **только** у проёма, за которым ни одна комната прохода
не влезла в слой родителя; «по нужде» карта складывается, а не глохнет.

### 4.5. Замыкание петель (после роста каждой попытки и после дозаполнения)

`free` — несвязанные метки (`len ≥ 1`) в порядке (экземпляр по `order`, метка по индексу). Для `i` по
возрастанию (пропуская связанные) — первое `j > i` другого экземпляра, несвязанное, такое что:

1. метки совместимы (§3 G) и стоят лицом к лицу в 3D (§4.6 G) — **в любых слоях**;
2. `dw = w(b) − w(a)` допустим: `|dw| ≤ maxShift` и правила пары меток (§3.2: `never` → 0, `always` → ≠ 0, ✗ — нет);
3. новая связь не нарушает гарантию 2: `NA` — экземпляры в ≤ `localRadius − 1` от `a` (с расстояниями
   `dA`), `NB` — от `b`; для всех `X ∈ NA, Y ∈ NB, X ≠ Y` с `dA(X) + 1 + dB(Y) ≤ localRadius` — `X` и `Y`
   не пересекаются (это ровно пары, которые новая дверь сводит в радиус);
4. при `sightM > 0` проём петли не открывает линию длиннее предела (§13.3, та же проверка);
5. при бесшовности петля не делает пересекающиеся комнаты взаимно видимыми (§14.4).

Пара связывается `Link { a, b, dw }`. ГСЧ не используется.

### 4.6. Дозаполнение листьями (`fill = true`)

§4.7 G, но на потоке `F = root.sub("fold-fill")` и со складчатой стыковкой §4.4 (фазы 1/2, броски
`F.weightedIndex`, `F.shuffle`, `order` — на `F`). После очереди — замыкание петель §4.5.

### 4.7. Наполнение

§5 G без изменений: для каждого экземпляра в порядке `order` — `rollContent` на `C(i)` (+ отделка на
`Fin(i)`); `dangerAcc` — по дереву роста (`parent`), как в G.

### 4.8. Сводка и диагностика

`Run.fold = { minW, maxW, layers, overlaps, shifted }`: диапазон слоёв (с учётом стартового 0), число
занятых слоёв, число пересекающихся пар (§2, все пары), число связей с `dw ≠ 0`. Если count не набран —
`Run.stop` как в §4.8 G (`sight` — тупики из-за предела обзора; «правила» и «бесшовность» считаются в
`noSpace` и дают отдельные строки). `Run.sight` — полный скан по порталам (§13.2), `Run.pvs` — §14.
Предупреждения: «Складки: слоёв N (W от a до b), порогов со сдвигом W — S из L, пар комнат в одном
месте 3D — O.», обзор, дозаполнение, попытки, min/max — по-русски, движку повторять не нужно.

Реализационные подсказки (на результат не влияют): форма комнаты в повороте и её «раздутая на gap»
битовая карта кэшируются; проверка пары — сначала bbox, расширенные на `gap`, затем клетки меньшей
комнаты против карты большей; экземпляры хранятся по слоям; индекс петель — по линии метки.

## 5. Формат

| где | поле | смысл |
|---|---|---|
| `Instance` | `w` | слой, целое, `|w| ≤ maxLayer`; нет поля — 0 (евклидов прогон) |
| `Link` | `dw` | `w(b) − w(a)`; `a` — родитель или более ранняя метка петли; нет поля — 0 |
| `Run.settings` | `mode: 'fold'`, `fold: FoldSettings` | нормализованные настройки |
| `Run` | `fold: FoldStats` | сводка §4.8 |
| `Run` | `sight` | `{ maxM, line }` — самая длинная линия обзора по порталам (§13.2), считается всегда |
| `Run` | `pvs` | `{ [instId]: instId[] }` — что рендерить, стоя в комнате (§14); только при `seamless` и `sightM > 0` |

Связь двусторонняя: из `a` в `b` слой меняется на `+dw`, из `b` в `a` — на `−dw`. Остальное (клетки,
метки, декор, споты, наполнение) — как в евклидовом прогоне, в мировых 3D-координатах; одна и та же
мировая клетка может принадлежать нескольким экземплярам разных слоёв.

В экспорте `room-forge-run` (`exportRunJSON`) `links[].dw` и `settings.fold` уже есть;
`instances[].w` и сводку `fold` экспорт должен передавать так же (нет поля — 0 / нет сводки).

## 6. Как рендерить

**Есть `Run.pvs` (бесшовность, §14) — рисуем PVS текущей комнаты**, это точнее и без мерцания дверей.
Ниже — запасной вариант для прогонов без PVS.

**Видимое множество — по графу, а не по слою.** Рисуем текущую комнату и комнаты в ≤ `d` дверях от неё:
`visibleSet(run, roomId, d)`. Комнаты своего слоя, до которых далеко по дверям, **не рисуем**: в 3D они
могут стоять там же, где соседи за сдвигающей дверью.

Почему это безопасно: любые две комнаты множества связаны путём ≤ `2d` дверей через текущую; при
`2d ≤ localRadius` они не пересекаются (гарантия 2) — множество выглядит как кусок обычного дома, двери
совпадают с дверями, стены не прорастают в пол. По умолчанию `localRadius = 2` → `d = 1`.

Практика (Babylon):

- Меши и коллайдеры строятся **по экземплярам** (по `inst.id`) и включаются/выключаются
  `setEnabled(true/false)` при смене текущей комнаты. Пул мешей можно держать для «комната + соседи +
  соседи соседей», чтобы переход был без подгрузки.
- Болванка (`docs/BLOCKOUT-BABYLON.md`) рассчитана на плоский план. Для складчатого прогона её строят по
  **видимому подмножеству**: в JSON прогона оставить экземпляры из `visibleSet`, связи с обоими концами
  внутри, у меток со связью наружу — `linkedTo: null`. Пересечений внутри нет — ядро болванки работает
  как есть; двери, ведущие за границу множества, закроются панелью «тупика» — это и есть «дальняя
  дверь закрыта». Результат кэшируется по текущей комнате.
- Дальние двери соседей (ведут в комнаты на расстоянии `d + 1`) рисовать закрытыми, тёмными или с
  «туманом» в проёме. Открытую дверь в комнату, которой нет в множестве, рисовать нельзя — за ней может
  стоять пересекающаяся комната.
- Нужен взгляд через две двери — `localRadius = 4`, `d = 2`.

**Вариант для `localRadius = 1` — порталы со стенсилом.** При `localRadius = 1` гарантировано только
«текущая комната не пересекается ни с одним соседом»; два соседа между собой могут пересекаться. Тогда
каждый сосед рисуется **только сквозь свой проём**:

1. Текущая комната — обычным проходом (цвет + глубина).
2. Квады всех проёмов текущей комнаты: тест и запись глубины, цвет не пишется, стенсил := `k` (номер
   двери). Ближний к камере проём выигрывает пиксель — дальний проём, видный «сквозь» ближний, стенсил
   не перезапишет.
3. Для каждого соседа `k`: очистить глубину (цвет и стенсил не трогать) и нарисовать соседа с тестом
   «стенсил = k». В Babylon: `material.stencil` (`MaterialStencilState`), сосед — в своей rendering
   group, `scene.setRenderingAutoClearDepthStencil(group, true, true, false)` (глубину чистить, стенсил
   нет), `RenderingManager.MAX_RENDERINGGROUPS` поднять под число дверей.
4. Почему пересекающиеся соседи не мешают друг другу: отрезок луча от камеры до проёма `k` лежит внутри
   текущей комнаты, а сосед `k` с ней не пересекается — значит в области портала `k` перед дверью нет
   ничего, кроме текущей комнаты, и всё, что видно сквозь портал, — геометрия соседа `k`. Области
   порталов на экране не перекрываются (шаг 2), так что соседи `j ≠ k` туда не попадут.

Это дороже (по проходу на дверь) и требует порталов для физики (см. §7), поэтому по умолчанию — `localRadius 2`.

## 7. Как считать физику

**Рекомендуется — по видимому множеству.** Коллайдеры текущей комнаты и соседей (то же множество, что
рисуется, или `d = 1` при большем рендере). Пересечений нет — физика ведёт себя как в обычном доме,
проём двери проходим, стены соседей стоят где нарисованы. Игрок за кадр проходит не больше одной двери,
после перехода множество пересчитывается.

**По слою текущей комнаты — не годится в одиночку.** Слой — плоский план без пересечений, но сосед за
сдвигающей дверью лежит в **другом** слое: в своём слое на его месте может стоять чужая комната, игрок
упрётся в её стены у самого проёма. Если физика всё же «по слоям», нужно добавлять соседей за дверями
(и тогда это то же видимое множество).

Предметы, NPC, лут принадлежат экземпляру (`inst.id`): симулируются, только пока их комната в чьём-то
активном множестве; навигация NPC — навмеш по комнатам + связи как переходы с `w += dw`.

---

## 8. Двое игроков в одной точке

Состояние игрока: позиция в 3D + **текущая комната** `roomId` (+ `w` для детекторов). Комнату нельзя
определять по точке в 3D: одну точку могут занимать несколько комнат разных слоёв. Её ведут по переходам
через пороги (§9); на старте — стартовая комната.

- Игрок B **виден** игроку A, если `B.roomId ∈ visibleSet(A.roomId, d)`. То же правило для звука,
  выстрелов, взаимодействия.
- Двое в одной точке 3D, но в пересекающихся комнатах разных слоёв: эти комнаты по гарантиям дальше
  `localRadius ≥ 2d` по графу, значит не входят в видимые множества друг друга — игроки не видят и не
  толкают друг друга, хотя их координаты совпадают.
- Сетевой код: сервер хранит `roomId` каждого, рассылает сущности только из комнат видимого множества
  получателя (interest management по графу, а не по расстоянию).

---

## 9. Переход через порог

Связь `L` — пара меток лицом к лицу; между ними полоса стены толщиной `gap` клеток (проём). Триггер
перехода — объём этой полосы (длина проёма × `gap`, по высоте двери). Игрок, вошедший со стороны `a` и
вышедший со стороны `b`:

```
roomId = L.b.inst
w      = w + L.dw          // со стороны b в a: w − L.dw
```

3D-позиция не меняется: двери совпадают. Видимое множество пересчитывается от новой комнаты; прежняя
комната остаётся в нём (она сосед), так что «за спиной» ничего не пропадает. Пропадают комнаты, которые
стали дальше `d`, — они за закрытыми дальними дверями.

## 10. Детекторы (позже)

Данные уже есть в прогоне, сами детекторы — геймдизайн:

- **Слой** текущей комнаты `w`, разница `|Δw|` до других игроков/объектов: «он рядом, но через 2 слоя».
- **Соседство в 4D** — комнаты, пересекающиеся с текущей в 3D (другие слои того же места):
  `overlapPairs(project, run)` → для комнаты список «кто здесь же в других слоях». Детектор может
  показывать их контуры-призраки, считать их, подсвечивать «за этой стеной в слое +1 кухня».
- **Слои рядом**: комнаты в слоях `w ± 1`, близкие в 3D, — кандидаты на «просачивание» Самосбора.
- Игроки в одной точке 3D и разных `w` — «фантомное присутствие» (шаги, холод), без видимости.

## 12. Ограничения

- `maxShift = 0` (или `maxLayer = 0`) даёт плоский план без пересечений с теми же гарантиями, что у
  евклидова, но без проверки «свободного фасада» (§4.5 G) — он хуже заполняет место (count 300 на
  пресетах — 1/10). Для плоских карт используйте евклидов генератор.
- Складки «по нужде» происходят у каждого проёма, за которым в своём слое ничего не влезло, — поэтому
  даже при `shiftChance = 0` на 30 комнатах бывает несколько сдвигов. Режим «складывать только при
  остановке роста» — возможное развитие.
- `overlaps` считает пары по критерию §2 (с зазором `gap`), а не только общие клетки пола.
- Предел обзора 5 м и меньше пресеты не выдерживают (§13.4): нужны комнаты с короткими входами.
- Бесшовность дорожает и снижает достижимость больших count при жёстком пределе (§14.6).

## 13. Дальность обзора в 4D (`settings.sightM`)

### 13.1. Зачем

Дискомфорт: **неестественно недалеко видно**, будто сами структуры не дают смотреть вдаль. Генератор не
собирает ни одной прямой линии взгляда длиннее `sightM` — ни внутри комнаты, ни сквозь цепочку дверей:
каждая анфилада ломается, за проёмом — стена, тамбур, поворот. В 4D это сильнее, чем в обычном доме:
дом бесконечен и сам себя перекрывает, но взгляд всегда упирается в несколько метров.

### 13.2. Определение — по порталам

Луч всегда находится в **контексте**: комната (экземпляр) или проём связи. Проём — клетки зазора между
двумя связанными метками на пересечении их пролётов (как §7.1 G); при `gap = 0` клеток нет, проём —
ребро между рядом клеток одной комнаты и рядом клеток другой на том же пересечении.

Шаг по стороне из клетки `p` (в контексте `K`) в соседнюю клетку `q`:

| контекст `K` | `q` | новый контекст |
|---|---|---|
| комната | клетка этой комнаты | та же комната |
| комната | клетка проёма одной из **её** связей (gap ≥ 1) | этот проём |
| комната | шаг через ребро её связи (gap = 0) | связанная комната |
| проём | клетка этого проёма | тот же проём |
| проём | клетка одной из двух его комнат | эта комната |
| иначе | — | стена, луч кончился |

Диагональный шаг `(dx, dy)` — только если проходимы **оба** обхода через угловые клетки
(`p → (px+dx, py) → q` и `p → (px, py+dy) → q`) и они приводят в один контекст: сквозь угол смотреть
нельзя. Направления, линия (максимальная цепочка шагов) и длина — как §7.2 G: `n·cellM` по прямой,
`n·cellM·√2` по диагонали; отрезок `Run.sight.line` — «от края до края».

Слой `W` в определении не участвует. Комнаты других слоёв, занимающие те же клетки, **для луча не
существуют** — не удлиняют и не обрывают его; проходимость задаёт только цепочка комнат вдоль луча.
Несвязанные двери — стена. Одну и ту же мировую клетку могут пересекать разные линии из разных цепочек
комнат.

**Полный скан** (`Run.sight`): у каждой максимальной линии ровно одно начало — состояние
(контекст, клетка), из которого шаг назад невозможен. Для каждого направления (порядок §7.2 G), каждого
контекста (комнаты по `order`, затем проёмы по номеру связи) и каждой его клетки (по возрастанию
`(y, x)`), если шаг назад невозможен, — идём вперёд до упора. Побеждает строго большая длина; `maxM`
округлён до 0.001 м. Работа линейна по числу клеток (каждое состояние лежит ровно на одной линии
направления); count 150 — около 15–30 мс.

### 13.3. Ограничение при `sightM > 0`

Пределы в клетках — §7.3 G (`Nорт`, `Nдиаг`).

1. **Пул** — §4.2, п. 2 (комнаты с собственной линией длиннее предела — из пула, предупреждение; если
   такая комната стартовая — ставится всё равно, с предупреждением).
2. **Кандидат** (§4.4, шаг 3а): комната-кандидат и проём будущей связи добавляются на пробу. От каждой
   клетки проёма (при `gap = 0` — от клеток родителя у ребра) по каждому направлению идём назад (в
   родителя и дальше сквозь его проёмы — в любые слои) и вперёд (в кандидата), останавливаясь, как только
   длина превысила предел. Длиннее — кандидат отвергается. Этого достаточно: у кандидата единственная
   связь, значит любая новая линия проходит через её проём.
3. **Петли** (§4.5, п. 4) — та же проверка для проёма петли (обе комнаты уже стоят).

ГСЧ в проверках обзора не используется. Независимая проверка — `validateFoldRun`: свой полный скан по
мировым клеткам (`instanceWorld`) и меткам связей; каждая линия ≤ предела (кроме линий целиком внутри
стартовой комнаты, если она сама длиннее), `Run.sight.maxM` совпадает со сканом.

### 13.4. Помогает ли складывание

Пресеты, 10 сидов `hrush-001…010`, `fill = false`; «набрано» — сколько сидов дали count; пересечения —
среднее число пар комнат в одном месте 3D:

| `sightM` | count | 4D набрано | 4D комнат мин–макс | слоёв | пересечений | евклидов набрано | евклидов мин–макс |
|---|---|---|---|---|---|---|---|
| 0 | 150 | 10/10 | 150 | 8.8 | 303 | 10/10 | 150 |
| 9 | 150 | 10/10 | 150 | 9.7 | 307 | 10/10 | 150 |
| 7 | 60 | 10/10 | 60 | 7.7 | 83 | 6/10 | 16–60 |
| 7 | 150 | 8/10 | 71–150 | 9.2 | 280 | 0/10 | 16–138 |
| 6 | 60 | 9/10 | 46–60 | 7.9 | 61 | 5/10 | 48–60 |
| 6 | 150 | 1/10 | 43–150 | 8.7 | 125 | 0/10 | 58–148 |
| 5 | 30 | 0/10 | 11–20 | 3.3 | 1 | 2/10 | 7–30 |

Да, помогает на 6–7 м. Слой на линии обзора не влияет (луч идёт сквозь слои), так что складка не может
«сломать» длинную линию. Но в евклидовом генераторе кандидата при жёстком пределе отсекают **два**
фильтра — коллизия с уже построенным и обзор, — и вместе они быстро глушат рост. В 4D коллизию снимает
складка (остаётся только локальная — с соседями родителя), и единственным серьёзным фильтром остаётся
обзор. Тупики при 6 м — примерно поровну «обзор» и «нет места» (последнее — соседи родителя по
`localRadius`: ванная, упирающаяся в уже стоящую кухню той же прихожей).

При 5 м не работают оба генератора: из пула уходят 17 комнат (все залы, длинные коридоры), а прямой взгляд
с площадки в квартиру — глубина площадки 2.4–3.5 м + проём + прихожая ≥ 1.8 м — уже длиннее 5 м, так что
квартиры не пристыковываются. Для 5 м нужны свои комнаты: узкие тамбуры и повороты у входов.

### 13.5. Рекомендации

| `sightM` | ощущение |
|---|---|
| 5–7 м | давящее: дальше пары комнат не видно никогда; 6–7 м — рабочий диапазон на пресетах |
| 9 м | умеренное: почти не мешает, длинные анфилады исчезают |
| ≥ 12 м или 0 | не ощущается |

### 13.6. Как поддержать ощущение в движке

- **Давит геометрия, а не затемнение.** Генератор гарантирует, что по прямой (оси, диагонали) дальше `sightM`
  смотреть некуда — взгляд упирается в стену, тамбур, поворот. Портальный рендер (§6,
  `docs/BLOCKOUT-BABYLON.md` §12) показывает всё, что видно, без тумана: даль не темнеет, если место не тёмное
  по смыслу (тёмная лестница — отдельная локация со своим туманом).
- **Туман на `sightM` — по желанию** (атмосфера; в Babylon — `scene.fogMode = Scene.FOGMODE_LINEAR`,
  `fogEnd = sightM`, `fogStart ≈ 0.4·sightM`). Обязателен только при рендере набора PVS одной сценой (§14.5):
  там он прячет край набора.
- **Видимое множество** (§6) — по графу, а не по слоям; луч обзора по определению тоже идёт по графу
  (по порталам), поэтому то, что генератор считает видимым, — ровно то, что движок рисует сквозь двери.
- **Портальный рендер** (§6, стенсил) естественно сужает картинку до проёмов; дальние двери соседей —
  закрытые или тёмные.
- Свет — короткие источники, тёмные проёмы; звук — затухание по числу дверей, а не по метрам.

## 14. Бесшовная видимость (PVS, `fold.seamless`)

### 14.1. Почему мерцало

Рендер «комната + соседи по графу» закрывает двери на краю набора. При переходе через порог набор
меняется: дверь, бывшая краем (закрытой), становится внутренней (открытой), а у новой границы
закрываются другие. Игрок видит, как двери появляются и исчезают. Математика позволяет сделать это
бесшовно: рисовать не «соседей по графу», а всё, что **может быть видно** из комнаты, и гарантировать, что
это множество непротиворечиво в 3D.

### 14.2. Определение

**PVS(A)** — потенциально видимый набор комнаты A: комнаты, в которые из A (из любой точки её пола **и**
клеток её проёмов) можно увидеть хоть что-то по прямой в плане (любого направления, не только 4 оси) сквозь
цепочку проёмов, не дальше `sightM`, независимо от W (портальная логика §13.2). A ∈ PVS(A).

Набор **консервативен** — надмножество настоящей видимости: лишняя комната допустима, пропущенная — нет.
Дальность ограничена `sightM`: при рендере набора одной сценой движок обязан делать туман до полной
непрозрачности к `sightM` (§13.6) — то, что дальше, не видно в любом случае (оси и диагонали генератор и так
не пускает дальше `sightM`, а косые линии отрезает туман). Портальному рендеру туман не нужен: он открывает
проёмы, пока они видны, а бесконечный мир раскрывает комнаты на дальность его горизонта (§15.7).

### 14.3. Гарантия и почему смена набора невидима

**Гарантия:** для каждой комнаты A комнаты PVS(A) попарно не пересекаются в 3D (критерий §2, с зазором `gap`).

- Рендер PVS(A) точен: это кусок обычного дома без наложений, всё, что видно из A, в нём есть.
- Комнаты PVS(A), которые из текущей точки не видны, закрыты стенами видимых комнат (стена, в которую
  упирается луч, принадлежит комнате, до которой луч дошёл, — она видна и нарисована) или туманом.
- **Порог.** Игрок переходит из A в B, текущая комната меняется, когда глаз в проёме связи A–B. Клетки
  проёма входят в источник **обоих** наборов, поэтому всё, что видно из этой точки, лежит в PVS(A) ∩ PVS(B).
  Остальные комнаты каждого набора из этой точки не видны (закрыты стенами или туманом). Значит, кадр из
  точки переключения одинаков с PVS(A) и с PVS(B): смена набора не меняет ни одного пикселя.
- **Двери на краю PVS** (ведут в комнату вне набора) рисуются **открытыми, в темноту** — без заглушки.
  Сквозь такую дверь из текущей комнаты не проходит ни одна прямая (иначе комната за ней была бы в PVS),
  поэтому её проём не виден; а заглушка была бы видна и исчезала бы при смене набора — то самое мерцание.
  Тупики (метки без связи) — обычная стена или дверь-заглушка, одинаковая во всех наборах.

### 14.4. Расчёт (`src/gen4d/pvs.ts`)

Обход цепочек проёмов от A (поиск в глубину по связям; проём в цепочке не повторяется). Цепочка
продолжается через проём, если:

1. проём в пределах `sightM` (евклидово, в плане) от рамки источника — прямая длиной ≤ `sightM` до
   дальнего проёма не дотянется;
2. цепочка «прокалываема»: есть прямая, проходящая источник и все проёмы цепочки в нужную сторону.
   Прямые — `(θ, s)`: направление и смещение вдоль нормали `(−sin θ, cos θ)`. Направления разбиты на
   720 корзин по 0.5°. Для корзины у каждого отрезка интервал смещений `[min, max]` проекций его концов в
   центре корзины, расширенный на `|p − o|·0.25°` (столько проекция может уехать внутри корзины), —
   поэтому, если прямая есть хоть при каком-то угле корзины, проверка её не пропустит. Корзина жива, пока
   пересечение интервалов не пусто и направление идёт через каждый проём в нужную сторону.
   - Источник — выпуклая оболочка клеток A вместе с прямоугольниками всех её проёмов.
   - Проём из A — только дальняя линия (взгляд может начаться внутри проёма); следующие проёмы — обе
     линии (ближняя и дальняя) — прямая проходит проём насквозь.
   - Проёмы удлинены на допуск `0.05 м` с каждой стороны; стены промежуточных комнат и порядок
     пересечения проёмов не учитываются. Всё это только расширяет набор.

Каждая комната, в которую вошла живая цепочка, — в PVS(A).

**В генераторе.** PVS ведётся по экземплярам и только растёт.

- **Кандидат R** (§4.4, шаг 3б) — PVS(R) по пробной геометрии (R и проём). Видимость симметрична, а у R
  единственная связь, поэтому R появится ровно в PVS(A) для A ∈ PVS(R), и других изменений нет: новые
  прямые проходят через новый проём и кончаются в R. Проверка: R не пересекается ни с одной комнатой из
  PVS(A) для всех A ∈ PVS(R); пары внутри PVS(R) проверяются, кроме тех, что обе лежат в PVS(родителя) —
  они уже проверены. После постановки: PVS(R) записан, R добавлен в PVS(A) для A ∈ PVS(R).
- **Петля X–Y** — новые прямые проходят X и Y, значит затронуты комнаты, видящие X или Y:
  `{X, Y} ∪ PVS(X) ∪ PVS(Y)`. Их наборы пересчитываются и объединяются со старыми; новые члены не должны
  пересекаться с остальными, иначе петля не замыкается.
- Отказ — следующий кандидат или поворот, а не другой `dw`: пересечение в 3D от слоя не зависит.

**В валидаторе** (`validateFoldRun`): (1) каждый PVS попарно без пересечений; (2) выборочно —
консервативность: из точек пола каждой комнаты (сетка 0.2 м; по умолчанию 4 точки на комнату,
`{ pvsPoints, pvsRays }` — гуще) и клеток проёмов выпускаются лучи в 180 направлениях; марш по клеткам
(DDA) с портальной логикой до стены или `sightM`; каждая комната, куда луч зашёл, обязана быть в PVS
источника. На пресетах при полной сетке и 240–360 лучах промахов нет; настоящий набор в среднем 6–7
комнат, PVS — 7–8 (запас консервативности ~1.3 комнаты).

### 14.5. Как рендерить в движке

- **Рендер:** меши комнат `run.pvs[текущая комната]` — включить, остальные — выключить. Набор меняется
  на пороге (§9), это невидимо (§14.3).
- **Двери на краю PVS** — открытые, без заглушки; за ними — фон или цвет тумана.
- **Туман:** до полной непрозрачности к `sightM` (§13.6) — обязательная часть гарантии рендера набором
  (у портального рендера тумана нет, `docs/BLOCKOUT-BABYLON.md` §12.3).
- **Физика:** по PVS текущей комнаты (пересечений нет, всё, во что можно упереться рядом, в нём есть)
  или по слою текущей комнаты плюс соседи за сдвигающими дверями (§7). Двое игроков: B виден A, если
  `B.roomId ∈ pvs[A.roomId]` (§8 с PVS вместо видимого множества).
- **Формат:** `Run.pvs: { [instId]: instId[] }` — id экземпляров по возрастанию `order`, включая саму
  комнату; в экспорте `room-forge-run` — поле `pvs` (или `null`).

## 15. Бесконечный мир (`src/gen4d/stream.ts`)

### 15.1. Идея

> Карта бесконечно генерируется, пока мы идём куда-то. Уже прогенерированное пространство сохраняется
> локально, и в него можно вернуться. Всё генерируется на основе сида + модификаторов сида.

Мир не строится целиком. Старт — одна комната. Когда игрок входит в комнату, движок просит мир «раскрыть»
окрестность — сгенерировать комнаты за ещё не открытыми дверями поблизости. Сгенерированное больше не
меняется, сохраняется (`save()` → localStorage) и при возврате восстанавливается как было.

Стыковка, проверки, петли, предел обзора и PVS — **те же, что у складчатого прогона** (общий код —
`foldcore.ts`, §4.4–4.5, §13, §14). Отличаются порядок роста (по дверям, которые открывает игрок), ГСЧ (по
«адресам», §15.5), тупики и гарантия бесконечности (§15.4).

Складки по умолчанию другие, чем у прогона (`DEFAULT_STREAM_FOLD`):

| поле | значение | почему |
|---|---|---|
| `seamless` | **false** | рендер — порталами: комната за дверью рисуется только в экранной области проёма, поэтому комнаты в поле зрения **могут** пересекаться в 3D; бесшовность даёт рендер, а не запрет. PVS всё равно считается — это список того, что обходить порталами |
| `localRadius` | **1** | комната не пересекается со своими соседями — нужно физике на пороге (текущая + соседняя) |
| `shiftChance` | 0.8 | складок много |
| `maxShift` | 4 | шире окно слоёв: при возврате цепочки в плотное место 3D свободный слой находится чаще (§15.4) |
| `maxLayer` | 1000 | слоёв сколько угодно |

Предел обзора `sightM` (по умолчанию 9 м) **действует** — по порталам (§13): структуры не дают смотреть вдаль.

### 15.2. API

```ts
import { createStreamWorld, streamSettings, viewHorizonM, worldKey } from './gen4d/stream';

const key = worldKey(seed, mods);                       // "room-forge/world/<seed>[+mod+mod]"
const saved = localStorage.getItem(key);
const world = createStreamWorld(project, streamSettings(seed, { deadEndChance: 0.2 }), saved ? JSON.parse(saved) : undefined);
if (world.stale) console.warn(world.warnings);          // сохранение не подошло к проекту — мир начат заново

let here = world.startId!;
world.ensureAround(here);                                // при входе в комнату
world.ensureVisible(here);                               // всё, что может попасть в кадр (до viewHorizonM(sightM)), — окончательно
const run = world.run();                                 // Run: instances (w), links (dw), content, pvs, fold, sight
world.onChange((ids) => { buildMeshes(ids); localStorage.setItem(key, JSON.stringify(world.save())); });
```

| метод | что делает |
|---|---|
| `run()` | снимок мира — обычный `Run` складчатого прогона: `instances` (с `w`), `links` (с `dw`), `openConnectors` (заколоченные **и** ещё не раскрытые двери), `content`, `pvs` (при `sightM > 0`), `fold`, `sight`. Кэшируется до следующего изменения; новый снимок — новый объект (экземпляры и связи не меняются никогда) |
| `expand(id)` | раскрыть экземпляр: решить судьбу всех его нераскрытых дверей. Возвращает id новых экземпляров |
| `ensureAround(id, doors = aheadDoors)` | раскрыть всё на расстоянии `< doors` по графу дверей от `id` (BFS), дальше — нет |
| `ensureVisible(id, reachM?)` | раскрыть всё, что видно из `id` сквозь проёмы до дальности `reachM` (по умолчанию `viewHorizonM(sightM)` — горизонт портального рендера), — до замыкания (§15.7). `reachM ≤ sightM` — только PVS(`id`), как раньше |
| `viewHorizonM(sightM)` | горизонт без тумана, м: max(3·`sightM`, 24), при `sightM = 0` — 40 (`src/gen4d/pvs.ts`) |
| `doorState(id, connectorId)` | `'linked'` — проём; `'dead'` — заколоченная дверь (тупик); `'pending'` — ещё не раскрыта |
| `isExpanded(id)`, `addressOf(id)` | раскрыт ли экземпляр; его адрес (§15.5) |
| `stats()` | комнат, раскрыто, нераскрытых дверей (и ростовых), выросло / петель / тупиков по шансу / «не встало», слои, пересечения, время раскрытия (ср / p95 / макс по последним 500) |
| `save()` / `onChange(cb)` | сохранение (§15.8) / подписка на новые экземпляры (возвращает отписку) |
| `warnings`, `stale`, `startId` | предупреждения мира, «сохранение устарело», стартовый экземпляр |
| `locationOf(id)`, `descend(id)`, `exitOf(id)`, `ascend(id, floor, side)`, `liftExitOf(…)` | спец-локации: розыгрыш локации экземпляра; переход на этаж(и) ниже — комната-выход; выход лифта на этаж(и) выше (§15.14) |

Проверка снимка — тот же `validateFoldRun(project, world.run())` (§15.10).

### 15.3. Настройки `StreamSettings`

| поле | по умолчанию | смысл |
|---|---|---|
| `seed`, `mods` | —, `[]` | сид и модификаторы сида (§15.9); ГСЧ мира — `makeRng(seed)` или `makeRng(seed + "+" + mods.join("+"))` |
| `gap`, `match` | 1, `'exact'` | как у генератора |
| `sightM` | 9 | предел обзора по порталам, м (0 — без предела и без PVS) |
| `fold` | `DEFAULT_STREAM_FOLD` | §15.1 |
| `startRoomId` | null | стартовая комната; null — по тегу `start` (вес), иначе по весу |
| `deadEndChance` | 0.15 | вероятность, что дверь при раскрытии окажется **заколоченной**, даже если за ней есть место |
| `branching` | 1 | ветвистость: вес развилки с `k` ходами вперёд × `branching^(k − 1)` (§15.6) |
| `aheadDoors` | 2 | окно `ensureAround` по умолчанию |
| `world` | null | режим квартир: биомы, квартиры с закрытыми выходами, переходы (`WorldSettings`, §16); null — рост §15 |

Нормализация — `normStream` (мусор → умолчания, `deadEndChance ∈ [0, 1]`, `branching ∈ [0, 100]`,
`aheadDoors` — целое `[0, 16]`); `streamSettings(seed, partial)` — полные настройки.

### 15.4. Раскрытие экземпляра (для повторения в движке)

**Двери.** Метка с `len ≥ 1` — дверь. У раскрытого экземпляра каждая дверь либо связана, либо заколочена;
нераскрытые двери бывают только у нераскрытых экземпляров. «Ростовая» дверь — ростовая метка §4.2 G
(за ней может встать комната, продолжающая рост).

**Потоки ГСЧ** (адрес — §15.5): `root = makeRng(seedKey)`; старт — `root.sub("start")`; дверь —
`D = root.sub("door:" + адрес двери)`; магистраль — `root.sub("spine:" + адрес экземпляра)`; наполнение —
`root.sub("content:" + адрес)`, отделка — `root.sub("finish:" + адрес)`.

**Старт:** комната по `startRoomId` / тегу `start` / весу (`root.sub("start").weightedIndex`), `rot = 0,
dx = dy = 0, w = 0`, адрес `0000000000000000`; старт — на магистрали.

**Раскрыть экземпляр P:**

1. Если P на **магистрали** — сначала её продолжение: нераскрытые ростовые двери P в порядке
   `room.connectors`, повёрнутом на `off = root.sub("spine:" + адрес P).int(0, k − 1)` (при `k = 1` — без
   броска). По очереди — «дверь магистрали» (ниже), пока за одной не встанет комната с нераскрытой ростовой
   дверью: она становится магистралью.
2. Остальные нераскрытые двери P — по порядку `room.connectors`, «обычная дверь».
3. Если в мире не осталось ни одной нераскрытой ростовой двери — крайняя мера (§15.4, «Бесконечность»).

**Дверь A экземпляра P:**

1. `roll = D.next() < deadEndChance` — бросок **всегда** (поток роста от статуса двери не зависит).
   `reserve` = дверь ростовая и нераскрытых ростовых дверей в мире (включая эту) `≤ STREAM_RESERVE = 10`.
2. Обычная дверь: `roll` и не `reserve` → **заколочена** («по шансу»). Иначе — **петля**: если напротив A в 3D
   (любой слой) стоит нераскрытая дверь другого экземпляра и связь проходит проверки §4.5 (совместимость, лицом
   к лицу, правила порогов, гарантия 2, обзор, бесшовность), — связать. Кандидатов несколько — в каноническом
   порядке (глубина, адрес, индекс метки). Без ГСЧ. У двери магистрали шаг 2 пропускается.
3. **Складчатая стыковка** §4.4 на потоке D со следующими отличиями:
   - кандидаты — все комнаты пула с весом > 0, совместимые с A, одной группой (min в бесконечном мире
     смысла не имеет);
   - вес — `weight × branchMul(grow, branching) × applyMods(...)`;
   - комната, которую сейчас ставить нельзя (`unique` уже стоит; `max` в окрестности — §15.6), **остаётся в
     списке весов**: выпала — пропускается без бросков. Так выбор остальных комнат не зависит от того, где
     уникальная уже встала;
   - **«комната важнее слоя»**: кандидат, прошедший проверки, сразу пробует весь свой порядок `dw` (фаза 2
     §4.4 не откладывается). Выбор комнаты не зависит от занятости слоёв — от неё зависит только `W`;
   - у двери магистрали и при `reserve` — сначала проход только комнат, дающих рост (`growOthers > 0`), затем
     обычный (как ростовой проход §4.5 G).
4. Ничего не встало — дверь заколочена с причиной (`space` / `sight` / `seam` / `rule` / `max` / `nomatch`).

Новый экземпляр: `id = "i" + n` (n — номер постановки), `parent`, `depth`, `w`; связь `parent → ребёнок`
с `dw`; PVS (§14.4, без бесшовности — по поставленной геометрии; затем симметрично в наборы видимых);
наполнение — §4.7 на потоках адреса, `dangerAcc` — по родителю.

**Бесконечность.** Гарантия: у мира всегда есть нераскрытая ростовая дверь, а всё сгенерированное связно —
до неё можно дойти.

- **Магистраль** — одна линия роста от старта, выбранная по адресам: её двери не заколачиваются по шансу и
  сначала пробуют комнаты, дающие рост. Пока магистраль продолжается, мир бесконечен независимо от тупиков.
  Если ни одна ростовая дверь её комнаты не дала роста (нет места / обзор), магистраль переходит к первой
  новой комнате с ростовой дверью, поставленной где угодно.
- **Резерв роста** (как в генераторе, `RESERVE_MAX`): пока нераскрытых ростовых дверей ≤ 10, ростовые двери
  не заколачиваются по шансу и сначала пробуют рост. На пресетах держит фронт на ~10 дверях.
- **Крайняя мера**: если после раскрытия нераскрытых ростовых дверей не осталось (подряд отказали все — так
  бывает, когда цепочка возвращается в место 3D, где заняты все слои `w ± maxShift`), «расколачивается»
  заколоченная по шансу ростовая дверь — самая глубокая (при равной — с большим адресом); её экземпляр снова
  нераскрыт и становится магистралью. Предупреждение в `warnings`.
- Мир может кончиться, только если все ростовые двери отказали по месту или обзору, а заколоченных по шансу
  нет (`deadEndChance = 0` или их не было) — тогда сводка говорит «Мир заглох». На пресетах ни разу
  (6 сидов × 4000 комнат «пожирающим фронт» игроком, §15.11).
- **Бесшовность** (`fold.seamless = true`) поддержана с теми же гарантиями, что у прогона, но бесконечному миру
  она вредит: на пресетах мир глохнет на ~40 комнатах (бесшовность отвергает много стыковок, а фронт роста
  мал). Для потокового мира — портальный рендер и `seamless: false`.

### 15.5. Детерминизм и адреса

**Адрес** экземпляра — 64-битный хэш пути дверей от старта:

```
addr(старт)   = "0000000000000000"
addr(ребёнок) = childAddr(addr(родитель), id метки родителя, через которую он поставлен)
childAddr(p, c) = hex8(FNV1a32(p + "/" + c)) + hex8(FNV1a32(c + "\" + p))
```

Адрес двери — адрес комнаты, которая за ней встанет. Все броски, относящиеся к двери, — на её потоке
`root.sub("door:" + адрес)`, наполнение и отделка — на потоках адреса экземпляра. Поэтому:

- **Наполнение** (тир, споты, лут, отделка) комнаты по адресу **не зависит** от порядка, в котором игрок ходил:
  если по тому же пути стоит та же комната, у неё то же наполнение (тест: 0 расхождений).
- **Раскладка** может зависеть от истории раскрытий — это нормально, мир сохраняется. Что может зависеть:
  занятость слоёв (меняет `W`, не комнату), уникальные комнаты (кто первый), резерв роста (сколько ростовых
  дверей открыто во всём мире), петли (существует ли уже дверь напротив), линии обзора сквозь соседей
  соседей. Не зависит: всё остальное — броски по адресам, окно `max` (§15.6), порядок дверей экземпляра.
- **Каноническая очередь**: `ensureAround` раскрывает нераскрытые экземпляры окна по одному — каждый раз
  минимальный по (глубина от старта, адрес), окно пересчитывается после каждого раскрытия; `ensureVisible` —
  так же по PVS. Два разных маршрута к одному месту чаще дают одно и то же.

Замер (тест «две разные истории»: два игрока-блуждателя по 150 шагов, в мире A сначала ходит первый, в мире B
— второй; 6 сидов): общих адресов 812, **постановка** (комната, поворот, место) совпала в **98.6 %**, из них
сдвиг порога `dw` — в 94.6 %; наполнение при совпавшей постановке — 100 %. Абсолютный `W` совпадает реже: одно
расхождение слоя сдвигает `W` всего поддерева (`w = w(родителя) + dw`), игроку это не видно.

Что улучшило совпадение (было 85 %): потоки ГСЧ по адресам дверей; запрещённые комнаты остаются в списке
весов; «комната важнее слоя»; магистраль вместо частого переключения резерва.

### 15.6. Тупики, ветвистость, max / unique / min

- **`deadEndChance`** — доля дверей, заколоченных по шансу (кроме магистрали и резерва). Плюс тупики «не
  встало» (~7 % дверей на пресетах). Замер — §15.11.
- **`branching`** — `branchMul`: развилка с `k` ходами вперёд (ростовых меток кроме входной) получает вес ×
  `branching^(k − 1)`: коридор (2 ростовые) — ×1, T (3) — ×`branching`, крест (4) — ×`branching²`. Множитель
  «всем хабам» ничего бы не дал: с одной дверью совместимы комнаты одного рода (за дверью коридора — только
  коридоры), важна доля развилок среди них. Пресеты, доля развилок среди поставленных хабов: `branching`
  0.25 → 0.14, 1 → 0.36, 4 → 0.67.
- **`unique`** — один раз на мир.
- **`max`** — «не больше `max` копий в окрестности пути»: окрестность — `MAX_WINDOW = 10` предков по дереву
  роста (включая саму комнату) и все их дети. Буквально «не больше `max` в мире» убил бы бесконечность (у
  площадок и коридоров пресетов `max = 99`: после сотни площадок рост встал бы), а окрестность пути
  существует целиком к моменту раскрытия при любом порядке ходьбы — правило не зависит от истории. Смысл для
  дизайнера: «на пути игрока такая комната встречается не чаще `max` раз на ~10 дверей».
- **`min`** не применяется: у бесконечного мира нет конца, к которому его выполнять.

### 15.7. Сколько раскрывать: `aheadDoors` и `ensureVisible`

- **Физика** — текущая комната + соседи за порогами: они существуют после `expand(текущей)`. `aheadDoors = 2`
  (по умолчанию) раскрывает и соседей — шагнув через порог, игрок уже окружён готовыми комнатами.
- **Рендер** — PVS текущей комнаты. Комната, которая могла бы быть видна, но ещё не сгенерирована, при
  генерации «появится» в кадре. PVS дотягивается далеко по дверям (пресеты, 9 м — глубина PVS в дверях:
  2 — 18 %, 3 — 33 %, 4 — 33 %, 5 — 13 %, 6 — 4 %), поэтому рекомендация «`aheadDoors` ≥ глубины PVS» означает
  5–6 дверей и много лишнего.
- **Точнее — `ensureVisible(id)`**: раскрыть все комнаты, которые видны из комнаты, пока среди них есть
  нераскрытые. После этого всё, что видно из комнаты (и из её проёмов), окончательно: каждая линия взгляда
  идёт по видимым комнатам, а у раскрытых комнат все двери либо ведут в комнату (она тоже видна —
  консервативность), либо заколочены. В момент входа в комнату B из A взгляд — из проёма A–B, а он входит в
  источник набора A, который уже был замкнут, — новые комнаты в кадр не попадают.
- **Дальность — горизонт рендера, а не `sightM`.** Генератор не пускает дальше `sightM` прямые по осям и
  диагоналям, но косая линия сквозь цепочку дверей бывает длиннее. Раньше её край прятал обязательный туман
  на `sightM`; портальный рендер теперь без тумана открывает проёмы, пока они видны, до горизонта
  `viewHorizonM(sightM)` = max(3·`sightM`, 24 м) (без предела обзора — 40 м; `docs/BLOCKOUT-BABYLON.md` §12.3).
  Поэтому `ensureVisible(id, reachM = viewHorizonM(sightM))`:
  1. PVS(`id`) (`Run.pvs`, дальность `sightM`) — как раньше: каждый раз нераскрытый экземпляр, минимальный по
     (глубина, адрес), и так, пока такие есть;
  2. если `reachM` больше `sightM` — «дальний» набор: `computePvs` (§14.4, та же логика: цепочки проёмов,
     прокалываемые прямой, допуск 5 см) с дальностью `reachM` от комнаты **по текущей геометрии мира** (он не
     хранится — считается на месте, ≈ 0.3 мс); все его нераскрытые экземпляры раскрываются в каноническом
     порядке, затем набор пересчитывается (раскрытые добавили проёмы); снова п. 1 — до замыкания.

  Если сквозь проём в кадре видно хоть что-то, туда дошла прямая из глаза сквозь всю цепочку проёмов, а все
  они ближе горизонта (дальше рендер проёмы комнаты не открывает) — значит комната за ним в дальнем наборе
  (глаз — внутри источника, расстояние от рамки источника не больше расстояния от глаза), и она раскрыта:
  нераскрытых дверей (проёмов в пустоту) в кадре нет. Замкнутость устойчива: позже раскрытые где-то ещё комнаты не видны из этой (иначе были бы в наборе), а
  петля к её видимой комнате не может появиться — у раскрытой комнаты нет нераскрытых дверей.

  Цена (пресеты, `sightM` 9 → дальность 27 м, блуждание 200 шагов, 3 сида): дальний набор в среднем
  11–13 комнат (PVS — 7–8), максимум 25–38; комнат в мире на тех же шагах — на 1–8 % больше; `ensureVisible`
  0.6–1.0 мс в среднем, p95 ≤ 4 мс, максимум 15–41 мс (раскрытие сразу нескольких комнат).

Рекомендация движку: при входе в комнату — `ensureAround(id)` (`aheadDoors = 2`) **и** `ensureVisible(id)`
(по умолчанию — на горизонт рендера). Без предела обзора (`sightM = 0`) хранимого PVS нет, но
`ensureVisible` работает (дальний набор на 40 м). `ensureVisible(id, sightM)` — прежнее поведение (только
PVS; тогда рендеру нужен туман на `sightM`).

### 15.8. Сохранение

`save()` → `StreamSave` (`format: 'room-forge-world', version: 1`), ключ localStorage — `worldKey(seed, mods)`:

| поле | что |
|---|---|
| `settings` | нормализованные настройки (при загрузке берутся отсюда, а не из аргумента) |
| `run` | снимок `Run` **без клеток и без наполнения**: экземпляры (`roomId, rot, dx, dy, w, parent, depth`), связи (`dw`), `pvs`, `sight`, `fold`, предупреждения мира. Геометрия при загрузке — из проекта по `roomId + rot + dx + dy`; наполнение выводится заново из адресов (тот же ГСЧ — тот же результат) |
| `expanded` | id раскрытых экземпляров |
| `dead`, `deadWhy` | заколоченные двери `"inst/connector"` и причины (`chance` / `space` / …) |
| `spine` | экземпляры магистрали |
| `rooms` | отпечатки комнат мира: `roomId → "клеток:хэш"` (FNV по отсортированным клеткам и меткам: id, место, сторона, длина, тег, порог) |
| `savedAt` | время |

Загрузка не генерирует ничего заново: комнаты, связи, слои, пространство лучей и PVS восстанавливаются в
том же порядке, поэтому **продолжение после загрузки даёт ровно то же, что без сохранения** (тест: три набора
настроек, прогоны и повторные сохранения совпадают). ГСЧ сохранять не нужно — потоки по адресам.

Если в проекте комната мира изменилась (клетки, метки) или удалена, двери старого мира больше не стоят лицом к
лицу — мир помечается **устаревшим** (`stale = true`), предупреждение «Сохранённый мир устарел: комната
«…» изменена…», сохранение отбрасывается, мир начинается заново с того же сида. Правки, не трогающие
геометрию (лут, споты, отделка), не делают мир устаревшим — наполнение просто выводится по-новому.

Размер: ~320 Б на комнату (3000 комнат — ~1 МБ JSON; save ~0.1–0.2 с, загрузка ~0.7 с с выводом наполнения).

### 15.9. Модификаторы сида (план)

Сейчас `mods` только входят в сид (`hash(seed + "+" + mods)`) — другой модификатор даёт другой мир. Точка
расширения — `applyMods(mods, room, weight)` (вес комнаты при выборе, сейчас возвращает вес как есть). План:
множители весов по тегам («+подвал», «−кухня»), сдвиг `shiftChance` / `deadEndChance` («лабиринт»), запрет
комнат, «тьма» (меньше `sightM`). Модификаторы, меняющие веса, ключ `worldKey` уже различает.

### 15.10. Проверка

`validateFoldRun(project, world.run())` работает и для снимка бесконечного мира: нераскрытые и заколоченные
двери — в `openConnectors`; проверяются слои (нет пересечений в слое), `localRadius` (соседи не
пересекаются), пороги и `dw`, линии обзора по порталам ≤ `sightM` и `Run.sight` против полного скана, PVS —
консервативность лучами (при `seamless` ещё и попарно без пересечений; без бесшовности наложения в PVS
допустимы — их разводит портальный рендер), сводка `fold`. Опция `pvsPoints: 0` — только лучи из проёмов
(для очень больших миров).

### 15.11. Цифры (пресеты, ноутбук разработчика)

«Исследователь» — игрок идёт к случайной нераскрытой комнате кратчайшим путём, в каждой комнате —
`ensureAround` (жёсткий режим: съедает фронт роста); «блуждание» — случайный сосед. Настройки по умолчанию.

| сценарий | шагов | комнат | слоёв | пар в одном месте 3D | тупиков | раскрытие, мс ср / p95 / макс |
|---|---|---|---|---|---|---|
| блуждание | 2000 | 317 | 27 | 1 657 | 17.5 % | 1.2 / 4.6 / 11.5 |
| исследователь | 5 055 | 1 000 | 44 | 11 983 | 20.7 % | 0.3 / 1.3 / 4.3 |
| исследователь | 23 769 | 3 001 | 76 | 51 863 | 20.2 % | 1.4 / 6.1 / 14.4 |
| исследователь + `ensureVisible` (PVS, 9 м — было) | 12 270 | 3 006 | 61 | 40 231 | 20.2 % | 1.0 / 4.1 / 8.3 |
| исследователь + `ensureVisible` (горизонт, 27 м — сейчас) | 10 488 | 3 009 | 70 | 43 364 | 19.4 % | 0.7 / 2.7 / 10.6 |

Раскрытие одного экземпляра (обычно 1–4 новые комнаты) — единицы миллисекунд и на 3000 комнатах (индекс
занятости по слоям — корзины 32 клетки, PVS и линия обзора — только для новой комнаты и нового проёма).
Пересечений в 3D много — 3–17 пар на комнату: это и есть 4D.

Тупики (3 сида × 600 шагов блуждания): `deadEndChance` 0 → 7.2 % дверей (все — «не встало»), 0.15 → 17.3 %,
0.5 → 42.7 %.

### 15.12. Как пользоваться в движке (Влад, Babylon)

- **Вход в комнату** (переход через порог, §9): `world.ensureAround(id); world.ensureVisible(id);` — в том же
  кадре (миллисекунды). Новые экземпляры приходят в `onChange` — строить их меши и коллайдеры там (по
  `inst.id`), а сохранение — с задержкой (раз в несколько секунд), не на каждый шаг.
- **Рендер — порталами** (`src/view3d/portal.ts`, `docs/BLOCKOUT-BABYLON.md` §12): текущая комната обычным
  проходом, комнаты за дверями — только внутри экранной области проёма (стенсил), по связям, пока проём
  виден в кадре, до горизонта `viewHorizonM(sightM)`. Комнаты в кадре могут пересекаться в 3D — портальный
  рендер их разводит. Тумана не нужно (по желанию — атмосфера, §13.6).
- **Двери**: `doorState` — `'dead'` рисовать заколоченной (доски, глухое полотно); `'pending'` встречается
  только у нераскрытых комнат на краю — после `ensureVisible` (на горизонт рендера) такие двери не видны;
  если видна — закрытая.
- **Физика** — коллайдеры текущей комнаты + соседа за порогом, который игрок пересекает (`localRadius = 1`:
  они не пересекаются). Комнаты-соседи за другими дверями между собой пересекаться могут — их коллайдеры не
  включать.
- **Состояние игрока** — текущий `inst.id` и `w` (§8–9); после загрузки — те же id.
- **Сохранение** — `JSON.stringify(world.save())` в localStorage по `worldKey(seed, mods)`; при загрузке
  проверять `world.stale` и показывать `world.warnings`.

### 15.13. Ограничения

- Мир бесконечен по графу, но в 3D ограничен ±16000 клеток (±1.6 км при 0.1 м): у края стыковки наружу
  отвергаются, рост идёт вдоль и внутрь. Случайное блуждание удаляется на ~√N комнат — до края порядка 10⁵
  комнат.
- Раскладка зависит от истории раскрытий (§15.5) — два игрока с одним сидом, ходившие по-разному, получат
  немного разные миры; для общего мира нужен общий сервер мира.
- Петли на пресетах редки (двери должны встать точно лицом к лицу в 3D); на «коробках» с дверями на всех
  сторонах — есть.
- Бесшовность для бесконечного мира непригодна (§15.4); `sightM = 0` — без хранимого PVS (`ensureVisible`
  считает дальний набор на 40 м на месте).
- Время раскрытия медленно растёт с плотностью мира в 3D (больше соседей в корзинах): ~0.3 мс на 1000
  комнатах, ~1–1.5 мс на 3000 (среднее «исследователя»).

### 15.14. Спец-локации и этажи

Подробно — `docs/LOCATIONS.md` §4 (лестница, вниз) и §10 (лифт, вверх: `ascend(id, floor, side)` — связь
`{ kind: 'lift', floors, side }`, комната пристыкована к стене шахты на этаже `floor(лифта) + floor`; всё остальное —
как у `descend`). Коротко:

- Экземпляр комнаты со спец-локацией (`Room.location`, например «Бесконечная лестница») вниз сам не
  раскрывается: `expand` / `ensureAround` / `ensureVisible` решают только его двери. Переход создаёт
  `descend(id)` — один раз, детерминированно по адресу (поток `root.sub("descent:" + адрес)`): комната-выход
  (площадка/коридор с маршем) на этаже `floor − k`, `k = rollStairwell(spec, locationSeedKey(seedKey, адрес)).floorsDown`
  (тот же розыгрыш отдаёт `locationOf(id)` движку), и связь `{ kind: 'descent', floors: k }` (в `Run.links`
  после дверей; метки у локации нет, у выхода — марш прихода). Выход — ребёнок локации, адрес
  `childAddr(адрес, "@descent")`, начало своей магистрали; дальше мир растёт от него как обычно.
- `Instance.floor` (нет поля — 0) — ещё одно измерение занятости, как W: слой занятости — пара (этаж, W)
  (`layerKey` в `foldcore.ts`; на этаже 0 — просто W, прогоны без переходов бит в бит прежние). Двери этаж не
  меняют, петли между этажами не замыкаются, пересечения в 3D (`overlaps`, `overlapPairs`, `validateFoldRun`)
  считаются внутри этажа. `Run.fold.layers` — число занятых пар (этаж, W).
- Переход — не проём: в пространстве лучей, PVS и соседстве по дверям его нет. Сохранение — с этажами и
  переходами; `validateFoldRun` проверяет переход (из локации, метка прихода есть, этаж = этаж локации − floors).

## 16. Квартиры, биомы, переходы (режим квартир бесконечного мира)

Реализация — `src/gen4d/stream.ts` (режим включён, когда `StreamSettings.world ≠ null`), биомы и формулы —
`src/gen4d/biomes.ts`, настройки — `Project.world` (страница «Генератор» в режиме 4D → секция «Бесконечный мир»),
3D — «Прогулка» с галочкой «Квартиры, биомы и переходы» (`WalkOptions.clusters`, по умолчанию включена). Без режима
(`world: null`) мир растёт как в §15 — бит в бит прежний.

### 16.1. Для геймдизайнера: правило

> Мир делится на биомы. Мир растёт **квартирами** (кластерами комнат): в квартире до 15 комнат и от 2 до 10 закрытых
> дверей-выходов. Игрок открывает выход (E) — за ним новая квартира, **все неоткрытые выходы старой квартиры
> исчезают** (становятся стенами); через открытую дверь можно вернуться.
>
> **Переход** — спец-комната (лестница, лифт). Пока игрок не прошёл 50 комнат (впервые, спец-комнаты не в счёт),
> переходов нет. Каждая следующая новая комната даёт шанс 10%, следующая — 11%, 12%… Выпал — переход стоит **прямо за
> следующей дверью, которую игрок откроет** (шанс 100%). Не зашёл в него и ушёл через другой выход — переход исчезает.
> Прошёл через переход — счёт с нуля. Переход ведёт в квартиру **другого биома** или в **богатую квартиру**.

Все числа — настройки (`WorldSettings`):

| поле | по умолчанию | смысл |
|---|---|---|
| `clusterRooms` | [6, 15] | комнат в квартире, мин–макс (предел 15) |
| `clusterExits` | [2, 10] | закрытых выходов квартиры, мин–макс (1…10) |
| `trAfter` | 50 | сколько комнат пройти без шанса перехода |
| `trBase` | 0.1 | шанс для первой комнаты после порога |
| `trStep` | 0.01 | прибавка за каждую следующую комнату |
| `trToBiome` | 0.7 | доля переходов в другой обычный биом; остальные — в богатую квартиру |
| `trLanding` | 0.4 | доля переходов — лестничная площадка (все её двери — в биом назначения, §19.4); остальные — спец-комнаты |
| `richBoost` | 8 | множитель весов тиров элитности ≥ 2 в богатой квартире (как `tierBoost` проходки) |
| `biomes` | 5 пресетов | §16.2 |
| `startBiome` | `khrush` | стартовый биом; null — первый обычный |

Шанс перехода для `k`-й пройденной комнаты (`transitionChance`):
`p(k) = 0` при `k ≤ trAfter`, иначе `min(1, trBase + trStep · (k − trAfter − 1))`. Бросок — свой поток
`makeRng(seedKey + "#tr:" + resets + ":" + k)` (детерминированно по сиду, числу сбросов и номеру комнаты).

### 16.2. Биомы

Биом — **набор комнат по тегам**: вес комнаты в биоме = вес роста × наибольший множитель среди её тегов (`biomeMul`);
ни одного тега из списка — комната в биоме не растёт. Спец-комнаты (`Room.location`) в квартирах не растут никогда —
они только переходы.

| id | биом | основные теги (×) |
|---|---|---|
| `khrush` | Хрущёвки | лестница, прихожая, кухня, санузел, жилая, балкон, кладовка ×1; лифт ×0.4; коридор ×0.3 |
| `malosem` | Малосемейки | коридор ×2, лифт ×1, служебное ×1, прихожая/санузел ×0.8, жилая ×0.7 |
| `dorm` | Общежитие | общежитие ×3, служебное ×1, коридор ×0.5 |
| `basement` | Подвал | подвал ×3, кладовка ×1, служебное ×0.6 |
| `barn` | Сарай | сарай ×1 — сеть проходов из своих комнат (§19) |
| `snow` | Снежные тоннели | снег ×1 — сеть лазов из своих комнат, выход — подтаявшая берлога (§20) |
| `factory` | Завод | завод ×1 — сеть цехов с влажностью: «иди туда, где влажнее» — болото и финал игры (§21) |
| `rich` ★ | Богатая квартира | жилая ×1.5, прихожая/кухня/санузел/балкон/кладовка ×1 (`rich: true`) |

Богатый биом (`rich`) — не старт и не «другой биом»: в него попадают только переходом. Наполнение богатой квартиры —
с проходкой `@rich` (`tierBoost = richBoost`), т. е. элитные варианты в ней выпадают чаще. Её выходы ведут в обычные
квартиры **того биома, откуда игрок пришёл** (`Cluster.home`).

### 16.3. Рост квартиры (`fillCluster`)

Квартира растёт от входной комнаты (за открытой дверью, комната-выход перехода или старт). Поток квартиры
`C = root.sub("cluster:" + адрес входа)`: `N = C.int(clusterRooms)`, `K = C.int(clusterExits)`.

1. Открытые двери комнат квартиры — две очереди по порядку постановки: **внутренние** и **наружные**. Наружные — метки с
   тегами `OUTER_TAGS` = `landing>apt`, `apt>landing`, `corridor`, `stair`, `basement` (входная дверь квартиры,
   коридоры и площадки, марши, подвальные ходы); остальные — внутренние (прихожая → кухня, комната → балкон…).
2. Берётся дверь: сначала внутренние (квартира достраивается), наружные — когда внутренних нет. Петля к двери своей
   квартиры напротив — связать; иначе обычная складчатая стыковка (§15.4) из **пула биома** на потоке двери
   `root.sub("door:" + адрес двери)`. У наружной двери, когда наружных впереди меньше `K + 1`, — сначала комнаты, дающие
   рост. Не встало — дверь глухая.
   **Запас под выходы:** если открытых дверей в очередях (с текущей) не больше `K`, за дверью встаёт только комната, у
   которой есть ещё дверь (проходная), и петля не замыкается; не встало — дверь остаётся под выход. Так квартира держит
   ~`K` выходов и меньше тупиковых комнат: чем больше `K`, тем чаще дверь прихожей ведёт в другую квартиру, а не в
   кухню или санузел (на пресетах: тупиковых комнат 2.5 из 7 вместо 3.8, выходов 6.9 вместо 3.3, квартир всего с двумя выходами — 4% вместо
   60%). Дверь, за которой не встанет ни одна совместимая комната (смотрит внутрь своей же комнаты — внутренний угол
   Г-образной прихожей), — стена, не выход. Иначе замкнутая квартира (все двери связаны) осталась бы без выходов.
3. Набрали `N` комнат (или двери кончились) — **все оставшиеся двери квартиры — закрытые выходы**, не больше
   `clusterExits[1]`: сначала наружные (`C.shuffle`), затем неиспользованные внутренние от входа; стены — только сверх
   предела (иначе квартира — сплошные тупики: кухни, санузлы и стены).
4. Двери, за которыми комната уже не встала (место, обзор), — выходами только до минимума `clusterExits[0]`: при
   открытии за ними скорее всего снова ничего не встанет. Порядок — от входа (сначала наружные неиспользованные,
   затем наружные, где не встало, затем так же внутренние): квартира без выходов остановила бы мир.
5. Все комнаты квартиры раскрыты: `ensureAround` / `ensureVisible` в режиме квартир ничего не растят — мир растёт только
   открытием дверей.

### 16.4. Открытие двери (`openDoor(inst, connector)`)

- Дверь должна быть закрытым выходом (`doorState = 'exit'`), иначе исключение.
- **Выпал переход** (`pending`) — за этой дверью встаёт спец-комната перехода (§16.5); игрок квартиру не покинул:
  остальные выходы на месте. Возвращает id перехода.
- Иначе за дверью — входная комната новой квартиры биома `home` текущей (у богатой — биом, откуда пришли). Вход — с
  запасом дверей, по порядку попыток (`m = clusterExits[0]`, «дверей» — кроме двери стыковки):
  1. по меткам, из биома, дверей ≥ `m + 2`; 2. **любой своей дверью** (4D-шов, связь `loose`), из биома, ≥ `m + 2`;
  3–4. то же с ≥ `m`; 5–6. то же из всех комнат; 7–9. по меткам с ≥ 1 (биом, затем все), из биома — любая; 10. любая.
  Зачем шов: выходы квартиры, в которую вошли через входную дверь, — её внутренние двери (прихожая → комната), а по
  меткам за ними встают только комнаты-тупики; через шов за такой дверью оказывается прихожая, площадка или коридор
  другой квартиры (на пресетах — около половины открытых дверей). Совсем не встало — дверь глухая, `null`.
- Встало: новая квартира растёт (§16.3); если переход выпал, но за дверью не встал, — он ставится в новую квартиру
  ближе ко входу. Затем **остальные закрытые выходы старой квартиры исчезают** (`'vanished'`), пропущенный переход
  старой квартиры исчезает (§16.6). Новая квартира без единого выхода и перехода (вырожденный случай) — старые выходы
  остаются: мир не должен встать.
- Возвращает id входной комнаты новой квартиры (или перехода).

### 16.5. Переход (`placeTransition`)

Спец-комната — по весу роста среди комнат с `location.kind ∈ {stairwell, lift}` (поток
`root.sub("transition:" + адрес двери)`); с долей `trLanding` вместо неё — обычная лестничная площадка (§19.4). Встаёт за **любой** дверью шириной от 0.7 м (`TRANSITION_MIN_LEN = 7`
клеток) — проёмы разной ширины совмещаются, теги не сверяются; связь помечена `loose: true` (`validateFoldRun` её теги и
ширину не проверяет). Предел обзора и бесшовность для перехода не действуют (внутри — своя сцена).

Проход — как в §15.14: `descend(id)` (лестница) или `ascend(id, floor, side)` (лифт) создаёт комнату-выход; в режиме
квартир она — вход новой квартиры назначения (`transitionTarget`, поток `root.sub("trdest:" + ключ выхода)`): с
вероятностью `trToBiome` — другой обычный биом (равновероятно), иначе богатая квартира; нет другого биома — богатая;
нет богатой — другой биом. Выход лифта в логово босса — квартира биома, откуда пришли. **Проход сбрасывает счётчик**
(`count = 0`, `resets + 1`).

### 16.6. Исчезновение пропущенного перехода

Игрок открыл другой выход квартиры, а в её переходе ни разу не был (`enter` не вызывался) — связи перехода помечаются
`sealed: true` (в `Run.links` остаются — экземпляры не меняются никогда), `doorState` двери к нему — `'dead'`. Движок
рисует такую дверь стеной и не пускает в комнату перехода. Счётчик не сбрасывается — следующий переход выпадет снова по
формуле.

### 16.7. API режима

| метод | что делает |
|---|---|
| `enter(id)` → `EnterResult` | вызывать при **каждом** входе игрока в комнату: впервые и не спец-комната — `count + 1` и бросок; `{ count, chance, pending, resets, counted, triggered }` |
| `openDoor(id, connector)` | §16.4 |
| `doorState(id, connector)` | + `'exit'` — закрытый выход квартиры (дверь-панель, открывается) |
| `clusterAt(id)` → `ClusterInfo` | квартира экземпляра: биом, `home`, `rich`, комнат, выходов, переход |
| `transitionState()` | счётчик (`null` — режим выключен) |
| `stats()` | + `clusters`, `exitsOpen`, `transition` |

Сохранение (`StreamSave.world`, §15.8): квартиры (биом, `home`, `rich`, вход, выходы, открытые, переход), квартира
каждого экземпляра, исчезнувшие связи, посещённые комнаты, счётчик. Ключ в localStorage у «Прогулки» с квартирами —
`worldKey(seed, ["квартиры"])` (отдельный мир от прежнего).

### 16.8. Как это выглядит в «Прогулке» и в движке

- Закрытый выход — метка с флагом `exit` в JSON прогона (`RunConnector.exit`): блокаут ставит на неё **дверь-панель**
  (а не стену или темноту), глухие двери в режиме квартир — стены (`deadEnds: 'wall'`). Рядом с выходом (≤ 1.3 м) —
  подсказка «E — открыть дверь», E → `openDoor`; новая квартира достраивается в сцене, исчезнувшие выходы — стены.
  Метка прихода перехода (комната за выходом лифта или спуском лестницы) — флаг `arrival`: тоже всегда панель — у неё
  игрок появляется и через неё возвращается в локацию.
- В комнате перехода (лестница, лифт) открывается сцена спец-локации; выход из неё — `descend` / `ascend` (§15.14,
  `docs/LOCATIONS.md` §4, §10) в квартиру другого биома или в богатую. HUD показывает биом квартиры (★ — богатая).
- Сводка «Прогулки»: квартир, закрытых выходов, счётчик и шанс перехода («выпал — за следующей открытой дверью»).
- «Прогон» и «Файл» (один прогон без мира за переходом): шаг в комнату лестницы или лифта открывает её сцену; любой
  выход возвращает игрока к двери, через которую он вошёл.
- Проверка — `src/gen4d/stream.world.test.ts`: старт-квартира, открытие двери, цепочка из 25 квартир (у каждой ≥
  `clusterExits[0]` выходов), формула шанса, переход за дверью, исчезновение пропущенного, сброс и назначение, элитность
  богатой, сохранение/загрузка, детерминизм и прежний режим. В браузере — `node tools/qa-world-walk.mjs` (двери-панели,
  E, исчезновение выходов, переход лифтом и лестницей, пропуск, вход в спец-комнату в «Прогоне»).

## 17. Подвал: сеть ходов, хабы, кольца, бесконечные участки

Реализация — `src/gen4d/stream.ts` (режим квартир, кластер с `tunnels`), биомы и настройки — `src/gen4d/biomes.ts`
(`Biome.layout = 'tunnels'`, `WorldSettings.tunnels`), комнаты — `src/data/roomsBasement.ts`, ассеты — набор
пользователя `basement-3d` (`tools/optimize-basement.mjs`: текстуры отделок и модели предметов). Настройки — «Генератор»
(4D) → «Бесконечный мир» → «Подвал: сеть ходов» и галочка «подвал» у биома.

### 17.1. Для геймдизайнера: правило

> Подвал — не квартиры, а **длинные ходы** шириной 1 м, которые растут, пока идёшь. Изредка ход выводит в **хаб** —
> зал на несколько ходов (узел с колоннами, подвальный клуб, тепловой узел, зал кладовых). Сбоку от ходов —
> **кладовые** жильцов за решётчатыми дверями. Ход может уйти из хаба и **вернуться в тот же хаб другим проходом** —
> кольцо (оно идёт сквозь другие ходы в соседних слоях 4D, поэтому кажется, что ходы пересекаются, а ты их не
> встречаешь). Изредка попадается **бесконечный прямой участок**: развилка, прямой ход — и снова та же развилка с
> проходом, откуда пришёл. Идти можно бесконечно, выйти — тем же боковым проходом.
>
> В подвал попадают **через хабы**: «Спуск в подвал» из подъезда (его дверь в подвал — закрытый выход квартиры) или
> переход (лестница, лифт), который ведёт в подвал, — приходишь в хаб. Выходят **через хаб**: марш наверх — закрытая
> дверь (E) — за ней подъезд и квартиры того биома, откуда спустился. Остальные марши подвала при этом исчезают.

Три подвала — те же комнаты, своя отделка (правила отделки биома, §17.3): **сухой** (кирпич с побелкой, пыльный
бетон), **заброшенный** (синяя облупленная штукатурка, доски), **затопленный** (сырой бетон с плесенью, вода на полу).

### 17.2. Настройки `WorldSettings.tunnels`

| поле | по умолчанию | смысл |
|---|---|---|
| `hubEvery` | [40, 100] м | хаб не ближе 40 м хода от прошлого хаба; к 100 м — наверняка (шанс растёт линейно) |
| `turn` | 0.12 | шанс поворота на кусок хода |
| `branch` | 0.10 | шанс развилки |
| `storage` | 0.45 | боковая дверь хода: шанс, что за ней кладовая (иначе стена) |
| `ring` | 0.40 | шанс, что из хаба (при раскрытии) уйдёт кольцо в другой его проход |
| `ringLen` | [30, 80] м | длина кольца |
| `loop` | 0.05 | шанс бесконечного прямого участка на кусок хода (не ближе 12 м к хабу) |
| `loopLen` | [16, 30] м | длина участка — через столько метров снова тот же тройник |

### 17.3. Комнаты и отделка

Куски роста ходов — комнаты пула биома (теги биома: `подвал`, `кладовка`, `служебное`), вид — по меткам:

| вид | как определяется | пресеты |
|---|---|---|
| хаб | тег `хаб` | `bsm_hub_columns`, `bsm_hub_cinema`, `bsm_hub_boiler`, `bsm_hub_storage` — 3–4 прохода `basement` и марш `stair` наверх |
| прямой | два прохода `basement` на противоположных стенах, других дверей кроме `basement>storage` / `corridor>service` нет | `bsm_tun_1/2/4/4p/6/8` (1.0 × 1…8 м), `bsm_columns` |
| поворот | два прохода на соседних стенах | `bsm_tun_turn` (1×1 м), `bsm_passage_L` |
| развилка | три и больше проходов | `bsm_tun_T` (1×2 м), `bsm_tun_X`, `bsm_node` |
| кладовая | метка `storage>basement` | `bsm_storage`, `bsm_storage_jars`, `bsm_storage_junk`, `bsm_storage_moon` |

Проход `basement` — 1.0 м во всю ширину хода. Мебель и детали — модели набора (стеллажи, шкафчики, верстак, ряды
кресел, трубы у пола и под потолком, задвижки, лампочки, столбы, лужи, доски, мусор); в болванке — боксы с теми же
габаритами (§17.7). Отделка — `Biome.finishRules` поверх правил проекта по тегу комнаты (`подвал`, `кладовка`,
`служебное`): стены `f_bsm_brick` / `f_bsm_plaster` / `f_bsm_damp` / `f_bsm_planks`, полы `f_bsm_concrete` /
`f_bsm_boards` / `f_bsm_damp_floor` / `f_bsm_water` (повтор по реальному размеру: кирпич — 1 м на 10 рядов).

**Предел обзора.** Ходы и хабы (теги `ход`, `хаб`) — длинные пространства по замыслу: в режиме квартир линия обзора,
проходящая через такую комнату, пределом `sightM` не ограничена (рост, петли, `validateFoldRun` — по флагу прогона
`settings.longSight`). Квартиры по-прежнему «давящие». В прогонах («Прогон», прежний рост) — строго по пределу.

### 17.4. Рост (`expandTunnel`)

Подвал растёт на ходу, как прежний мир (§15): экземпляры не раскрыты заранее, `ensureAround` / `ensureVisible` их
раскрывают. Двери куска — по порядку `room.connectors`, поток двери `D = root.sub("door:" + адрес)`:

1. Проход `basement` — `tunnelStep`: выпавший переход (§16.5) — прямо здесь; петля к проходу напротив (своей сети);
   броски `u = D.next()`, `v = D.next()`: хаб при `u < pHub` (`pHub` по метрам хода от прошлого хаба — `tdist`, §17.2);
   иначе по `v`: `[0, loop)` — бесконечный участок (§17.6), затем развилка, поворот, остальное — прямой кусок. Вид не
   встал — следующий (прямой, поворот, развилка); ничего — стена. Стыковка — складчатая (`growFrom`, «комната важнее
   слоя»), без предела обзора.
2. Дверь в кладовую (`basement>storage`) — `D.next() < storage`: кладовая, иначе стена.
3. Прочие (служебка у `bsm_node`) — любая совместимая комната биома.
4. Марш хаба наверх (`stair`) — закрытый выход сети (ставится при постановке хаба).

`tdist` — метры хода от прошлого хаба (хаб — 0, кусок — родитель + длина куска по оси); в сохранении.

### 17.5. Кольцо из хаба (`buildRing`)

При раскрытии хаба с ≥ 2 свободными проходами — с шансом `ring` (поток `root.sub("ring:" + адрес хаба)`): кольцо от
прохода `a` до прохода `b` того же хаба. Путь — прямые прогоны и `n` поворотов в одну сторону (`n` = 1…4 — чтобы
последний курс смотрел в проход `b`). Шаги кусков считаются пробной стыковкой (якорь — середина проёма на линии стены):
прямой кусок длины `L` клеток — шаг `L + gap` по курсу; поворот — свой сдвиг по каждому курсу. Длины прогонов —
суммы шагов прямых кусков (1, 2, 4, 6, 8 м → 11, 21, 41, 61, 81 клетка; НОД 11 и 21 — 1, поэтому любая длина от ~20 м
складывается точно до клетки). Уравнение замыкания — по двум осям: свободные прогоны — броски, по одному на ось —
зависимые; длина кольца — в `ringLen`. Куски ставятся у слоя хаба (`placeFixed`: слой — ближайший к W хаба в пределах
`maxShift`) — где место в 3D занято, кольцо уходит в соседние слои W и идёт **сквозь** другие ходы. В конце — связь
последнего прохода с `b` (`tryLink`: |dw| ≤ `maxShift`). Не вышло на любом шаге — поставленное остаётся обычным
ходом. `stats().rings` — замкнутых колец.

### 17.6. Бесконечный прямой участок (`buildWrapLoop`, связь `wrap`)

Тройник встаёт **боком** к проходу (вход — его боковой проход), от одного прохода его оси — прямые куски на
`loopLen` м (не меньше двух), последний проход **сшит** со вторым проходом оси тройника связью
`{ a: последний кусок, b: тройник, wrap: [dx, dy] }`: тройник, сдвинутый на `wrap` клеток, стоит лицом к последнему
куску. Связь — в `Run.links` после дверей (как переходы), в пространстве лучей её нет.

- `validateFoldRun`: метки лицом к лицу со сдвигом, `dw = w(b) − w(a)`; комнаты — соседи по графу.
- Болванка целиком (`buildBlockoutModel`): шов — не проём, обе метки — тупики без жалоб. Куски портального рендера
  (`pieces.ts`) сдвигают соседа по шву и открывают проём; у портала — `shift` (м плана): комната за ним видна
  сдвинутой. Портальный рендер рисует её со сдвигом сцены, шагнул за шов — игрок переносится на `−shift`
  (docs/BLOCKOUT-BABYLON.md §12.13). Шов виден сквозь шов: ход уходит вдаль, повторяясь.

### 17.7. Выходы, входы, переходы

- **Вход**: закрытый выход квартиры с меткой `basement` («Спуск в подвал», тег `спуск` в биомах квартир) — `openDoor`
  ставит за ним **хаб** подвала (биом — бросок среди подвалов, хабы которых стыкуются с меткой двери — `descentBiomes`, не
  сарай; `root.sub("basement:" + адрес двери)`; по меткам, иначе
  швом `loose`); сеть — новая «квартира» с `tunnels: true`, `home` — биом, откуда спустились. Переход (§16.5) в
  подвал — комната-выход из хабов биома (`entryPool`).
- **Выход**: марш хаба (`stair`) — `openDoor` ставит квартиру биома `home` (подвал — квартирный биом по броску);
  остальные выходы сети исчезают, пропущенный в ней переход — тоже.
- **Переход по счётчику** в подвале выпадает так же (§16.1) и встаёт за ближайшим проходом хода, который раскрывается.
- Старт в подвале (`startBiome`) — хаб.

## 18. Параметры генераторов «Прогулки»

Все параметры — в `Project.world` (`WorldSettings`, `src/gen4d/biomes.ts`), интерфейс — «Генератор» (4D) → «Бесконечный
мир» (сворачиваемые блоки «Квартиры», «Переходы», «Подвал: сеть ходов», «4D и обзор прогулки»; у биома — «свои параметры
генератора»). Действуют на новые миры: сохранённый мир хранит свои настройки (`StreamSave.settings`).

### 18.1. Квартиры (`ApartmentSettings`: общие — поля `WorldSettings`, свои — `Biome.apartments`)

| поле | по умолчанию | смысл |
|---|---|---|
| `clusterRooms` | [6, 15] | комнат в квартире (≤ 15) |
| `clusterExits` | [2, 10] | выходов: `K` — бросок в диапазоне; минимум держится запасом, все оставшиеся двери — выходы до максимума (§16.3) |
| `exitReserve` | 1 | **проходимость**: при росте открытыми держится `max(min, round(K · exitReserve))` дверей — за ними только проходные комнаты. 1 — меньше тупиковых комнат, 0 — обычные квартиры (кухни, санузлы), больше тупиков |
| `entrySpare` | 2 | вход новой квартиры — сначала комната, у которой кроме двери входа ≥ `min + entrySpare` дверей |
| `seamEntries` | true | стыковка 4D-швом: по меткам за выходом ничего с запасом не встаёт — вход стыкуется любой дверью (`loose`). Выключено — только по меткам, внутренние двери выходами не бывают |

Только общие: `outerTags` (по умолчанию `landing>apt`, `apt>landing`, `corridor`, `stair`, `basement`) — метки «наружу»,
выходы квартиры в первую очередь; `transitionMinLen` (0.7 м) — переход встаёт за дверью не уже этого.

**Гарантия перехода.** Выпал переход (счётчик §16) — он встаёт за той дверью, которую игрок откроет следующей. Для этого
выходом квартиры становится только дверь, за которой переход встанет (`trFits`: не уже `transitionMinLen`, и хоть одна
спец-комната не пересекает в 3D саму комнату с дверью — дверь во внутреннем углу Г-образной прихожей смотрит в её
габарит); остальные — стены или добор до минимума выходов. За открытой дверью переход ставится любой ширины
(`placeTransition(…, anyWidth)`), выпавшая спец-комната не встала — пробуются остальные (лифт поместится там, где не
встаёт лестница). Переход ставится без предела обзора, бесшовности и складок по метрам (внутри своя сцена); для
`validateFoldRun` лестница и лифт — комнаты длинного обзора (`longSight`), складки с ними по метрам не меряются.
Проверка — `stream.params.test.ts` («гарантия перехода»: 48 выходов, складки 0 и 6 м).

### 18.2. Подвал (`TunnelSettings`: общие — `WorldSettings.tunnels`, свои — `Biome.tunnels`)

| `pieceWeights` | {} | **частота кусков**: множитель веса роста по id комнаты (нет — 1, 0 — кусок не ставится); свои у подвала — поверх общих по ключам |

Вид куска для таблицы частот — `tunnelKind(room)`: хаб (тег `хаб`), кладовая (метка `storage>basement`), прямой / поворот /

|---|---|---|

| `maxShift` | 4 | наибольший сдвиг на одном пороге |

### 18.4. Свои параметры у биома

Галочка «свои параметры генератора» копирует действующие (общие) параметры в биом: у квартирного — `Biome.apartments`,
у подвала — `Biome.tunnels`; дальше они правятся у биома. Генератор берёт `aptOf(world, биом)` / `tunOf(world, биом)` —
свои поля поверх общих. Например, общежитию — квартиры побольше, затопленному подвалу — реже хабы и без длинных ходов.

### 18.5. 4D-складки не ближе N м пути (`FoldSettings.localM`)

Складку игрок замечает, когда две комнаты одного места в 3D близки по ходьбе: вышел из комнаты, повернул в соседнюю —
и стоишь там, где только что была первая. `localRadius` считает двери, а не метры: за дверью кладовки в 1 м и за
дверью зала в 10 м — одна и та же «1 дверь». `localM` — предел в метрах пути: комнаты, пересекающиеся в 3D, не ближе
стольких метров ходьбы друг от друга, в этом радиусе мир — обычный трёхмерный.

Путь — Дейкстра по дверям (`aroundM`, `src/gen4d/foldcore.ts`): проём связи (и шов `wrap` бесконечного хода) — 0, внутри
комнаты — по прямой между серединами её проёмов; цена выхода из комнаты зависит от двери, которой в неё вошли.
Проверки — там же, где `localRadius`: стыковка (`growFrom`, `nearOf`: ближе предела от двери родителя), куски колец
подвала (`placeFixed`), петли (`loopLocalOk`: пары по обе стороны новой двери с суммой путей меньше предела) и шов
бесконечного хода. `validateFoldRun` пересчитывает пути сам и сообщает пары ближе предела.

**Выходы квартир.** За внутренней дверью (кухня, комната) в 3D обычно стоят комнаты этой же квартиры ближе предела —
вход новой квартиры там не встанет. Поэтому выходом становится только дверь, за которой он встанет (`exitFits`: хоть
одна комната пула — по метке или швом — не пересекает `nearOf` и находит свободный слой в пределах `maxShift`) и
встанет переход (`trFits`, §18.1). Остальные — стены или добор до минимума `clusterExits[0]` по ярусам: 1 — квартира
встанет, переход нет; 2 — квартира встанет, только если ослабить складки; 3 — не встанет ничего (в 3D за дверью сама
комната с ней) — всегда стена. Квартира без выходов — тупик всего мира. Если при открытии выхода (`openDoor`) ничего не встало, попытки повторяются с пределом `localM / 2`, затем только
по `localRadius` — дверь открывается всегда, а связь помечена `Link.close` (такой вход `validateFoldRun` по метрам не
меряет; счётчик — `StreamStats.closeDoors`).

Замеры (6 цепочек по 10 квартир, `localM` → комнат и выходов в квартире, входов ближе предела из 60): 0 → 8.9 и 7.5;
3 м → 8.1 и 6.3, 5; 4 м → 7.7 и 5.4, 8; 6 м → 7.3 и 5.4, 9. Пар одного места ближе 6 м пути: без предела — у 70–90%
комнат, при 6 м — ни одной (кроме входов `close`). Подвал (ходы прямые, складок мало) почти не меняется.

Нет поля / 0 — без проверки: прогоны фиксированного размера и старые сохранения мира не меняются; старые проекты
получают `walk.localM` по умолчанию (6 м) при загрузке.

Проверка — `src/gen4d/stream.params.test.ts`: сохранение → загрузка, квартира биома в одну комнату, проходимость 100% vs 0%,
без швов — без `loose`, метки «наружу», ширина двери под переход, свои параметры подвала и частота кусков, 4D прогулки,
складки не ближе 6 м (квартиры, подвал, прогон фиксированного размера; без предела проверка находит близкие пары).

## 19. Сарай, комнаты «только в биоме», площадка-переход, биом старта прогулки

### 19.1. Для геймдизайнера: правило

> **Сарай** — бесконечный трухлявый сарай: **длинные тёмные проходы** шириной 1.5 м. На одной стене — **гирлянда**
> (единственный свет), с другой стороны — **ряд открытых стойл**, как в конюшне: загоны 2 × 2.4 м за низкими
> перегородками (столб с шаром у прохода, жердь, доски понизу), у задней стены ясли с решёткой для сена; стойла по всему
> ходу — по одну руку. Иногда вместо стойла в задней стене проём — **проход дальше**. Изредка (через 60–140 м прохода)
> проход выводит в **хаб** — крытый двор, верхнюю комнату или конюшню; из хаба — лестница наверх (закрытая дверь, E): за ней квартиры того биома, откуда
> пришли. Растёт, как подвал (§17): кольца из хаба через W, бесконечные прямые участки. В сарай попадают **переходом**
> (или стартом прогулки в нём) — лестницы «Спуск в подвал» ведут только в подвалы. Пока игрок в сарае, свет «Прогулки»
> гаснет (`Biome.dark` 0.85, §19.5).
>
> **Переход — лестничная площадка.** Кроме бесконечной лестницы и лифта переходом бывает обычная этажная площадка
> подъезда (доля `trLanding`, по умолчанию 40%). Выпал переход — за открытой дверью площадка; **любая её дверь** (марш,
> квартиры, тамбур) — закрытый выход в биом назначения (другой биом или богатая квартира). Прошёл — счёт с нуля,
> остальные двери площадки исчезают; вернуться можно той же дверью. Не зашёл на площадку и ушёл другим выходом — она
> исчезает, как спец-комната.

### 19.2. Сарай: комнаты и отделка

Комнаты — `src/data/roomsBarn.ts` (модули набора пользователя barn-kit; моделей в наборе нет — мебель болванками
`p_barn_*`); гирлянда (`p_barn_garland`, сегмент 1 м: провод с провисом и две лампочки, светятся сами), перегородка стойла
(`p_barn_stall_div`, 2.4 м) и ясли (`p_barn_manger`) — модели из примитивов (`tools/make-barn-props.mjs` →
`src/view3d/assets/barn_props.glb`); отделка — доски набора (`f_barn_*`, `tools/optimize-barn.mjs`). Ни ламп, ни ковров,
ни сена на полу: свет — только гирлянды. Биом `barn` (`layout: 'tunnels'`, тег `сарай` ×1, `dark` 0.85, свои параметры
ходов: `hubEvery` [60, 140] м, `turn` 0.06, `branch` 0.12).

Кусок прохода — проход 1.5 м (восток, гирлянда) и ряд открытых стойл 2.4 м (запад), всего 3.9 м; проходы `barn` — у
прохода. Стойла — часть куска (без дверей): перегородки через 2 м, ясли и спот «в яслях» в каждом стойле.

| вид | метки | пресеты |
|---|---|---|
| прямой | два прохода `barn` (1.5 м) на северной и южной стенах | `barn_tun_2/4/6/8` (3.9 × 2…8 м, 1–4 стойла), `barn_tun_1` (вставка 1.5 × 1 м без стойл); шаги 11 … 81 клетка |
| поворот | вход с юга, выход на восток или запад; без стойл, гирлянда по внешнему углу | `barn_tun_turn`, `barn_tun_turn_l` (1.5 × 1.5 м) |
| развилка | вместо второго стойла — проём `barn` в задней стене («проход дальше») | `barn_tun_T` (3.9 × 4 м) |
| хаб | тег `хаб`: 2–3 прохода и марш `stair` — выход | `barn_hub_yard`, `barn_hub_loft`, `barn_hub_stable` (конюшня: три стойла) |

**Направление кусков** (`barnFlow`, `growKind` в `stream.ts`): проход `barn` на южной стене куска — вход, на остальных —
выход; за выходом следующий кусок встаёт входом (за входом — выходом), поэтому стойла по всему ходу — по левую руку,
гирлянда — по правую. У хабов направления нет; кольца и бесконечные участки (§17.5–17.6) ставятся без правила — на стыке
кольца сторона может смениться.

Сети ходов различаются **меткой прохода** (`TUNNEL_PASS_TAGS` в `src/gen4d/biomes.ts`: `basement` 1.0 м, `barn` 1.5 м) и
дверей к боковым помещениям (`TUNNEL_SIDE_TAGS` / `TUNNEL_STORE_TAGS`); рост (§17.4–17.6) — общий, по виду куска.
«Спуск в подвал» (выход с меткой `basement`) ведёт только в биомы-ходы, хабы которых стыкуются с этой меткой
(`descentBiomes`): в подвалы, не в сарай.

### 19.3. Комнаты «только в биоме» (тег `только-биом`)

`BIOME_ONLY_TAG` (`src/gen/generate.ts`): комната растёт только в биомах бесконечного мира. Её нет в прогонах
(«Прогон»: `generateRun`, `generateFoldRun`) и в прежней прогулке без биомов (`createStreamWorld` с `world: null`) —
`withoutBiomeOnly(p)`; миры и прогоны без таких комнат — бит в бит прежние. В режиме квартир она — только в пулах
биомов (`biomePool`); запасной рост «из всех комнат» (вход новой квартиры, комната-выход перехода) её не берёт. Все
комнаты сарая — с этим тегом (иначе лестница хаба стыковалась бы с маршами подъезда).

### 19.4. Площадка-переход (`placeTransition`, `WorldSettings.trLanding`)

1. Вид перехода — свой поток `root.sub("trkind:" + адрес двери)`: при `trLanding > 0` бросок `next() < trLanding` —
   площадка, иначе спец-комната (§16.5); при `trLanding = 0` броска нет (миры — прежние). Не встал выбранный вид —
   пробуется другой; нет спец-комнат — только площадки, нет площадок — только спец-комнаты.
2. Площадки — комнаты без спец-локации с тегом `лестница` и не меньше трёх дверей (этажные площадки, площадка у лифта):
   из пула биома, где выпал переход, иначе из всех (переход-площадка в подвале или сарае — хрущёвская). Выбор — по весу
   роста, поток `root.sub("landing:" + адрес двери)`; стыковка — любой меткой (`loose`), как у спец-комнаты, но площадка —
   обычная комната мира: предел обзора действует; складки по метрам — сначала с `localM`, не встала — без него (связь
   `close`, §18.5).
3. Площадка — своя «квартира»-переход (`Cluster.gate`): все её свободные двери — закрытые выходы; комнаты в счёт
   переходов не идут (`enter`). Квартира, где выпал переход, — `transition` = площадка (исчезновение пропущенного —
   §16.6).
4. `openDoor` у двери площадки (`passLanding`): назначение — `transitionTarget(площадка, "landing:" + адрес площадки)`
   (одно на все её двери); вход — из `entryPool` биома назначения (в подвале и сарае — хаб): по меткам с запасом
   `clusterExits[0] + 1` дверей, швом `loose` с тем же запасом (у перехода — всегда, без оглядки на `seamEntries`), затем
   с запасом 1, затем любой; не встал — то же со складками ближе `localM` (связь `close`). Новая квартира (или сеть ходов)
   растёт, **счётчик с нуля**, остальные двери площадки исчезают. Пропущенная площадка (§16.6) — связь `sealed`, её
   двери-выходы исчезают. HUD «Прогулки» на площадке: «· переход».
5. Сохранение: квартира с `gate: true`.

### 19.5. «Прогулка»: биом старта и темнота биома

Режим квартир: выпадающий список «Биом» в панели прогулки (обычные биомы, `· ходы` — сети ходов). Выбор сразу
открывает мир этого сида со стартом в выбранном биоме (`WorldSettings.startBiome` поверх проекта, `walkStreamSettings`).
У каждого биома — свой мир и своё сохранение (ключ `worldKey(seed, ["квартиры", "биом:" + id])`; стартовый биом
проекта — прежний ключ `["квартиры"]`): переключился и вернулся — продолжаешь с того же места. «Сбросить сохранение»
стирает миры сида во всех биомах. Дальше биомы меняются переходами, как обычно.

**Темнота** (`Biome.dark`, 0…1; «Генератор» → биом → «Темнота в прогулке»): пока игрок в квартире (сети ходов) биома,
рассеянный и направленный свет сцены — × (1 − dark), у игрока — тусклый тёплый точечный свет (4.5 м); светящиеся модели
(гирлянды, лампочки) горят как прежде (`src/view3d/biomeMood.ts`). Ушёл в светлый биом — свет как был. HUD на
площадке-переходе — «· переход».

## 20. Снежные тоннели: лазы, берлоги, обвалы, выход — подтаявший снег

Реализация — биом `snow` (`src/gen4d/biomes.ts`, `layout: 'tunnels'`, рост — §17, общий), комнаты —
`src/data/roomsSnow.ts`, оболочка снега — `src/view3d/snowMesh.ts` / `snowView.ts`, «Прогулка» в снегу —
`src/view3d/snowWalk.ts`, обвал — `src/locations/snowCollapse.ts`, выход — спец-локация «Ангар»
(`docs/LOCATIONS.md` §12). Ассеты — набор заказчика `snow-models` (`tools/optimize-snow.mjs`).

### 20.1. Для геймдизайнера: правило

> **Снежные тоннели** — лазы под снегом: ползёшь на четвереньках (арка 1.1 × 0.9 м), ходы виляют влево и вправо,
> ныряют вниз и лезут вверх (горки и ямы в лазе), много развилок, вдаль почти ничего не видно (туман). Иногда лаз
> выходит в **берлогу** — купол, где можно стоять скрючившись (у стены — снежная лавка, бывают находки). Сбоку от лаза
> бывает **тупиковая берлога**.
>
> **Обвал.** Затрещало и сыплется снег — уползай от места, где сыплется: через 2 с свод рухнет и завалит этот лаз
> (снежная пробка в проёме). Не успел — засыпало: откапывайся (E, ~12 раз), **напарник откопает быстрее** (~4). Завал
> никогда не запирает игрока: обваливается только проём, без которого из куска ещё есть путь в нераскрытые лазы.
>
> **Раскопка завала.** У пробки — «Завал. E — разгребать»: ~20 ударов (E), и лаз снова открыт; пробка с каждой четвертью
> работы меньше, сверху открывается щель. Копать можно с любой стороны, **в коопе удары всех игроков складываются**
> (вдвоём — вдвое быстрее). Начатая раскопка сохраняется.
>
> **Выход** — один: **подтаявший снег** — мокрое тёмное пятно в полу редкой берлоги (через 60–150 м ползком), снизу
> пробивается тёплый свет, капает. Бей его (E, 3–5 удара) — провалишься сквозь крышу в ангар промкомплекса
> (спец-локация «Ангар»). Переходов по счётчику (лестница, лифт, площадка) в снегу нет. Вход в снег — переходом из
> других биомов (или стартом прогулки в биоме «Снежные тоннели»): приходишь в берлогу на три лаза.

Биом: `T('snow', 'Снежные тоннели', …)` — тег `снег` ×1, отделка `f_snow` / `f_snow_floor` (для болванки и движка без
полости), темнота `dark` 0.9, свои параметры ходов: `hubEvery` [60, 150] м (подтаявшая берлога), `turn` 0.32, `branch`
0.24, `storage` 0.4 (тупиковая берлога за боковым лазом), `ring` 0.3, `ringLen` [24, 60] м, `loop` 0.02.

### 20.2. Комнаты

Все — с тегами `снег` (первый: группа спавна «снег», отделка) и `только-биом` (§19.3). Лаз стыкуется меткой `snow`
(1.2 м — арка 1.1 м в проёме; с ходами подвала и проходами сарая не стыкуется), боковой лаз — `snow>den` ↔ `den>snow`
(1.2 м). `TUNNEL_PASS_TAGS` + `snow`, `TUNNEL_SIDE_TAGS` + `snow>den`, `TUNNEL_STORE_TAGS` + `den>snow`.

| вид (§17.3) | пресеты | что |
|---|---|---|
| прямой | `snow_crawl_1/2`, `snow_crawl_3_up/down` (горка 0.25 м / яма 0.3 м), `snow_crawl_4_up/down` (`круто`: 0.5 / 0.6 м), `snow_crawl_jog` (сдвиг вбок на 0.6 м), `snow_crawl_side` (боковой лаз), `snow_den_pass` (проходная берлога) | лазы 1.2 × 1…4 м |
| поворот | `snow_turn` (дуга, 2 × 2 м), `snow_turn_tight` (1.6 × 1.6 м), `snow_den_corner` (угловая берлога) | — |
| развилка | `snow_fork_T`, `snow_fork_Y`, `snow_fork_X`, `snow_den_junction` (берлога на три лаза — концепт набора) | вход сети |
| кладовая | `snow_den_side` — тупиковая берлога за боковым лазом | обвалов в берлогах нет |
| хаб | `snow_thaw` — подтаявшая берлога, спец-локация «Ангар» | выход сети |

Теги кусков: `ход` (лазы и проходные берлоги — длинный обзор, как у подвала), `берлога` (купол, поза — скрючившись),
`лавка` (снежный уступ у глухой стены), `горка` / `яма` (+ `круто`), `поворот`, `развилка`, `подтаявшая`.

### 20.3. Рост (что добавлено к §17)

- **Выход сети — хаб со спец-локацией.** В режиме квартир спец-комнаты не растут (только переходы, §16.2); исключение —
  хаб сети ходов со спец-локацией и тегом `только-биом` (`netExit`): подтаявшая берлога растёт в своём биоме **по
  правилу хабов** (`tunnelStep`, `pHub` по метрам хода от прошлого хаба). Сцена ангара при этом не открывается при
  входе — только пробитым снегом (§20.6).
- **Вход сети** (`entryPool`): хабы без спец-локации; если все хабы биома — со спец-локацией (снег) — берлоги-развилки
  (`развилка` + `берлога`), иначе развилки, иначе весь пул без спец-комнат. Старт прогулки в снегу — берлога на три
  лаза.
- **Переходов по счётчику нет** в сети со своим выходом (`ownExit`: в пуле хабов биома есть спец-локация): выпавший
  переход ждёт, пока игрок не выйдет из снега (через ангар — счётчик с нуля).
- **Ворота ангара** (`descend` для `kind 'hangar'`): этаж — `floor(L) − roll.floorsDown`; есть биом `factory` — комната
  из его `entryPool` (хаб завода), `home` — биом, откуда пришли в снег; нет — `transitionTarget`, как у перехода.
- **Обвал** — `StreamWorld.collapse(instId, connectorId)`: связь двери помечается (`collapsedL`, она же в `sealed`):
  `doorState` обеих меток — `'collapsed'`, в `Run.links` — `sealed`; несвязанную метку не завалить (`false`).
  Сохранение — `WorldSave.collapsed` (индексы связей). Место выбирает движок (§20.5).
- **Раскопка** — `StreamWorld.digThrough(instId, connectorId, amount)`: работа копится по связи завала (`dugL`, с любой
  из двух меток); набралось 1 — завал снят (связь снова обычная дверь, `doorState` — `'linked'`), иначе — доля;
  `collapseProgress(instId, connectorId)` — доля (null — завала нет). Сохранение — `WorldSave.dug` ([связь, доля]).
  «Прогулка»: операция мира `{ k: 'dig', inst, conn, amount }` (`WalkSession.request`, в коопе — у всех игроков в
  порядке сервера); метка завала в JSON — `collapsed` и `dug` (четвертями: 0.25 / 0.5 / 0.75 — кусок пересобирается,
  пробка меньше).

### 20.4. Оболочка снега («Прогулка»)

У комнат снега стен нет: портальный рендер (`PieceCache.get`, `src/view3d/portal.ts`) прячет стены, пол и потолок
болванки и ставит **полость в снегу** — сетку и её коллайдер (`snowPieceFor`). Полость — функция расстояния
(`snowField`, < 0 — воздух), сетка — «surface nets» на мировой решётке 5 см:

- **лаз** — трубка профиля устья набора (`01-snow-tunnel`: полуэллипс 0.55 × 0.8 м на высоте 0.1 м, пол у стен
  поднят на 0.108 м; `tools/optimize-snow.mjs` проверяет профиль по вершинам торца) вдоль кривой: от середины проёма —
  прямой вывод 0.3 м по нормали, затем кубическая кривая Безье ко второму проёму (два проёма — прямой, сдвиг, поворот
  дугой) или к точке встречи (развилка); горка / яма — пол кривой синусом (на выводах — 0);
- **берлога** — купол (эллипсоид, 1.37 м в свету, как `02-snow-den`) и лазы к нему; лавка — снежный уступ у стены без
  проёмов;
- **глухой проём** — лаз обрывается в ~0.2 м от стены круглым торцом; **завал** (`RunConnector.collapsed`) — в проёме
  снежная пробка; при обвале на неё падают глыбы набора (`03-snow-collapse`, `snow_chunks.glb`);
- **рельеф** — шум (бугры 0.45 м и 0.15 м, слоистость стен), пол ровнее (по нему ползут); у проёмов шум гаснет, и в
  0.3 м от плоскости проёма полость — **точно трубка устья**: плоскость проёма — середина зазора между комнатами
  (граница кусков портального рендера), решётка мировая — кольцо вершин на плоскости у обоих соседей одно и то же, шов
  не виден (тест `snowMesh.test.ts`); нормали — градиент поля по решётке (тоже одинаковы на шве);
- полость не выходит за план комнаты (отступ 4 см), кроме пролётов проёмов — до их плоскости;
- цвет вершин: снег 0.86…0.92 (палитра набора), впадины темнее, свод светлее; материал — матовый, слабое свечение
  (умножается на цвет вершины: свод светится сквозь толщу снега), зерно — карта нормалей из шума (`snowGrain`);
- **коллайдер** — та же полость гладкой сеткой 10 см (камера в лазе ползёт по ней);
- сетки строит **воркер** (`snowWorker.ts`, встроен в сборку): мир вырос — куски впереди готовятся заранее
  (`snowPrefetch` в `PieceCache.setRun`); не успел — кусок строится на месте (20–60 мс).

Этажи в «Прогулке» по высоте не разводятся (портальный рендер, как у болванки) — полость всегда на высоте 0.

### 20.5. Поза, туман, обвал, подтаявший снег (`SnowWalk`, `src/view3d/snowWalk.ts`)

- **Поза** — общая поза от первого лица (`src/view3d/posture.ts`, во всех источниках 3D): **C** — на четвереньки /
  встать (во весь рост, если над головой ≥ 1.8 м, скрючившись — ≥ 1.25 м, иначе «Здесь не встать — низко»). Стоя — глаз
  1.6 м, эллипсоид 0.3/0.85, гравитация Babylon; скрючившись — 1.1 м; на четвереньках — 0.5 м, эллипсоид 0.25/0.2 (в
  лаз 0.9 м пролезает), скорость 0.22 / 0.11 / 0.075. Низко опора своя: эллипсоид висит на «шаге» 0.18–0.2 м над ногами
  и касается только стен, ноги ставит луч вниз до пола (вниз — плавно, вверх по склону — сразу). Гравитация Babylon —
  постоянные −16 см за кадр — на наклонном полу (чаша берлоги, горки лаза) стаскивала низкий эллипсоид сильнее шага
  ползком (4–10 мм за кадр при 60–144 к/с): игрок не мог проползти, особенно на подъёмах. Ползком — ход (`CRAWL_CYCLE`
  0.62 м на два шага рук: толчок 3 см и покачивание плеч ±1.7°) и руки в варежках внизу кадра (`src/view3d/snowHands.ts`).
  В снегу: вошёл — на четвереньки сам; в берлоге можно встать скрючившись (C); скрючившись упёрся в низкий свод лаза —
  на четвереньки сам; ушёл из снега — встаёт. Камеру поставили выше пола лаза (переход, загрузка) — сразу на пол. Свет у
  игрока в снегу — у глаз.
- **Туман** — линейный 1.2…7 м (вдаль почти ничего не видно), свет у игрока — холодный, ярче, чем в тёмных биомах.
- **Обвал** (`snowCollapse.ts`): метры ползком в лазах (не в берлогах) → порог `everyM` [45, 110] м (бросок на каждый
  обвал, `makeRng(seed + "/c" + n)`) → место — `collapseSite(rx, комната, x, y)`: проём куска, связанный с соседом,
  ближайший к игроку, **завал которого не запирает игрока** (из куска по оставшимся связям достижим нераскрытый проём);
  нет — отсрочка на `retryM` (6 м) → треск (`warnS` 2 с: сыплется снег, тряска, тёмная виньетка) → обвал:
  `collapse` в мире, глыбы, облако; игрок ближе `buryM` (1.1 м) к месту — **засыпан**: белая пелена, «E —
  откапываться» (`digSelf` 12 нажатий; напарник снаружи — `digMate` 4, `SnowWalk.mateDig()`), откопался — на своей
  стороне завала. Смерти нет.
- **Раскопка завала**: ближе 1.2 м к проёму с пробкой — «Завал. E — разгребать (n/20)»; нажатие — работа `1/clear`
  (`CollapseSpec.clear` 20) операцией мира `dig`, снег из-под рук, хруст; раскопан — лаз открыт, глыбы у него убраны.
- **Подтаявший снег**: в подтаявшей берлоге — пятно в полу (меш куска: мокрая каша, тёплый отсвет, трещины), тёплый
  свет у пола, капли; ближе 1.1 м — «Подтаявший снег. E — бить»; трещины растут с каждым ударом; последний —
  `onBreak` → сцена ангара (падение, `docs/LOCATIONS.md` §12).

HUD: `SnowHud { buried, crack, prompt, pose }` → страница рисует пелену, виньетку и подсказку.

**Звук** (`src/view3d/snowAudio.ts`, процедурный WebAudio): глухой ветер над толщей снега, изредка оседает снег; хруст
ползком (каждые 0.16 м) и скрючившись (0.45 м, глубже); треск свода — щелчки учащаются к обвалу, низкий стон, со
стороны места обвала; обвал — тяжёлый глухой удар и сыплется; засыпан — всё глохнет (низкий фильтр), слышно сердце и
дыхание; откопка — хруст; у подтаявшего пятна — капли (ближе — громче), удар — ледяной треск и хлюпанье, пробил — треск,
провал, свист. Включается первым нажатием клавиши / кликом в снегу (политика автоплея); выключить —

## 21. Завод: влажность, болото, финал игры

### 21.1. Для геймдизайнера: правило

> **Завод** — последняя локация: цеха из шестерёнок, сталелитейных комплексов и кручения всего подряд. Проход 2 м
> между двумя рядами станков за перилами (шестерни, маховики, валы, вентиляторы, конвейеры, прессы — **всё
> крутится**), двутавровые колонны, лампы-«тарелки»; изредка (через 30–70 м) — цех-хаб: машинный зал, литейный цех,
> насосная, затопленный цех. Из завода выход один — **болото**.
>
> **Иди туда, где влажнее.** На каждой развилке и в каждом цеху один проход ведёт к сырости, остальные — в сухие цеха.
> Влажнее — значит сначала конденсат и сырой бетон (сталелитейка), потом течь с потолка (капли в проходе), лужи и
> насосы, потом вода по полу, грязь, камыш и сухие деревья сквозь пол — а с потолка свисают камыш и комья грязи:
> болото начинается сверху, вверх ногами. Дошёл до болота — зал, где болото над головой; из воды встаёт огромная
> шестерня; встал на её зуб — он поднимает тебя и вдавливает в болото наверху: **конец игры** (`docs/LOCATIONS.md` §13).
> Свернул не туда — цеха сохнут, пока на следующей развилке не выберешь мокрый проход.

Сколько идти: по мокрому пути — 10–20 кусков (~50–120 м) от сухого входа (20 сидов: в среднем 14 кусков, ~75 м);
по сухому — болота нет. Переходов по счётчику в заводе нет: свой выход — болото (как подтаявшая берлога у снега, §20);
в завод приходят воротами ангара (§20), переходом из других биомов или стартом прогулки в нём.

### 21.2. Комнаты (`src/data/roomsFactory.ts`)

Все — тег `завод` (группа спавна), `только-биом` (§19.3); проход — метка `factory` (2.0 м, симметричная, с подвалом и
сараем не стыкуется; закрытый тупик — цеховые ворота `factory_gate`, `docs/DOORS.md`). Ступень влажности — тег
после `ход` / `хаб`: `сухо`, `сыро`, `течь`, `топь`; на каждой ступени полный набор:

| вид | пресеты | что внутри |
|---|---|---|
| прямой | `fac_bay_<ст>_4/6/8` (5 × 4…8 м) | проход 2 м между рядами по 1.5 м; места по 2 м — спот-группы: два станка или один длинный (пара шестерён, конвейер, насос), розыгрыш на экземпляр; перила, колонны, под потолком — лампы / течь, на полу — лужи / грязь |
| поворот | `fac_turn_<ст>_r/l` (2 × 2 м) | направо, налево; колонна в углу |
| развилка | `fac_tee_<ст>` (5 × 4 м), `fac_cross_<ст>` | боковой проход вместо ряда станков (тройник, крестовина) |
| хаб | `fac_hub_<ст>` (6.3 × 6.3 м) | машинный зал (поворотный круг), литейный цех (печи, ковш, формы с расплавом), насосная, затопленный цех; хаб ≤ 9 м по диагонали — предел обзора пула |
| финал | `fac_swamp_roof` (4 × 4 м) | «Под перевёрнутым болотом», `location.kind 'swamp'`, тег `топь`; вес 1, но **ростом не ставится** — только правилом влажности |

Станки по ступеням: **сухо** — шестерни, маховики, валы, вентиляторы, прессы, лампы; **сыро** — печи, ковши, формы с
расплавом (светятся), тали, трубы; **течь** — насосы, вентили, бочки, течь с потолка над проходом, лужи; **топь** —
камыш, грязевые островки, сухие деревья, ржавые шестерни, вода по полу, а **с потолка** — перевёрнутое болото: над
рядами станков свисает камыш (`p_fac_reeds_hang`) и комья грязи (`p_fac_mud_hang`), над проходом — грязь и течь. Модели — `factory_props.glb` набора
пользователя (`tools/optimize-factory.mjs`), подвижные части крутятся (`src/view3d/propAnim.ts`, `docs/LOCATIONS.md`
§13.5).

Отделка — правила по тегу ступени (на уровне проекта и в биоме): **сухо** — кирпич с побелкой, пыльный бетон; **сыро**
— кирпич и сырой бетон; **течь** — сырой бетон, пол местами в воде; **топь** — вода по полу. Правила `завод` нет:
правило выбирается по первому тегу комнаты, у которого оно есть, и `завод` победил бы ступень.

### 21.3. Биом `factory`

`layout: 'tunnels'`, тег `завод` ×1, `dark` 0.45 (лампы и расплав светятся); переходов по счётчику нет (`ownExit`: у биома
с `wet` свой выход — болото); свои параметры ходов: `hubEvery` [30, 70] м,
`turn` 0.14, `branch` 0.3, **`ring` 0, `loop` 0** (кольца и бесконечные участки ставятся без правила влажности — их
нет); `wet` — влажность (`Biome.wet`, `WetSettings`):

| поле | по умолчанию | что |
|---|---|---|
| `line` | 0.035 | прибавка (убыль) за кусок по ходу, который становится влажнее (суше) |
| `fork` | 0.15 | развилка или хаб: «мокрый» выход — мокрее на `fork` |
| `dry` | 0.25 | прочие выходы — суше на `dry` |

Биом без `wet` — как раньше (подвалы, сарай). `wet` сохраняется с биомом (`normBiome`).

### 21.4. Правило влажности (`src/gen4d/wet.ts`, `stream.ts`)

У каждого куска сети биома с `wet` — влажность `w ∈ [0, 1]`, направление `dir` (+1 — ход становится влажнее, −1 —
суше) и метка, через которую в него вошли (`in`):

1. **Вход в сеть** (кусок, родитель которого не из этой сети: старт, переход, ворота ангара) — `w = 0`, `dir = +1`.
   Входная комната — сухой хаб (`entryPool` — хабы ступени `сухо`).
2. **Ребёнок за проходом `ci` куска P** (`wetFor`): выходы дальше — проходы P, кроме `in`. Один — **линия**:
   `w + dir · line`, `dir` тот же. Несколько — «мокрый» выход разыгрывается по адресу куска (`root.sub("wet:" +
   адрес)`, не зависит от порядка раскрытия): за ним `w + fork`, `dir = +1`; за остальными `w − dry`, `dir = −1`.
   Обрезка в [0, 1].
3. **Ступень** ребёнка — `wetLevel(w)`: сухо [0, 0.1), сыро [0.1, 0.4), течь [0.4, 0.7), топь [0.7, 1). Кусок
   выбирается из пула вида (прямой, поворот, развилка, хаб — как в §17.4) **этой ступени** (`tunPool(биом, вид,
   ступень)`: комнаты с тегом ступени; нет таких — все). Ширина ступени 0.3 < `fork + dry` = 0.4: на любой развилке
   мокрый выход — на ступень мокрее сухого, разницу видно сразу.
4. **Болото**: `w` ребёнка дошла до 1 — в `tunnelStep` до бросков вида ставится комната-финал (`swampPool`: комнаты
   биома с `location.kind 'swamp'`, вес > 0); не встала — кусок ступени `топь`, попытка — у следующего прохода.
5. Влажность считается при постановке (`onPlaced` → `wetPlaced`) и хранится в сохранении (`WorldSave.twet`: по
   порядку экземпляров `[w, dir, in]` или `null`). Миры без биомов с `wet` — бит в бит прежние (лишних бросков нет).

API: `world.wetAt(id)` → `{ w, dir, level } | null`; `locationOf(id)` у финала — `{ kind: 'swamp', spec, roll }`
(номер части — `rollSwamp`, ключ — адрес комнаты).

  сида во всех биомах стираются, старт — биом проекта; в кооп-лобби недоступна), «Ещё раз», «На завод».

Рост — общий для сетей ходов (§17.4): проход `obshaga` / `obshaga_bsm` — `tunnelStep` (хаб, прямой, поворот, развилка —
куски с совместимой меткой); дверь комнаты `obshaga>room` — боковая дверь хода (`TUNNEL_SIDE_TAGS`, как кладовая
подвала): с шансом `tunnels.storage` комната (комнаты — `TUNNEL_STORE_TAGS`: метка `room>obshaga`), иначе дверь заперта;
дверь общего помещения `obshaga>common` — растёт всегда, любой совместимой комнатой биома (как служебка, в

комната вахтёра. Её дверь — на стене проёма 3.2×3.2 м посреди вестибюля, смотрит внутрь: комната 2.8×2.8 встаёт в
проём (при зазоре 0…2 клетки), место в 3D со всех сторон занято самим залом — ни другая комната, ни складки по
метрам (`localM` «Прогулки» 6 м) ей не мешают, войти в сеть через эту дверь нельзя. Поэтому у **каждого** вестибюля
(старт, вход переходом, дальние хабы) комната вахтёра и лампа в ней есть всегда. (Раньше дверь была на наружной
стене: в «Прогулке» комната упиралась в западный коридор и со складками не ближе 6 м не вставала никогда.) Лестничные клетки — **сбоку** коридора: проём `obshaga>stairs` куска `obsh_cor_9s` растёт всегда (как дверь общего
помещения, в `TUNNEL_DOORS`), за ним — клетка по весам (наверх 0.5, вниз 0.3, в подвал 0.45); клетка — не кусок хода
(`tunnelKind` — null), в линию коридора не встаёт и прямой не рвёт; за её дальним проёмом сеть растёт дальше (коридор
другого этажа или ход подвала). Подвал — та же сеть биома со своей меткой: в него ведёт только `obsh_stair_down`
(сверху `stairs>obshaga`, снизу `obshaga_bsm`), наверх — той же клеткой; хабов в подвале нет.

Отделка — правила биома по тегу помещения (правила `общага` нет: оно бы победило): коридоры — `f_obsh_corridor`
(побелка #D8D0B5 над кафельной панелью `f_obsh_tile_panel` 1.425 м: нижний ряд тёмно-зелёный #5E8A6E, восемь рядов

### 22.4. Параметры сети (`Biome.tunnels`) — почему такие

| поле | общага | по умолчанию | зачем |
|---|---|---|---|
| `hubEvery` | [90, 200] м | [40, 100] | вестибюль — событие, а не узел через каждые 50 м |
| `turn` | 0.04 | 0.12 | длинные прямые коридоры (сарай 0.06, снег 0.32) |
| `branch` | 0.03 | 0.10 | редкие тройники — меньше «лабиринта» |
| `storage` | 0.8 | 0.45 | у коридора почти все двери — живые комнаты; 20% заперты |
| `ring` | 0.08 | 0.40 | кольцо из вахты (проход сквозь другие коридоры в 4D) — редкость |
| `ringLen` | [40, 90] м | [30, 80] | если кольцо есть — длинное: наложение в 4D далеко от входа |
| `loop` | 0.01 | 0.05 | бесконечный прямой участок — почти никогда |
| `loopLen` | [24, 40] м | [16, 30] | и длинный — шов не бросается в глаза |
| `loopMinDist` | 30 м | 12 | не у вестибюля |

Замеры (4 мира по 200 комнат): поворотов и развилок — < 15% кусков сети (в снегу по умолчанию — вдвое больше), колец
и бесконечных участков — не больше одного на 100 комнат. Складки 4D на стыках (общие `WorldSettings.walk`) — как везде.

**Прямые прогоны** («прямых пространств маловато» — жалоба заказчика). Прогон — подряд стоящие прямые куски коридора от
поворота / развилки / вестибюля до следующего поворота, развилки, вестибюля, лестницы или тупика; замер — в настройках
«Прогулки» проекта (`walkStreamSettings`: складки не ближе 6 м), 8 сидов (`qa-obsh-1`, `qa-obsh-2`, `s1`…`s6`), идя по
прогонам из вестибюля старта и дальше из поворотов, развилок, вестибюлей:

| | было | стало |
|---|---|---|
| медиана прогона | 25.5 м | 36.1 м |
| четверть (p25) / три четверти (p75) | 10.5 / 33.9 м | 11 / 69.2 м |
| чем кончается прогон | лестница 33%, поворот 26%, развилка 28%, вестибюль 9%, тупик 4% | поворот 33%, развилка 31%, вестибюль 29%, тупик 7% |
| вставок 1 м среди прямых кусков | 10% | 3.4% |

Главная причина была — лестницы в линии коридора (кусок «прямой», 12% бросков прямого): каждая рвала прогон; теперь
клетки сбоку. Остальное — чаще длинные куски (9 и 7.2 м) и реже вставки по 1 м. Повороты и развилки — от бросков
`turn` / `branch` и от отказов по месту (за поворотом — свои же боковые комнаты; складки не ближе 6 м) — их оставили.

**Кольца и швы — своей сетью, без лестниц** (`ringKit(биом, метка)`, `src/gen4d/stream.ts`): детали кольца — только
куски, все проходы которых — метка прохода, откуда кольцо уходит (в одном биоме общаги две сети: коридоры и подвал), и
без тега `лестница` (марш меняет высоту пола — кольцо и шов замыкаются в плане); кольцо из хаба — только между его
проходами одной метки. У прежних биомов (одна метка прохода, лестниц в сетях нет) наборы деталей те же.

### 22.5. Для интеграции и движка

- **Двери комнат.** Метка двери коридора — `obshaga>room` (со стороны коридора), комнаты — `room>obshaga`; общие
  помещения — `obshaga>common` / `common>obshaga`, вахтёрская — `hall>vahter` / `vahter>hall`. Дверь всех трёх пар —
  `obshaga_room` (фанерное крашеное полотно 0.8 м в проёме 0.9, жестяной номерок со стороны коридора, накладной замок;
  цвета #7A3E22 / #B5832F / #D6C9A0). Полотно — **в комнате** (`LEAF_SIDE`: `room>obshaga` — true): у связанной двери
  слот комнаты (`DoorSlot.inst` — комната, `tag` `room>obshaga`, `leaf: true`, `role: 'open'`, `angle` — угол покоя,
  распахнута), у коридора — только наличник (`leaf: false`). Дверь, за которой комната не выросла (бросок
  `storage`), — тупик: слот коридора `role: 'dead'`, `style: 'obshaga_room'`, `leaf: true`, `angle: 0` — закрытое
  полотно на глухой стене, номерок к коридору, без досок заколоченной; у `obshaga_room` (`DoorStyle.selfClosing`) такой
  слот есть и при глухих тупиках «Прогулки» (`deadEnds: 'wall'`, `src/blockout/core.ts`). Связь двери в прогоне — обычная
  `Run.links` (`a`/`b` — экземпляр и метка). Поля слота: `inst`, `connector`, `tag`, `style`, `role`, `leaf`, `line`,
  `normal`, `widthM`, `heightM`, `hinge`, `angle`, `space`, `seed` (`src/blockout/types.ts`). Полотна
  самозакрывающихся дверей — подвижные меши при любой роли и коллайдеры (`BabylonBlockout.doorLeaves`, ключ
  `"inst/connector"` — он же id двери режиссёра); позу ставит «Прогулка» (`poseDoor`, `FoldDriver.doorPose`): закрыто,
  пока игрок не открыл (docs/LOCATIONS.md §14).
- **Керосиновая лампа.** Спот `lantern` (id `<roomId>_s_lantern`, имя «Керосиновая лампа», группа
  `<roomId>_g_lantern`) на полу: в `obsh_vahter_room` — всегда, в `obsh_room_*` и `obsh_kitchen` — 1 из 10. В прогоне:
  `run.content[k]` (k — индекс экземпляра в `run.instances`, `content[k].inst` — его id) → `spots[]`
  (`SpawnedSpot`): `spotId` оканчивается на `_s_lantern`, `x`, `y` — **мировые клетки плана** (× `cellM` 0.1 → метры;
  поворот и сдвиг экземпляра учтены; слой — `Instance.w`, высота — `Instance.z` модуля лестниц), `content` —
  `{ kind: 'prop', id: 'p_obsh_lantern', rot }` или `null` (лампы на этот раз нет). То же в экспорте болванки —
  `RunInstance.spots[]` (`id`, `x`, `y` в мировых клетках, `content`); в 3D (`spotProps`) — коллайдер
  `prop:<inst>:p_obsh_lantern` с моделью `propModel:<inst>:p_obsh_lantern`. Взял лампу — операция мира
  `{ k: 'lamp', inst, spot }` (`StreamWorld.takeLamp`, сохранение — `WorldSave.lamps`): у взятой спот в экспорте пуст,
  кусок комнаты пересобирается без неё (`src/view3d/walk.ts`).
- **Свет.** Плафоны `p_obsh_plafond` и лампы ЛДС `p_obsh_tube` (теги `лампа`, `потолок`, `свет`) — в коридорах через
  3.6–4.5 м, в каждом помещении, на площадках лестниц и в подвале. В 3D — меши `propModel:<inst>:p_obsh_plafond` /
  `…:p_obsh_tube` (metadata `{ kind: 'prop', inst, propId }`), светятся материалами `obsh_lamp_glow` /
  `obsh_tube_glow` — их гасит отключение света.
- **Вода по пояс.** Помещения с тегом `затоплено` (все `obsh_bsm_*`): плоскость воды на 0.9 м над полом комнаты (с
  высотой экземпляра) и шаг ×0.55 — `src/view3d/obshagaScene.ts` / `obshagaWalk.ts`; пол — `f_bsm_water`.
- **В «Прогулке»** (docs/LOCATIONS.md §14, `src/view3d/obshagaWalk.ts`): двери закрываются сами, отключения света,
  керосиновая лампа, рука, смерть и возрождение в ближайшем вестибюле, кооп. Рука ходит по графу проёмов только в
  комнатах общаги, без лестничных залов и швов (`chartOf`, `src/view3d/obshagaNav.ts`).
- **Кровати — укрытие.** Под `p_obsh_bed` (плита от 0.30 м) пролезают только лёжа (ползком к ней — ложится сам,
  `src/view3d/posture.ts`, `Posture.under`); под `p_obsh_table` (от 0.62 м) — на четвереньках, но стол от руки не

- **Обзор 45 м** (`Biome.viewM`, общий механизм): пока игрок в комнате биома с `viewM`, мир раскрывается вперёд не меньше

## 23. Сюжет: мир «Запустить без отладки» (`WorldSettings.story`)

### 23.1. Для геймдизайнера: правило

Игра идёт по цепочке локаций; переход (спец-комната, по тому же счётчику пройденных комнат, что в «Прогулке») ведёт
строго на следующий шаг, а не в случайный биом:

| шаг | биом | переход дальше | куда |
|---|---|---|---|
| 1 | хрущёвка `khrush` | бесконечная лестница | подвал или катакомбы |
| 2 | подвал `basement` или питерские катакомбы `catacombs` (если биом есть в мире) | ржавый лифт (клетка или каретка) — только с **верхнего** этажа; прочие этажи и вниз — снова подвал | сарай |
| 3 | сарай `barn` | люк в погреб (в полу закутка) | погреб |
| 4 | погреб `cellar` (пока заглушка — подвал) | дверь в снег (обвал, откопаться) | снег |
| 5 | снег `snow` | подтаявший снег → ангар (свой выход сети, без счётчика) | завод |
| 6 | завод `factory` | болото (свой выход, финал) | конец |

Шаг может быть одним из нескольких биомов (`StoryStep.alt`, `STORY_ALT_STEPS`): лестница хрущёвки ведёт в подвал или
катакомбы — в один из тех, что есть в мире, по переходу (детерминированно); номер шага у них общий (2).

Срыв: Хвататель утащил на лестнице или из лифта выпал — игрок в **общаге** (`obshaga`, вестибюль). Из общаги нет
чёткого выхода: её переход — дверь в снег (→ снег), двери на улицу — по двери хрущёвка (в начало) или подвал.
Лестничных площадок-переходов и богатых квартир в сюжете нет; «Спуска в подвал» из квартир тоже — в подвал только
бесконечной лестницей. Выходы хабов сетей ходов наверх (подвал, сарай, погреб) ведут, как и без сюжета, в квартиры —
в сюжете это хрущёвка (путь назад, в начало).

### 23.2. Мир сюжета (`storyWorld(w)`)

`story: true`, `startBiome: 'khrush'`, `trLanding: 0`; биомы — только `storyBiomes()` в порядке сюжета: свои из `w`
(правки автора), недостающие — из пресетов (`storyWorld(w, presets = defaultBiomes())`); другого биома шага
(катакомбы) нигде нет — его просто нет в мире; заглушка `STORY_PLACEHOLDER` (`cellar` → `basement`) — копия
биома-образца с id `cellar`, названием «Погреб», только если биома `cellar` нет ни в `w`, ни в пресетах (настоящий
биом погреба заменит заглушку сам). Богатые биомы отброшены, у квартирных снят тег `спуск`. Счётчик переходов,
квартиры, ходы, 4D — из `w`. `normWorld` поле `story` сохраняет (только `true`), `normStream`/сохранение мира — тоже.

### 23.3. Рост (`stream.ts`, при `W.story`)

* **Куда** — `transitionTarget` → `storyDest`: кандидаты `storyNexts(биом квартиры локации)` (у лифта — с `{ floor, top:
  roll.floors }`), из них те, что есть в мире; несколько (подвал или катакомбы) — по ключу перехода, поток
  `root.sub("story:" + ключ)`; один — без броска (миры без катакомб — бит в бит прежние). Сюжет не знает или биомов нет —
  как без сюжета. Ангар — тоже по сюжету (завод).
* **Что ставится** — `storySpecials(биом)`: комнаты со спец-локацией `storyVia(биом)` (лифт — оба пресета; люк и дверь
  в снег — с весом роста 0, поровну), из них растущие в биоме (`biomeMul > 0`), а среди них — свои комнаты биома (тег
  «только-биом»), если есть. `via` null / `hangar` / `swamp` — переходов по счётчику нет. Тот же список — у `trFits`
  (запас выходов квартиры под переход).
* **Дверь в снег**: метка с id `SNOWDOOR_CONN = 'snowdoor'` (`src/locations/storyDoors.ts`) у комнаты со спец-локацией
  `snowdoor` стыковкой перехода не служит, а при постановке комнаты любым путём (переход, рост сети, загрузка) — тупик
  (`'vanished'`: ни выходом квартиры, ни проёмом под переход не станет; в индекс петель не попадает): `doorState` —
  `'dead'`, никогда не связывается.
* **`descend`**: лестница, ангар, люк (`rollHatch`), дверь в снег (`rollSnowDoor`, этажей бывает 0). Дверь в снег вне
  сюжета (или сюжет не знает куда) — в снежные тоннели `snow`, если они есть в мире (`snowTarget`, как ворота ангара —
  `factoryTarget`).
* **Свой выход сети** (`ownExit`: хаб со спец-локацией — подтаявшая берлога снега, хаб «Дверь в снег» настоящего
  погреба) — переходов по счётчику в сети нет; `descend` из такого хаба ведёт по сюжету.
* **`fall(id)`** (новый, `WorldOp 'fall'`): из лестницы или лифта — комната прихода в биоме `STORY_FALL` (вход сети
  общаги — вестибюль) на этаже `floor − k` (лестница `floorsDown + 1`, лифт `down + 1`), поток `root.sub("fall:" +
  адрес)`, адрес `childAddr(адрес, '@fall')`, связь `kind 'descent'` + `fall: true`, своя карта (у той же лестницы
  спуск и срыв — разные комнаты); счётчик с нуля; повтор — тот же id.
* **Двери общаги на улицу** (`upBiome`): `STORY_OBSHAGA.streetDoors[root.sub("street:" + адрес двери)]`; в сеть ходов
  (подвал) — `openToNet`: вход сети по `netEntry` (как за дверью площадки-перехода), сеть растёт на ходу. Это дверь, не
  переход — счётчик не сбрасывается.
* **Кольцо из хаба** в сюжете не забирает последние проходы хаба (нужно ≥ 3 свободных): хаб с двумя проходами, куда
  пришли по маршу, иначе замыкался кольцом в тупик, и переход по счётчику не вставал.

### 23.4. Комнаты (`src/data/roomsSpecial.ts`)

* `barn_hatch` «Люк в погреб»: 3×3 м, проход `barn` (юг), проп `p_cellar_hatch` (1×1 м, в полу) **ровно в центре
  габарита**; теги `сарай`, `спец`, `люк`.
* `cellar_snowdoor` «Дверь в снег (погреб)»: тупик хода 2×3 м, вход `basement` (юг), метка `snowdoor` (`corridor>service`
  0.9 м) в западной стене; теги `подвал`, `погреб`, `спец`, `дверь-в-снег` — встаёт в погребе-заглушке (и в подвале по
  тегу, но там сюжет ставит лифт). В режиме «тупики — стены» дверь не рисуется (стена) — её показывает вид по метке.
* `obsh_snowdoor` «Дверь в снег (общага)»: тупик коридора 2×3 м, вход `obshaga` во всю ширину, метка `snowdoor`
  (`obshaga>room` 0.9 м — закрытое полотно двери общаги, как у запертых комнат) в западной стене; теги `общага`,
  `коридор` (кафель), `спец`, `дверь-в-снег`, `только-биом`.

Свой вариант двери в снег у настоящего погреба: комната со спец-локацией `snowdoor` (`newSnowDoor()`), меткой входа под
проход сети погреба и меткой id `snowdoor` на стене, тег группы погреба первым и `только-биом` — `storySpecials` возьмёт
её вместо заглушки. Либо (ходы погреба уже `transitionMinLen`, переходы по счётчику туда не встают) — хаб сети со
спец-локацией `snowdoor` и тегами группы, `хаб`, `только-биом`, весом > 0: сеть получает свой выход (`ownExit`), хаб
растёт по правилу хабов, `descend` из него — в снег. Метку `snowdoor` не делать проходом сети (`TUNNEL_PASS_TAGS`).
Вход в погреб — люк сарая: `entryPool('cellar')` — хабы без спец-локации (лучше с меткой `stair`: в неё приходят).

### 23.5. Сохранение

Ключ мира сюжета — модификаторы `['квартиры', 'сюжет']`: отладочная прогулка того же сида его не трогает. `checkSave`
принимает спуск из лестницы, ангара, люка, двери в снег и срыв (`fall`) из лестницы и лифта (раньше любой спуск не из
лестницы — в том числе ангара — делал мир «устаревшим»); `validateFoldRun` — то же (у двери в снег `floors ≥ 0`).
