# Болванка уровня в Babylon.js

Как превратить JSON прогона Room Forge в сцену Babylon: стены, перегородки, перемычки, полы, потолки,
заглушки тупиков и боксы мебели — с коллизиями, по которым можно ходить. Ядро (что и почему строится,
как решены наложения стен) описано в [`docs/BLOCKOUT.md`](BLOCKOUT.md); здесь — только адаптер Babylon.

- Адаптер: `src/blockout/babylon.ts` — `buildBabylonBlockout(scene, model, opts)`.
- Пример без React: `examples/babylon-demo/` (`npm run dev`, затем `/examples/babylon-demo/` на адресе dev-сервера).
- В Room Forge то же самое — вкладка **«3D»**: облёт, ходьба от первого лица, выгрузка `blockout.json` и `.glb`.

## 1. Подключение к своему проекту

1. Скопировать папку `src/blockout/` целиком (`types.ts`, `core.ts`, `babylon.ts`, `subrun.ts`, `pieces.ts`;
   тесты и `fixtures/` — по желанию, `*.fold.test.ts` — нет: они генерируют прогон модулями Room Forge).
   Она ничего не импортирует из Room Forge. Для складчатых (4D) прогонов — ещё `src/view3d/portal.ts`
   (портальный рендер, §12; зависит только от `@babylonjs/core` и `src/blockout/`).
2. `npm i @babylonjs/core` (проверено на 9.29). Адаптер импортирует модули точечно
   (`@babylonjs/core/Meshes/mesh` и т. п.), так что tree-shaking работает.
3. В своём коде — side-effect импорты того, чем пользуетесь:
   - `@babylonjs/core/Collisions/collisionCoordinator` — без него `checkCollisions` молча не работает;
   - `@babylonjs/core/Culling/ray` — для `scene.pick` (клик по полу → комната).

```ts
import { Engine } from '@babylonjs/core/Engines/engine';
import { Scene } from '@babylonjs/core/scene';
import { UniversalCamera } from '@babylonjs/core/Cameras/universalCamera';
import { HemisphericLight } from '@babylonjs/core/Lights/hemisphericLight';
import { Vector3 } from '@babylonjs/core/Maths/math.vector';
import '@babylonjs/core/Collisions/collisionCoordinator';
import { buildBlockoutModel } from './blockout/core';
import { buildBabylonBlockout } from './blockout/babylon';

const engine = new Engine(canvas, true);
const scene = new Scene(engine);
scene.collisionsEnabled = true;
scene.gravity = new Vector3(0, -9.81 / 60, 0);
new HemisphericLight('sky', new Vector3(0.2, 1, -0.3), scene);

const model = buildBlockoutModel(runJson, { deadEnds: 'panel' }); // чистые данные, без Babylon
const level = buildBabylonBlockout(scene, model, { collisions: true }); // меши, материалы

const player = new UniversalCamera('player', Vector3.Zero(), scene);
player.ellipsoid = new Vector3(0.3, 0.85, 0.3);   // капсула 0.6 × 1.7 м
player.ellipsoidOffset = new Vector3(0, 0.1, 0);  // низ капсулы = позиция − 1.6 м → глаза на 1.6 м
player.checkCollisions = player.applyGravity = true;
const [x, y] = model.rooms[0].anchor;             // план (x, y↓) → Babylon (x, −y)
player.position.set(x, 1.65, -y);
player.attachControl(true);
engine.runRenderLoop(() => scene.render());
```

Перестроить уровень — `level.dispose()` и заново: удаляются все меши, материалы и текстуры адаптера.

## 2. Опции адаптера (`BabylonBlockoutOptions`)

| опция | по умолчанию | что делает |
|---|---|---|
| `collisions` | `false` | `checkCollisions = true` у стен, перегородок, перемычек, колонн, полов (и пола проёмов) и мебели. Потолки и панели тупиков — без коллизий. |
| `merge` | `true` | Объёмы одного вида — в один меш (`wall`, `partition`, `lintel`, `column`). `false` — меш на каждый объём (удобно отлаживать, дорого рисовать). |
| `propTextures` | — | `{ [propId]: 'data:image/png;base64,…' }` — картинка вида сверху на верх болванки мебели. В JSON прогона текстуры есть, только если он экспортирован с ними (`props[].tex`). |
| `colors` | `BLOCKOUT_COLORS` | `#rrggbb` по ключам `wall`, `partition`, `lintel`, `column`, `floor`, `portalFloor`, `ceiling`, `deadEnd`. |
| `finishes` | `true` | Отделка из модели: облицовка стен по `model.faces` (обои, кафель, краска, побелка) и полы по `Surface.finish` (линолеум, паркет, плитка) — §5. `false` — стены и полы с сеткой блокаута. |
| `deadEndColor` | — | `(d: DeadEnd) => '#rrggbb' \| null` — цвет панели тупика. Панели с цветом — отдельный меш на цвет (`deadEnds:#rrggbb`) со слегка светящимся материалом; `null` — обычная панель. Нужно складчатым прогонам: «дверь за границей видимого множества», «дверь в другой слой» (§12). |
| `shared` | — | общие материалы и текстуры многих болванок одной сцены (`createBlockoutShared(scene, colors)`): куски комнат портального рендера (§12) — десятки болванок с одними материалами; `dispose()` болванки общее не трогает, его освобождает `shared.dispose()`. |

Опции самой геометрии (высота стен и дверей, толщина обвязки и перегородок, плиты, потолки, мебель,
тупики, заполнение пустот) — это `BlockoutOptions` ядра, второй аргумент `buildBlockoutModel`
(см. `docs/BLOCKOUT.md`, §4).

## 3. Что возвращается (`BabylonBlockout`)

| поле | что внутри |
|---|---|
| `root` | `TransformNode` «blockout» — родитель всех мешей. |
| `walls` | меши объёмов: при `merge` — до 4 штук (`wall`, `partition`, `lintel`, `column`). |
| `floors` | `floor:<inst>` — пол каждого экземпляра + один `portalFloor` (пол всех проёмов). |
| `ceilings` | `ceiling:<inst>` + `portalCeiling` (если ядро положило плиту над проёмом). |
| `props` | `prop:<inst>:<propId>` — по мешу на предмет (он же коллайдер); верх с текстурой — дочерний меш `propTop:…`; у укрытия (§7) без модели видимая болванка — дочерний `propBox:…`. |
| `deadEnds` | панели тупиков: при `merge` — один меш `deadEnds`, иначе `deadEnd:<inst>:<connector>`. |
| `materials` | общие `StandardMaterial` по ключам `colors` — можно перекрасить или заменить текстуру. |
| `facings` | облицовка стен: по мешу на отделку (`facing:<finishId>`), без коллизий. |
| `finishMaterials` | `StandardMaterial` отделок по id (облицовка и полы); текстура — одна на отделку. |
| `instOf(mesh)` | id экземпляра комнаты по мешу пола/потолка/мебели (`metadata.inst`), иначе `null`. |
| `setCeilingsVisible(v)` | показать/скрыть потолки (вид сверху ↔ от первого лица). |
| `dispose()` | убрать всё созданное адаптером; повторный вызов безопасен. |

### metadata

У каждого меша `metadata` — объект `BlockoutMeta`:

```ts
{ kind: 'wall' | 'partition' | 'lintel' | 'column' | 'floor' | 'portalFloor' | 'ceiling'
       | 'portalCeiling' | 'prop' | 'propTop' | 'deadEnd' | 'facing',
  inst?: string,      // экземпляр комнаты (пол, потолок, мебель, тупик при merge: false)
  finishId?: string,  // отделка: у облицовки и у пола с отделкой
  propId?: string, name?: string, connector?: string,
  cover?: 'bed' | 'table', clear?: number }  // укрытие — только у коллайдера предмета (§7)
```

Комната по клику:

```ts
import '@babylonjs/core/Culling/ray';
scene.onPointerDown = (_e, pick) => {
  const inst = level.instOf(pick.pickedMesh);          // 'i12' или null (стена, проём)
  const room = model.rooms.find((r) => r.inst === inst); // имя, теги, тир, площадь, anchor
};
```

Данные комнаты, которых нет в модели (лут, споты, опасность), — в исходном JSON прогона:
`runJson.instances.find((i) => i.id === inst)`.

## 4. Геометрия, нормали, UV

- **Батчер боксов.** Объёмы не создаются через тысячи `CreateBox`: адаптер собирает вершины сам
  (`BoxBatch` → `VertexData`) — 24 вершины и 12 треугольников на бокс, плоские нормали по граням,
  обход граней лицевой для левой системы Babylon (проверено тестом против `CreateBox`).
  `backFaceCulling` включён: стены видны и из комнаты, и снаружи; z-fighting'а нет (объёмы ядра не
  пересекаются). При `merge` **внутренние грани не выпускаются**: участок грани, которым объём касается
  соседнего (стена | перемычка, перегородка | обвязка), вычитается, остаток режется на прямоугольники.
  Треугольников меньше, а на стыках при MSAA ничего не просвечивает (торец стены под перемычкой
  смотрит в комнату ребром и иначе пробивает облицовку). При `merge: false` боксы замкнутые — для отладки.
- **UV в мировых метрах**, планарно по грани: X-грани → (Z, Y), Y-грани → (X, Z), Z-грани → (X, Y).
  Поэтому одна текстура с периодом 1 м идёт непрерывно по соседним боксам, а масштаб читается сразу.
- **Сетка-текстура** (`createGridTexture(scene)`) — `DynamicTexture` 512 px на 1 м: тонкие линии через
  0.1 м (клетка редактора), толстые — на каждом метре. Белая основа, оттенок задаёт `diffuseColor`.
- **Полы и потолки** — плиты толщиной `slabM` (верх пола — `Surface.z`, низ потолка — `Surface.z`);
  при `slabM = 0` — плоскости (пол смотрит вверх, потолок — вниз).
- **Мебель** — бокс `w × d × h`, пивот в центре на полу, `position = (x, z_пола, −y)`,
  `rotation.y = rot·π/180`. Перед предмета — локальная −Z (на плане при `rot = 0` это +y, низ картинки):
  там тёмная полоска у пола. Текстура вида сверху — отдельная плоскость на 3 мм выше верха с
  `zOffset = −2` (без мерцания); низ картинки = перед предмета, как в редакторе.
- **Тупики** (`deadEnds: 'panel'`) — дверное полотно 4 см толщиной, утопленное в стену на 2.5 см
  (выступает в комнату на 1.5 см, ни одна грань не совпадает с гранью стены), с ручкой-кубиком на
  высоте ~1 м у правого края.

## 5. Отделка: обои, кафель, краска, полы

Если комнатам в Room Forge разыграна отделка, в JSON прогона есть `finishes[]` (id, имя, средний цвет,
бесшовная текстура `tex` — только при экспорте с текстурами, размер повтора `tileW × tileH` в метрах,
`dado`) и у экземпляров `finish: { wall, floor }`. Ядро превращает это в `model.faces` — видимые из
комнат грани стен (по комнате, прямые, без проёмов внутри; участки над проёмами — `part: 'lintel'`) — и
в `Surface.finish` у полов. Адаптер рисует:

- **Облицовку** — вертикальные квады по `faces` на **1.5 мм перед гранью** стены (в сторону комнаты) и
  `zOffset = −1` у материала: без мерцания со стеной и издалека; панели тупиков выступают на 1.5 см —
  остаются поверх. По длине квад продлён на 1.5 мм с каждого конца, чтобы на выпуклых углах (колонны,
  торцы у проёмов) соседние облицовки смыкались без щели. Батч — **один меш на отделку** на всю карту
  (draw calls — по числу отделок), коллизий нет — сталкиваемся со стеной под ней.
- **Dado (двухтонная стена)**: у отделки `dado: { finishId, heightM }` грань делится по высоте — низ до
  `heightM` от пола другой отделкой (кафель в санузле, тёмная краска в подъезде), верх — основной.
  Перемычки над проёмами (выше `heightM`) — целиком основной.
- **Полы** с `finish` — материал отделки вместо сетки; полы проёмов и потолки — как без отделки.

**UV-соглашение** (одно для всех движков — повторите его, если строите облицовку сами):

- стены: `u = (координата вдоль грани) / tileW`, где координата — мировая, по направлению «вправо» для
  того, кто смотрит на стену из комнаты (план: нормаль `+x` → вправо `−y`, `−x` → `+y`, `+y` → `+x`,
  `−y` → `−x`); поэтому узор идёт непрерывно по соседним граням одной плоскости (в т. ч. через перемычку
  над дверью) и не зеркалится. `v = (z − z_пола) / tileH` — низ картинки у пола, верх — вверх;
- полы: `u = x / tileW`, `v = −y / tileH` (вид сверху: верх картинки — к северу плана);
- текстура `Texture(tex, scene, false, true)` — мипмапы, `WRAP`, анизотропия 8; без `tex` — `color`.
- На вогнутых углах фаза узора между гранями не совпадает (как у настоящих обоев).

**Свои материалы отделки** — по id или имени отделки:

```ts
const level = buildBabylonBlockout(scene, model, { collisions: true });
// по id: заменить общий материал отделки (облицовка и полы сразу)
const pbr = new PBRMaterial('wallpaper', scene); /* … */
for (const m of [...level.facings, ...level.floors])
  if (m.metadata.finishId === 'fin_wallpaper_damask') m.material = pbr;
// по имени: найти id в model.finishes
const tile = model.finishes.find((f) => /кафель/i.test(f.name));
if (tile) level.finishMaterials[tile.id].bumpTexture = new Texture('tile_normal.png', scene);
// UV уже в «повторах»: своя текстура на один повтор (tileW × tileH м) ляжет в масштаб.
```

Отключить отделку целиком — `{ finishes: false }` (в демо и во вкладке «3D» — галочка «отделка»).

## 6. Материалы под свой стиль

Три уровня, от простого к полному:

```ts
// 1) цвета — опцией
buildBabylonBlockout(scene, model, { colors: { wall: '#9aa0a6', floor: '#5b4a3a' } });

// 2) общий материал вида — текстура с периодом 1 м ляжет без растяжений (UV уже в метрах)
const tex = new Texture('concrete.jpg', scene);
tex.uScale = tex.vScale = 0.5;                 // плитка 2 × 2 м
level.materials.wall.diffuseTexture = tex;
level.materials.wall.diffuseColor = Color3.White();

// 3) свой материал (PBR, NodeMaterial…) на нужные меши
for (const m of level.walls) if (m.metadata.kind === 'wall') m.material = myConcretePBR;
for (const m of level.floors) if (m.metadata.kind === 'floor') m.material = linoleumByRoom(m.metadata.inst);
```

`dispose()` удаляет только материалы адаптера; свои материалы освобождайте сами.
Вместо боксов мебели обычно ставят свои модели: позиция и поворот — из `model.props`
(`x`, `y`, `rot`, `w`, `d`, `h`) по тем же правилам, или из `mesh.position`/`mesh.rotation` болванки;
болванку тогда можно не строить (`buildBlockoutModel(run, { props: false })`).

## 7. Коллизии и игрок

- `collisions: true` → `checkCollisions` у всего, о что можно удариться (стены, перемычки, колонны,
  мебель) и по чему ходить (полы, пол проёмов). Потолки без коллизий.
- Слитые стены разбиты на подмеши-тайлы **16 × 16 м**: коллайдер Babylon сначала проверяет габарит
  подмеша, поэтому камера сталкивается только с ближними тайлами, а не со всеми треугольниками карты.
- Капсула игрока `0.3 / 0.85 / 0.3` с `ellipsoidOffset.y = 0.1` даёт глаза на 1.6 м и рост 1.7 м;
  в дверь 0.8 × 2.1 м проходит с запасом. `scene.gravity = (0, −9.81/60, 0)` — смещение за кадр.
- Мебель тоже твёрдая: в узком проходе между шкафом и стеной (< 0.6 м) не протиснуться — так и задумано.
- **Укрытия: под кровать и под стол.** Таблица `PROP_COVER` в `src/blockout/core.ts` (по `propId`, отдельно от
  высот `PROP_HEIGHTS`; `propCover(id)`) даёт предмету `PropBox.cover = 'bed' | 'table'` и просвет `PropBox.clear`:
  кровать **0.30 м** (`BED_CLEAR_M`), стол **0.62 м** (`TABLE_CLEAR_M`). Коллайдер такого предмета — не бокс от пола,
  а **плита от `clear` до `h`** (над полом предмета, `PropBox.z` учитывается), и у этого меша
  `metadata.cover` / `metadata.clear`. Стоя (0…1.7 м) и присев (0.2…1.1) игрок в плиту упирается, на четвереньках
  (0.18…0.59) проходит под столом, лёжа (0.05…0.25) — и под кроватью; поза (`src/view3d/posture.ts`) ищет укрытие
  по `metadata.cover` среди коллайдеров. Коллайдер укрытия **всегда невидим**: с моделью предмета видна модель, без неё —
  дочерний меш `propBox:<inst>:<propId>` «плита + 4 ножки 5 см» без коллизий (вызов отрисовки — один, как у бокса).
  Сейчас: кровати `p_bed1`, `p_bed2`, `p_cot`, `p_obsh_bed`; столы `p_table_kitchen`, `p_table_round`,
  `p_obsh_table`. Сплошные до пола (тахта, диван, матрас, тумбовые столы, верстаки) — не укрытия. **Новая кровать или
  стол на ножках — допишите id в `PROP_COVER`.**

## 8. Производительность

Замеры на фикстурах (вкладка «3D», dev-сборка; draw calls — `SceneInstrumentation.drawCallsCounter`):

| прогон | мешей | облёт всей карты | от первого лица | модель (ядро)* | сцена (адаптер) |
|---|---|---|---|---|---|
| 31 комната, gap 1 | 257 | ≈ 230 draw calls | 50–160 | ≈ 40–90 мс | ≈ 45–130 мс |
| 150 комнат, gap 1 | 999 | ≈ 880 | ≈ 105 | ≈ 350 мс | ≈ 155–190 мс |

\* — в браузере, первый вызов (JIT); в node-тестах ядро заметно быстрее, см. `docs/BLOCKOUT.md`, §3.12.

Откуда draw calls: стены — по подмешу на тайл и вид (десятки), полы и потолки — по одному на комнату,
мебель — по одному на предмет (+1 за текстуру верха). От первого лица frustum culling оставляет только
ближние тайлы и комнаты. Если нужно меньше:

- `mesh.freezeWorldMatrix()` для всей болванки (статика), `scene.skipPointerMovePicking = true`;
- без текстур мебели (не передавать `propTextures`) — минус до половины вызовов мебели;
- мебель не нужна по отдельности → `Mesh.MergeMeshes(level.props.filter(...комната...), true, true)`
  по комнатам, или свои модели через `InstancedMesh`/thin instances;
- `scene.freezeActiveMeshes()` после постройки, если уровень не меняется.

## 9. Экспорт GLB

```ts
import { GLTF2Export } from '@babylonjs/serializers/glTF/2.0/glTFSerializer';
import '@babylonjs/core/Shaders/postprocess.vertex'; // см. ниже

const glb = await GLTF2Export.GLBAsync(scene, 'blockout', {
  shouldExportNode: (n) => n === level.root || n.isDescendantOf(level.root), // без камер и света
  metadataSelector: (md) => md?.kind ? { ...md } : undefined,                // metadata → extras
});
const blob = glb.files['blockout.glb'];
```

- Потолки перед экспортом сделайте видимыми (`level.setCeilingsVisible(true)`), если прятали.
- Babylon 9.29 при точечных импортах кодирует текстуры (сетку, текстуры мебели) служебным движком
  `dumpTools`, которому не хватает зарегистрированного вершинного шейдера `postprocess` — без импорта
  выше экспорт падает с `Cannot read properties of null (reading 'program')`. Во вкладке «3D» это
  обойдено так же (+ «прогрев» на картинке 1×1).
- 31 комната → GLB ≈ 1.6 МБ: 257 мешей, у каждого узла `extras` с `kind`/`inst`/`propId`.
  Экспортёр сам переводит сцену в правую систему glTF.

## 10. Система координат и поворот

- План: `x` вправо, `y` вниз, `z` вверх (метры). Babylon: **`X = x`, `Y = z`, `Z = −y`**.
  Вид сверху (камера над сценой, +Z вверх по экрану) совпадает с планом редактора.
- Поворот плана `rot°` по часовой ⇒ `rotation.y = rot·π/180`. Проверено тестом: шкаф с `rot = 90`
  смотрит передом в −X мира (на плане — влево), с `rot = 0` — в −Z (на плане — вниз, +y).
- Адаптер рассчитан на стандартную левую систему Babylon. Если в проекте
  `scene.useRightHandedSystem = true`, план зеркалится по Z: переводите координаты сами
  (`Z = +y`, `rotation.y = −rot·π/180`) и разворачивайте обход граней — либо держите уровень в
  отдельной сцене с левой системой.

## 11. Известные ограничения

- Мебель — меш на предмет (+ плоскость текстуры): на больших картах в облёте это основная часть draw
  calls (см. §8).
- Облицовка не покрывает откосы проёмов (торцы стен внутри проёма) и потолки — там сетка блокаута.
- `merge: false` даёт меш на каждый бокс — только для отладки.
- Коллизии — встроенные эллипсоидные Babylon (`moveWithCollisions`/камера). Для физического движка
  (Havok и т. п.) используйте `level.walls`/`floors` как статические `PhysicsAggregate` с формой `MESH`
  или стройте боксы прямо из `model.solids` (это уже непересекающиеся прямоугольные объёмы).

## 12. Складчатые (4D) прогоны: портальный рендер

Складчатый генератор (`docs/GENERATOR-4D.md`) даёт прогон, где у комнат есть слой `instances[].w`, у
порогов — сдвиг `links[].dw`, а в JSON — `mode: 'fold'` и сводка `fold`. Комнаты разных слоёв занимают
**одно и то же место в 3D**: болванку всего прогона строить нельзя (ядро классифицирует клетки глобально,
пересекающиеся полы отдаст первой комнате), а «нарисовать набор комнат обычной сценой» можно только если в
наборе нет пересечений. Поэтому рендер — **порталами**, как в движках с порталами: каждая комната рисуется
только внутри экранной области проёма, сквозь который её видно, рекурсивно по цепочкам проёмов. Тогда
комнаты могут пересекаться в 3D **даже в поле зрения** — каждая видна только сквозь свой проём, — и
переходы через пороги бесшовны.

| файл | что |
|---|---|
| `src/blockout/pieces.ts` | куски комнат: `buildPiece`, `piecePortals`, `pieceFloorRects`, `mergePieces` (`docs/BLOCKOUT.md` §10) |
| `src/blockout/subrun.ts` | подпрогоны: `subRun`, `layerRun`, `overlapIds` (детектор), `linkBetween`, `pvsIds` (прежний рендер) |
| `src/view3d/portal.ts` | Babylon: `PieceCache` (меши кусков, кэш) и `PortalRenderer` (стенсил, рекурсия, текущая комната, коллизии); зависит только от `@babylonjs/core` и `src/blockout/` — копируется в прототип вместе с ними |
| `src/view3d/fold.ts` | как это подключено во вкладке «3D» (`FoldDriver`): от первого лица — порталы, облёт — башня слоёв |

### 12.1. Куски комнат

Кусок комнаты A — её собственная геометрия (`docs/BLOCKOUT.md` §10): модель «A + все соседи по связям» с
владением, из неё — только объёмы, полы, облицовка, мебель и тупики A. Стена между A и соседом поделена
ровно пополам, проём (пол, перемычка, откосы) — тоже, по плоскости посередине толщины стены. Поэтому:

- кусок не зависит от того, откуда смотрят, — строится один раз и кэшируется (меши, материалы общие на все
  куски — `BabylonBlockoutOptions.shared`, `createBlockoutShared`);
- A и любой её сосед вместе — чистая стыковка (`validateBlockout` пуст: объёмы не пересекаются, пол закрыт,
  проём сквозной; тест `src/blockout/pieces.fold.test.ts` — для каждой связи прогонов с пересечениями);
- комнаты, пересекающиеся в 3D, друг про друга ничего не знают (у куска A в модели только соседи A).

Меши кусков лежат в отдельном слое камеры (`layerMask = PORTAL_LAYER`): обычный проход сцены их не рисует,
их рисует только портальный рендер.

### 12.2. Кадр: схема стенсила

Всё — в `scene.onBeforeDrawPhaseObservable` (кадр уже очищен, матрицы камеры готовы), меши рисуются
вручную `mesh.render(subMesh)` с состоянием стенсила/глубины движка (`engine.setStencilFunction` и т. д.;
у материалов `stencil` не включён — берётся глобальное). Обычные группы рендера идут после (детектор 4D —
в группе 1, поверх всего).

```
стенсил очищен в 0; область комнаты R — пиксели со стенсилом ref
текущая комната: меши — стенсил EQUAL 0 (запись выкл.), глубина LEQUAL + запись, цвет
очередь (в ширину) = [(текущая, 0, без отсечения)]; для каждого (R, ref, отсечение) из очереди:
  проёмы R, которые открываем (п. 12.3): кандидаты P1…Pk
  а) маски всех Pi — только глубина: EQUAL ref, глубина LEQUAL + запись, цвет выкл.
     (ближняя стена R закрывает проём; где проёмы перекрываются на экране — выигрывает ближний)
  б) номер области vi (уникальный в кадре, 1…254): маска Pi ещё раз — глубина EQUAL (только там, где Pi
     ближний), стенсил EQUAL ref, операция INVERT, маска записи ref ^ vi → в области ровно vi
  в) для каждого Pi: заливка области (EQUAL vi): цвет фона, глубина «далеко» (ALWAYS + запись);
     меши комнаты за Pi — стенсил EQUAL vi, глубина LEQUAL + запись, цвет, отсечение плоскостью Pi;
     Pi ближе горизонта — (комната за Pi, vi, плоскость Pi) в очередь; дальше — её проёмы не открываются
```

- **INVERT с маской записи `ref ^ v`** — так из `ref` получается любое `v` одной операцией (REPLACE записал
  бы `ref`, а он нужен для теста). Номера не переиспользуются в кадре — восстанавливать стенсил не нужно:
  каждый шаг работает только в своей области (EQUAL), области не пересекаются.
- **Глубина не восстанавливается**: в своей области каждая комната рисуется после заливки «далеко», а её
  проёмы обрабатываются позже, когда до них дойдёт очередь, — в её области за это время ничего не меняется.
- **Очередь — в ширину**: номера стенсила (254 на кадр) достаются сначала ближним уровням.
- Одна и та же комната может быть видна сквозь разные цепочки — она просто рисуется ещё раз в другой
  области (те же меши, другой стенсил и отсечение).
- Назад сквозь проём, через который вошли, не смотрим (оттуда видна своя же сторона).
- Сверх 254 проёмов в кадре — область отмечается номером 255 и в конце кадра заливается цветом фона
  (на практике в кадре до 12 проёмов на глубину 4, §12.8).

### 12.3. Маска проёма, отсечение, горизонт

- **Плоскость проёма** — середина толщины стены (граница кусков двух комнат). Комната за проёмом рисуется
  с отсечением `scene.clipPlane` по этой плоскости (остаётся её сторона; плоскость отступает на 1 мм назад —
  иначе край откоса комнаты за проёмом резался бы по точности интерполяции): глубже первого уровня за
  проёмом может оказаться геометрия, стоящая в 3D перед ним (в другой комнате цепочки), — она отсекается.
  Плоскость отсечения задана всегда (у текущей комнаты — «ничего не отсекает»), чтобы у материалов был
  один набор defines (без перекомпиляции шейдеров и «неготовых» кадров).
- **Маска — коробка**, а не квадрат: от плоскости проёма в сторону комнаты за ним, без ближней грани и без
  отсечения граней. Когда глаз в миллиметре от плоскости (как раз на пороге), ближняя плоскость камеры
  срезала бы квадрат — а лучи сквозь проём всё равно упираются во внутренние грани коробки. Глубокая
  (0.3 м) — когда глаз ближе 0.25 м к проёму, иначе тонкая (2 мм): глубокая ловила бы лучи, прошедшие
  плоскость в соседней двери вплотную.
- **Коробка шире проёма на 2 мм** — в откосы, пол и перемычку (боковые грани утоплены в стену). Граница
  области на экране задаётся краем видимой геометрии своей комнаты (откос, пол, перемычка обрываются на
  плоскости), а не краем маски: иначе на общем ребре «откос — маска» остаются щели в пиксель, разные до и
  после смены комнаты. Две двери вплотную без простенка — в сторону соседней двери коробка не расширяется.
- **Какие проёмы открываются** — те, что видны в кадре: глаз со стороны комнаты (у проёмов текущей комнаты —
  с допуском 3 см за плоскость, на самой плоскости — у всех); коробка хоть частью — по сохраняемую сторону
  отсечения и в пирамиде видимости (пирамида камеры ∩ пирамиды «глаз — проём» по цепочке). Комнаты, которых
  не видно, не рисуются; видимые — рисуются, как бы далеко ни были. **Тумана не нужно**, даль не
  затемняется.
- **Горизонт** `horizonM` — предел работы на кадр, а не обзора: `viewHorizonM(sightM)` (`src/gen4d/pvs.ts`) =
  max(3·`sightM`, 24 м), без предела обзора — 40 м. Проём, ближайшая точка которого дальше горизонта (или
  глубже 24 уровней), ещё открывается и комната за ним рисуется целиком — физически то, что там стоит, — но
  её собственные проёмы уже нет (в них цвет фона). Это далеко и редко: генератор не пускает прямые по осям
  и диагоналям дальше `sightM`, а косая линия сквозь цепочку дверей длиннее 3·`sightM` — редкость (§12.8: ни
  одного такого проёма на 384 видах двух прогулок).
- **Туман — по желанию (атмосфера).** Рендер сам смотрит на туман сцены: если он линейный
  (`FOGMODE_LINEAR`), проёмы целиком дальше `fogEnd` не открываются — туман там непрозрачен (Babylon
  считает его по расстоянию до глаза). Цвет тумана = цвет фона (`clearColor`) — тогда и заливка областей с
  ним совпадает. Обязателен туман только у прежнего рендера набором (§12.9).

### 12.4. Текущая комната и физика

- **Текущая комната** — по полу, среди текущей и её соседей: пол куска = пол комнаты + её половины
  проёмов, граница с соседом — ровно плоскость портала. Смена — в `onBeforeDrawPhase` перед рисованием, по
  позиции глаза: в кадре глаз всегда со стороны текущей комнаты. Комнату нельзя определять по точке во всём
  прогоне — одну точку занимают несколько комнат разных слоёв; её ведут по переходам, на старте — стартовая.
- **Коллизии** — только у текущей комнаты и у соседа, к проёму которого игрок ближе 0.8 м (один, ближайший:
  соседи между собой могут пересекаться, и стены «чужого» соседа стояли бы в проходе). У остальных кусков
  `checkCollisions = false`. Кусок замкнут сам (полустены вокруг пола), поэтому сквозь стену текущей
  комнаты не пройти, даже если за ней сосед без коллизий. Капсула игрока — §7.
- Свой физический движок: статические тела из `piece.solids` + полы текущей комнаты и соседа у порога,
  переключаются вместе с текущей комнатой.

### 12.5. Почему пересечения теперь допустимы в поле зрения

Луч от глаза до проёма P комнаты R идёт по воздуху R (иначе его закрыла бы стена R, и маска P не прошла бы
тест глубины), а комната за P с R не пересекается (сосед; гарантия localRadius ≥ 1). Значит, в области P
перед плоскостью P нет ничего, кроме R, и всё, что там видно, — комната за P (глубже — отсечение по
плоскости последнего проёма: прямая пересекает плоскость один раз, всё до проёма — по ту сторону
отсечения). Области разных проёмов на экране не перекрываются (стенсил), поэтому соседи, пересекающиеся
между собой, и вообще любые комнаты, стоящие в том же месте 3D, друг другу не мешают.

Генератору больше не нужен запрет пересечений в поле зрения (бесшовность PVS, `fold.seamless`): для
портального рендера достаточно `seamless: false` и `localRadius 1` (комната не пересекается со своими
соседями — нужно стыковке кусков и физике на пороге). Пересечений в 3D при этом в 3–10 раз больше
(`docs/GENERATOR-4D.md` §14.6) — это и есть «квартиры в одной точке».

  открываются): все отличия P от Q обязаны быть внутри проёмов (в Q там фон, ± 2 px сглаживания). Для

открываются — как было, пока туман был обязателен). `tools/qa-3d-nofog.mjs`, «Прогулка» `qa-nofog-2`
(`sightM` 9 м, горизонт 27 м), каждый вид попеременно в обоих режимах, по 30 кадров:

| виды | draw calls ср / макс, без тумана · с туманом | комнат в кадре ср / макс | мс на кадр (swiftshader), без · с |
|---|---|---|---|
| 40: середины 10 комнат × 4 стороны | 34.5 / 94 · 34.2 / 94 | 2.9 / 7 · 2.9 / 7 | 198 · 218 |
| 10 самых глубоких видов обхода | 101.1 / 138 · 101.1 / 138 | 7.1 / 9 · 7.1 / 9 | 332 · 312 |

Цена отказа от тумана — нулевая: проёмов, целиком дальше 9 м, в этих видах почти нет (прямые по осям и

затемнял. Разница в мс — шум программного рендера (±10 %, порядок режимов чередуется). Горизонт 27 м — запас

### 12.8. Бесконечный мир («Прогулка»)

Вкладка «3D», источник **«Прогулка»**: бесконечный складчатый мир (`src/gen4d/stream.ts`,
`docs/GENERATOR-4D.md` §15) от первого лица, портальный рендер. `src/view3d/walk.ts`:

- мир — `createStreamWorld(project, streamSettings(seed, { gap, match, sightM, startRoomId из «Генератора»,
  deadEndChance, branching, aheadDoors из полей }), сохранение)`;
- при входе в комнату — `ensureAround(id)` (двери вперёд) и `ensureVisible(id, viewHorizonM(sightM))`: всё,
  что может попасть в кадр, — окончательно, на ту же дальность, что горизонт рендера (§12.3; для `sightM`
  9 м — 27 м). Раскрываются комнаты, в которые из этой видно по прямой сквозь цепочку проёмов не дальше
  горизонта (PVS той же логики, что у генератора, но с большей дальностью, `docs/GENERATOR-4D.md` §15.7), и
  так до замыкания. Поэтому тумана, прятавшего край сгенерированного, больше нет: в кадре нет ни одной
  нераскрытой двери. Раскрытие — в отдельной задаче после кадра перехода (в момент перехода взгляд — из
  проёма, а он входит в источник набора прежней комнаты, уже замкнутого);
- JSON прогона для кусков собирается по мере роста: экземпляр экспортируется один раз (экземпляры мира не
  меняются), у старых меняются только связи меток и «раскрыта ли дверь»; куски комнат, у которых
  изменились связи или двери, перестраиваются (`PieceCache.setRun`). Ещё не раскрытая дверь — проём в
  темноту (метка `cut` + `openCut`), заколоченная — дверь-панель;
- автосохранение мира — `localStorage[worldKey(seed, mods)]` через 0.4 с после роста (≈ 320 Б на комнату),
  позиция игрока (комната + камера) — раз в секунду и при закрытии страницы (`…/player`). После
  перезагрузки — продолжение с того же места. Кнопки «Новый мир» (случайный сид), «Сбросить сохранение»;
  HUD: комнат сгенерировано, W, глубина, тупиков, время сохранения.

QA `tools/qa-3d-walk.mjs` (сид `qa-walk-1`): авто-ходьба — камера с коллизиями и гравитацией идёт к проёму
и сквозь него, текущая комната меняется сама: **32 порога из 32**, без телепортов и застреваний (проём
проходим, коллизии на пороге не мешают). Мир вырос до 433 комнат (31 слой W, 3809 пар комнат в одном месте
3D; раскрытие экземпляра — 1.4 мс в среднем, максимум 24 мс), сохранение — 141 КБ. После перезагрузки
страницы — та же комната, сдвиг камеры 0 м, все 433 комнаты совпали (id, комната, позиция, поворот, W);
5 порогов назад — те же комнаты. Ошибок в консоли нет. С раскрытием на горизонт (27 м вместо 9 м) тот же
прогон: 32 порога из 32, мир — 440 комнат (+1.6 %), после перезагрузки и назад — всё то же.

**Без тумана: «дыры в пустоту».** `tools/qa-3d-nofog.mjs`: авто-ходьба через 24 порога, в каждой комнате
8 видов (6 из середины по кругу + 2 от входа вперёд). Каждый вид — три кадра: порталы с фоном пурпурным и
зелёным (где они различаются — виден фон) и «области проёмов» (залиты голубым, комнаты за ними не

Нераскрытой двери в кадре не было ни разу: оставшиеся пиксели — одиночные точки на ребре откоса дальнего

### 12.9. Прежний рендер — набор (PVS)

Во вкладке «3D» от первого лица есть переключатель «Порталы / Набор (PVS)». Прежний рендер строит одной
болванкой потенциально видимый набор текущей комнаты (`pvsIds`, `subRun`: связи наружу — проёмы в темноту,
`cutEnds: 'open'`) и на пороге подменяет его набором соседа. Бесшовен, только если генератор запретил
пересечения внутри PVS (`fold.seamless` + `sightM`) — это и убивало суть 4D. Без PVS (`seamless: false`) —
«комната + соседи», и при `localRadius 1` соседи между собой пересекаются — набор с наложениями. Для новых
прототипов — порталы.

Этому режиму (и только ему) **туман обязателен** — во вкладке «3D» он включается принудительно с подписью
«нужен режиму «Набор (PVS)»»: набор отсекает всё дальше `sightM` (косые линии обзора бывают длиннее), за его
краем — проёмы в темноту, и туман, непрозрачный ровно на `sightM`, прячет этот край — иначе на порогах было
бы видно, как комнаты появляются и исчезают. Во всех остальных режимах вкладки (облёт, от первого лица —
«Прогон», «Комната», «Файл», «Прогулка», порталы) тумана по умолчанию нет; галочка «туман на дальности
обзора» в «Атмосфере» — необязательная атмосфера (запоминается).

### 12.10. Двое игроков, детекторы, отладочные виды

- Игрок B **виден** игроку A, если комната B нарисована в кадре A (`PortalRenderer.lastRooms` — с
  повторами цепочек) — и только в областях её проёмов: сущности B рисуются тем же проходом, что и
  комната B (её стенсил и отсечение). Для сервера (interest management) — «комнаты в пределах обзора по
  проёмам»: PVS, если он есть в прогоне, иначе обход по связям до `sightM`.
- Двое в одной точке 3D в пересекающихся комнатах разных слоёв не видят и не толкают друг друга: каждый
  рисуется только в своей области, коллизии — по комнатам.
- **Детектор 4D (отладка)** — как был: контуры комнат других слоёв, стоящих в 3D там же, где текущая
  (`overlapIds`), поверх всего (группа рендера 1). На скриншотах из `tools/qa-3d-portal.mjs` видно, что они
  там есть, но в кадре их нет.
- **Облёт** — как был: башня слоёв, один слой, видимый набор выбранной комнаты (обычные болванки частей).

### 12.11. Рекомендации для прототипа

1. Скопировать `src/blockout/` (с `pieces.ts`) и `src/view3d/portal.ts` (поправить пути импорта), камеру —
   как в §1; `scene.collisionsEnabled = true`, движок с `stencil: true`.
2. `const cache = new PieceCache(scene, runJson, { blockout: { deadEnds: 'panel' } });`
   `const portal = new PortalRenderer(scene, camera, cache, { horizonM: viewHorizonM(sightM), onCross: (from, to) => … });`
   `portal.setCurrent(startId); portal.setActive(true);` — дальше всё сам: кадр, текущая комната, коллизии.
   `viewHorizonM` — из `src/gen4d/pvs.ts` (или `stream.ts`): max(3·`sightM`, 24 м), без предела — 40 м.
3. Тумана не нужно. Если хочется атмосферы — `FOGMODE_LINEAR`, `fogEnd = sightM`, `fogStart ≈ 0.45·sightM`,
   `fogColor = clearColor`: рендер увидит туман и не будет открывать проёмы за `fogEnd`. Бесконечный мир —
   `world.ensureVisible(id)` при входе в комнату (по умолчанию — на ту же дальность `viewHorizonM`).
4. Куски строить заранее (соседи и соседи соседей — `cache.get(id)` в свободное время), ограничивать кэш
   (`cache.trim(нужные)`: предел по памяти и по числу кусков — Babylon каждый кадр перебирает все меши сцены).
5. Свои материалы — как в §6, но через общий набор `cache.shared` (материалы всех кусков одни).
6. Генератор: `fold: { seamless: false, localRadius: 1 }`, `gap ≥ 1`, `sightM` 7–9 м.

### 12.12. Ограничения

- `gap = 0` — во внутренних углах, где сходятся три комнаты, облицовка может на ≤ 2.5 см не иметь стены
  своего куска за собой (видно только без отделки); для складчатых прогонов — `gap ≥ 1`.
- Две двери вплотную без простенка: граница «двух миров» на линии стыка при смене комнаты может сдвинуться
  на 1–2 px (§12.6).
- Мебель и прочее, торчащее из комнаты сквозь проём в соседнюю, обрезается плоскостью проёма (в коробке
  комнаты за проёмом её нет).
- За горизонтом (`viewHorizonM`: 3·`sightM`, не меньше 24 м; без предела обзора — 40 м) комната за проёмом
  рисуется без своих проёмов — в них цвет фона. Сверх 254 проёмов в кадре — то же для всей области проёма.
- Весь складчатый прогон одним GLB не выгрузить (наложения): во вкладке «3D» выгружается то, что на
  сцене в облёте (набор, слой или все слои башней).

### 12.13. Шов бесконечного хода (портал со сдвигом) и модели предметов

**Шов.** Связь `links[].wrap = [dx, dy]` (клетки плана; бесконечный прямой участок подвала, docs/GENERATOR-4D.md
§17.6): комната `b`, сдвинутая на `wrap`, стоит лицом к `a`, а на самом деле — далеко. В модели целиком шов — не проём
(тупики). Кусок комнаты строится по окрестности, в которой сосед по шву **сдвинут** (`translateInstance`), — проём
открыт, как у обычного соседа; у портала куска `shift` — сдвиг в метрах плана (со стороны `a` — `+wrap`, со стороны
`b` — `−wrap`).

Портальный рендер: у каждого задания очереди свой сдвиг сцены `off`. Комната рисуется на своём месте, вид — перенос на
`off` · вид камеры (`scene.setTransformMatrix`); отсечение и пирамида видимости переводятся в её систему
(`movePlanes`: свободный член плоскости + n·shift), глаз — `eye − off`. За швом `off` растёт на `shift`, так что ход
сквозь шов уходит вдаль, повторяясь (до горизонта и `MAX_LEVEL`). Текущая комната: глаз за плоскостью шва (в пределах
проёма) — камера переносится на `−shift`, текущая — комната за швом (`onCross`, `onWrap`); кадр этого шага рисуется
со сдвигом `+shift` от старых матриц — картинка не прыгает. Коллизии соседа за швом не включаются (он далеко).

**Модели предметов.** `BabylonBlockoutOptions.propModel(propId)` — шаблон модели (выключенный меш: перед — −Z, низ —
пол; у подвесных — тег «потолок» — верх в 0). Есть шаблон — бокс болванки остаётся **невидимым коллайдером**, его
ребёнок — клон шаблона (геометрия и материалы общие); подвесное — под потолком (`wallHeightM`). Портальный рендер
рисует только видимые меши куска. Шаблоны — `src/view3d/propModels.ts`: GLB набора (`basement_props.glb`, узел на
prop), меши узла слиты в один, материалы glTF заменены стандартными (тот же свет, что у болванки; лампочка светится).
Просмотрщик грузит их при создании и сообщает `onPropsReady` — части и куски пересобираются с моделями.

**Подвижные части** (завод: шестерни, маховики, валы, вентиляторы, ролики, пресс, капли — `factory_props.glb`,
`tools/optimize-factory.mjs`). Узел модели с `extras.anim` — подвижная часть: свой шаблон, ребёнок шаблона предмета
(`rotor:<id>:<k>`, покой — единичная трансформация). Клон модели в болванке — **с детьми**
(`tpl.clone(…, false)`), клон части — `<клон>.rotor:<id>:<k>`; `PropAnimator` (`src/view3d/propAnim.ts`) ловит такие
меши при добавлении в сцену и каждый кадр ставит позу (равномерное вращение или выборки за период; фаза — по клону
предмета: пара шестерён согласована); замороженную матрицу куска портального рендера перезамораживает. Движку:
`extras.anim` — `{ spin, pivot, turns, period }` или `{ period, n, p, q, s? }` в системе предмета glTF; в левой
системе Babylon ось x отражена (кватернион `(x, −y, −z, w)`, перенос `(−x, y, z)`).

## 13. Спец-локации: своя сцена поверх болванки

Комната со спец-локацией (`Room.location`, [LOCATIONS.md](LOCATIONS.md)) в 3D — отдельная сцена Babylon в том же
движке: `BlockoutViewer.setOverlay(scene)` рисует её вместо болванки и отключает камеру болванки от ввода; в
«Прогулке» вход — порог в такую комнату, выход назад — `FoldDriver.placeAtDoor` (к той же двери), вниз —
`world.descend` → комната-выход. Связи `kind: 'descent'` в JSON болванки не попадают (это не проёмы).
«Бесконечная лестница» (петля из 5 модулей GLB, контроллер по карте высот, фонарик и лампы, WebAudio, захват,
перенос в игру) — [LOCATION-STAIRWELL-BABYLON.md](LOCATION-STAIRWELL-BABYLON.md).

## 14. Двери

`BlockoutOptions.doors` — у меток слоты дверей (`BlockoutModel.doors`, `DoorSlot`): какая дверь из каталога
(`src/blockout/doors.ts`), где петли, закрыта или распахнута. Адаптер рисует наличники и неподвижные полотна одним мешем
`doors`, полотна закрытых выходов — отдельными мешами на оси петель (`bo.doorLeaves`, `poseDoor`); закрытые двери —
вместо панелей тупиков. Анимация открытия и бесшовная подмена «стена → проём» за закрытым полотном, список дверей по
локациям, правила выбора и как поставить свои модели — [DOORS.md](DOORS.md).
